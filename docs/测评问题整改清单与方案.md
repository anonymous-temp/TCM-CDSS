# 灵犀中医CDSS测评 · 问题清单与整改方案

> 来源:《灵犀中医CDSS测评.docx》(医学测试 2026-07-15,用例=演示病例+西宁测试),含 11 张截图逐一核对。
> 编号:M=医学测试结果,P=产品侧问题。行号会漂,以函数名/字符串为准。

## 1. P0 级

### P3 首次推药必失败(截图9:红卡"候选方药未完成,请重新生成")

- **现象**:每次第一次进入候选方药必失败,重试后成功。既毁演示信任,又直接把全链耗时翻上去(连带 P2)。
- **根因排查路径**(必现=确定性问题,可查):
  1. 服务器日志 `grep "finalized M04 rejected"` / `finalized_prescription_` 看 `issue` 值——M04 的 `outputTransform` 在 `formulaCompilationContractIssue` / `m04SemanticIssue` 拒绝时会 throw(`prescribe/route.ts` outputTransform)。
  2. 重点怀疑**新加字段首验必败**:`modifications`/`symptomClusters`/`rootDeficiency` 等 7-15 刚加的字段,若 zod/语义合同对模型第一版输出过严(如空值/别名),会稳定首拒、重试时因提示词携带失败上下文而通过。
  3. 也要排除:首个请求冷启动(evidence 检索超时 12s 连锁)、签名 M03 未就绪竞态。
- **整改**:
  1. 按日志定位具体 `issue`,**修产出端**(prompt 给该字段更明确格式)或**松校验端**(可选字段坏行丢弃而非整单拒绝——`m04-proposal-compiler.ts` 已有"malformed optional row must not…"注释,把该原则贯彻到所有新字段);
  2. 结构化拒绝**服务端自动重试**(已有 `validatedStructuredReasoning` 可重试机制,把首败类 issue 纳入重试白名单),用户不应看到"请重新生成";
  3. 保底:重试仍失败时,红卡文案降级为草稿+说明,而非空板块(伴随式原则)。
- **验收**:连续 10 个新病例,首次 M04 成功 ≥9;用户可见"重新生成"卡出现率≈0。

### P2 全链耗时 >5 分钟

- **现象**:M01→M05 超 5 分钟,门诊不可用。
- **分解与措施**(先测后改,给每阶段加服务端耗时日志再动手):
  1. **修 P3 即提速**:消除"必失败+整段重跑"直接砍掉一整个 M04 时长;
  2. **输出瘦身(预计最大头)**:M03 同时输出 Markdown 深度正文 + 完整 sentinel JSON,内容大量重复(前端已改从 JSON 渲染)。砍掉 Markdown 中与结构化重复的表(证候分布/子病机/证据链表),预计省 30-50% 输出 token≈同比例省时;
  3. **证据检索并行/限时**:`buildCdssEvidenceContext` 在流前 await(M03/M04 各一次),EviMed 超时 12s;改并行预取+缓存(同病例复用)+超时降级 6s;
  4. **参数**:diagnose/prescribe 已是 flash+关思考;`max_tokens 24000` 在输出瘦身后可回落(约 12-16k),减少长尾;
  5. 可选:M03 出来医生审阅期间**后台预生成 M04**(注意签名链依赖,只预热不落地)。
- **验收**:演示病例全链 ≤2.5 分钟(建议目标 M03≤90s、M04≤90s);各阶段耗时有日志可查。

### M2 "中医证候"→"中医诊断",失眠应叫"不寐"(截图2)

- **现象**:诊断结论右卡标题"中医证候",内容"失眠(心脾两虚证)"。医学规范:中医诊断=**中医病名+证型**,失眠的中医病名是"不寐"。
- **整改**:
  1. **前端**:卡标题"中医证候"→"中医诊断";展示格式:`不寐(心脾两虚证)`——病名+证型;
  2. **确定性病名映射表**(新建小词表,如 `tcm-disease-names.ts`):西医/口语病名→规范中医病名(失眠→不寐、头晕→眩晕、胃痛→胃脘痛、心慌→心悸、便秘→便秘…),在解析后**代码强制覆写**(沿用 `determineCompletenessLevel` "代码覆盖模型"的既有模式),模型写了"失眠"也纠成"不寐";
  3. **prompt**:M03 要求 `overview` 给规范中医病名(可新增 `tcmDiseaseName` 字段,与证型分开)。
- **验收**:演示病例显示"中医诊断:不寐(心脾两虚证)";词表内病名 100% 归一。

### M4 子病机"本/标"语义错误(截图4)

- **现象**:子病机1[始动][本]=脾虚失运,子病机2[标]=心血亏虚。专家:**本=心脾两虚,标=失眠**;把病机链下游的虚证(心血亏虚)标成"标"是医学错误——标本是"本质vs表象"关系,不是"先后"关系(先后已有"始动/传变"承载)。
- **整改**(建议取②,最不容易再错):
  1. ~~逐节点修 prompt 里 `biaoBen` 定义~~(逐节点标本本来就容易错);
  2. **子病机卡只保留"始动/传变"时序徽章,去掉逐节点 本/标**;"本虚标实"改为病机小结里**全案一句**:`本:心脾两虚(气血不足);标:不寐,兼食少便溏`——prompt 新增全案级 `biaoBenSummary{ben,biao}` 字段(或复用 rootDeficiency/branchExcess 拼装),前端在病机分析顶部渲染一行;
  3. "始动/传变"给 hover 提示(始动=最先发生的病机环节),避免再被问"是什么含义"。
- **验收**:演示病例病机区显示"本:心脾两虚;标:不寐";子病机卡不再出现逐节点 本/标 徽章。

## 2. P1 级

### M3 病位/病性辨证只是现病史罗列、无分析;"本虚"不是病性(截图3)

- **现象**:病位辨证"脾:现病史:入睡常需1小时,多梦易醒…"——把整段现病史原样当依据贴给每个脏腑,没有"症状→脏腑"的提炼;病性辨证类目名显示"本虚:脾气虚、心血虚","本虚"不是病性术语(应为气虚/血虚/气血两虚等)。
- **整改**:
  1. **prompt 约束依据必须是提炼式对应**:每脏腑 basis ≤60 字,格式"具体症状/舌脉 → 归该脏腑的理由"(如"纳差便溏、舌边齿痕 → 脾失健运;心悸健忘、脉细弱 → 心血不足,心神失养"),**禁止整段复制现病史**(可在 schema 上限 basis 长度硬约束,超长截断即倒逼提炼);
  2. **病性辨证渲染改造**:类目直接列病性项(气虚、血虚,或合成"气血两虚");`rootDeficiency/branchExcess` 不再以"本虚/标实"作病性类目名出现——挪去 M4 的全案"本:…标:…"行;
  3. 判断依据同样按"症状→病性"提炼(舌淡齿痕、脉细弱、面色少华 → 气血两虚)。
- **验收**:病位/病性卡不再出现"现病史:"整段引用;病性类目无"本虚"字样。

### M5 治则治法只有治法、无治则(截图5/8)

- **现象**:板块只展示"总治法:补益心脾、养血安神"+分治法。缺**治则**(原则层:如"补虚为主,标本兼顾;虚则补之,先健脾以资化源")。
- **整改**:`therapy.overallPrinciple`(总治则)字段**本来就有**——①核对 M03 prompt 是否要求其为"治则"(原则性表述,与治法区分,给一个例句);②前端"治则治法"板块加"治则"一行渲染 overallPrinciple(当前只渲染了总治法)。顺带:两张分治卡都显示"主要治法"(截图8),按 `priority` 渲染"主要/次要"。
- **验收**:板块内"治则:""总治法:"两行齐全且内容不同质。

### P4 随症加减:要主动建议,不是只给工作台(截图10)

- **现象**:只有"药味加减工作台"(医生自己增删改)。专家预期:系统在主方上**主动给条件加减建议**——若烦躁→加合欢皮;若便溏加重→加芡实;46岁轻度气血不足→减人参量或党参代替。
- **整改**(方案桶C1 的收尾,后端已铺路):
  1. `formula.modifications[]` schema/compiler 已就位(`normalizeModifications`)——核对 **M04 prompt 是否真的要求产出**(条件/动作[加|减|替换|调量]/药味/剂量/理由),没有就补槽位;
  2. **前端主方下渲染"随症加减建议"卡**(条件→动作→理由),置于工作台之前;工作台保留,改名"处方调整"(医生编辑工具定位);
  3. 安全边界:每条建议标注"加减未经审方,采纳后请更新风险提示"(工作台已有该机制,建议卡对齐);加味药仍过十八反/剂量词表校验。
- **验收**:演示病例主方下出现 ≥3 条条件加减建议,含加/减/换三种动作类型。

### P5+M1 一致性专项:同输入不同输出(截图7 vs 11;M02 昨天不问今天问)

- **现象**:①同一病历(主诉只多一个句号)两次西医诊断:"慢性失眠障碍(Chronic Insomnia Disorder)" vs "非器质性失眠症(失眠障碍)";鉴别方向一次是 RLS,一次是 OSA+焦虑抑郁。②演示病例昨天未触发追问、今天触发(演示脚本预期"信息充分时自动推进")。
- **根因**:LLM 采样随机性未被收口:病名无归一词表;鉴别方向无规则约束;M02 触发依赖 M01(LLM)结构化结果的字段存在性,LLM 波动→完整度启发式翻转。
- **整改**:
  1. **温度归零**:M03/M04/collect 温度设 0(现 `PRIMARY_TEXT_TEMPERATURE=0.1`,并核对 diagnose/prescribe 各自 override);
  2. **西医病名归一表**:同义病名(慢性失眠障碍/非器质性失眠症/失眠障碍→统一规范名+ICD 编码)代码层覆写,与 M2 的中医病名表同一套机制;
  3. **鉴别方向规则化**:常见鉴别由确定性触发规则兜底(病历含"否认打鼾"→OSA 固定进入"需排除"并引用该否认;心悸健忘→焦虑抑郁量表建议固定出现),模型自由发挥的鉴别列在其后——保证核心鉴别集合稳定;
  4. **M02 触发确定性化**:`deriveOperationalCompleteness` 的 infoGain/answerability 改为**从医生原始录入字段**(HIS 表单原文)计算,不依赖 M01 结构化结果;演示病例(全字段)应稳定直通,删舌脉后稳定追问;
  5. 说明层:向用户明确"同案复跑,病名/证型/鉴别集合稳定,措辞可能微调"。
- **验收**:演示病例连跑 5 次:西医诊断名、中医病名+证型、鉴别集合 5/5 一致;全字段版 0/5 触发追问,删舌脉版 5/5 触发。

## 3. P2 级

### M6 煎服法写清火候与服药-进餐间隔(截图6)

- **现象**:"一煎30分钟"没说火候;"早晚分服"没说饭前饭后。
- **整改**:`applyDeterministicDecoctionMethod`(`diagnosis-visible-summary.ts`)确定性模板升级:
  - 煎煮:"冷水浸泡30分钟;**武火煮沸后转文火**,一煎30分钟、二煎20分钟;两煎合并约500mL"(特殊煎法照旧逐味标注);
  - 服法:"早晚各一次,**餐后约1小时温服**(与进餐间隔约1小时)"。
  - 纯改模板字符串,零模型依赖;文本请药师过目一遍。
- **验收**:煎服卡含火候与进餐间隔表述。

### P1 "模型输出基于什么?"——来源说明

- **现象**:评审方不清楚结论来源(病案数据?大模型?)。
- **整改**:①报告页固定脚注/「关于本报告」弹窗:"由大模型临床推理 + 本地中医药知识库(方剂出处/饮片剂量/配伍禁忌)+ 循证证据检索 + 确定性安全规则与合理用药审方共同生成;每个结论附证据标注;仅供医生决策参考"。②对外一页纸说明(给评审/院方):数据流、知识库构成、安全层职责。不涉及代码改动,纯文案+一个渲染位。
- **验收**:报告页可见来源说明;评审侧不再有此疑问。

## 4. 建议执行顺序

1. **先查 P3 日志定根因**(半小时内能定位)→ 修首败+服务端自动重试——它同时是 P2 的最大单项;
2. M2 + M4(医学正确性,专家点名,改动小:词表+渲染+prompt 一句);
3. M5 + M6 + P1(小改,一次带过);
4. M3(prompt 约束+渲染调整);
5. P4(随症加减建议卡——后端已铺路,补 prompt 槽位核对+前端卡);
6. P5+M1 一致性专项(温度/词表/规则化/M02 确定性触发);
7. P2 性能余项(输出瘦身、证据并行)。

## 5. 回归(改完必跑)

- `npx tsc --noEmit` + `npm run lint`
- `npm run regress:tcm-cdss`(golden;病名归一/文案改动会影响断言,需同步更新)
- `regress:quality-flow` / `quality-deep`(M04 首次成功率纳入 quality-deep 断言:首试即成)
- 演示病例人工过 5 遍:一致性验收(§P5)+ 首败验收(§P3)+ 医学项逐条对照截图确认。
