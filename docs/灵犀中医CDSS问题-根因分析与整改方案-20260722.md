## 0. 核心架构原则：数据表驱动，不打补丁

测评暴露的问题有一个共同形态：**约束写在代码里（正则、关键词、if 分支），覆盖面靠猜**。补丁式加词永远落后于真实语料。整改统一按以下范式：

1. **词表即数据**：所有词族（证型/病性/病位/治则/检查检验/红旗线索/工程术语/方名别名/药品别名）抽为 `src/data/` 下的数据表（JSON，构建产物或治理产物），代码只存"匹配逻辑"，不存词条。
2. **组合式规则替代平铺列举**：规则 = 词表维度组合（如红旗 = 急迫线索词族 × 症状词族 × 病程词族 − 缓和/否定线索），覆盖来自维度乘积而非逐条枚举。
3. **覆盖度可测**：每张词表配三类测试——①表内完整性（别名归一闭环、无重复无冲突）；②语料回扫（deeptest 病例库 + 测评病例 + fixtures 的真实文本过一遍，输出/输入中出现的目标词必须命中词表，漏词即测试失败并进入增补流程）；③变异矩阵（维度组合采样断言行为）。
4. **单一事实源**：每张表有唯一消费入口，prompt 注入、确定性校验、UI 展示、测试四处同源引用，杜绝双边界漂移。

## 1. 类 A：性别必填（问题 1）— 决策：按建议采纳

- **方案**：性别必填落地两层——客户端 `SelectCell required`（工作区已修）+ 服务端 fail-closed：`collect` 路由按"必填矩阵"校验，缺性别返回可修复 400（结构化 missingItem）。"其他或未明确"= 已填，放行流程，但 `patientSexText` 返回空 → 剂量级处方保持锁定（现有机制自洽，保留）。
- **数据表化**：必填矩阵（字段 × 阶段[建案/诊断/剂量级] × 是否阻断 × 文案）做成 lib 常量表，UI 星号、空态文案、服务端校验、测试四处同源。
- **验收**：`test:safety-mutations`；regress 增加"直接 API 建案缺性别 → 400"用例。

## 2. 类 B：红旗触发边界（问题 2）— 决策：LLM 驱动为主，规则融合

**测评根因**：截图"AI语义分诊提示：当前信息支持急腹症红旗"出自 LLM 语义回补层（`clinical-facts.ts:49`），HEAD 确定性词表不含"胃痛"。双边界 + 红旗无来源 + 文案一刀切"程序化"，造成"触发原则不明"。

**整改架构（LLM 主裁 + 规则三角色）**：

1. **LLM 语义分诊为主裁**（保留并强化）：`clinical-facts.ts` 抽取层继续负责自然语言红旗判断——这是覆盖真实场景的正确载体，口语、变体、组合表述靠模型。
2. **规则层三个角色**（不做主裁）：
   - **保命兜底**：T6 词族维度组合命中（急迫线索 × 高危症状词族）→ 确定性直接红旗，不等 LLM，防模型漏判；
   - **LLM 输出约束**：schema + quote 逐字 grounding + urgency 合法性（已有机制，保留）；
   - **误报护栏**：缓和/否定线索表（"已缓解""偶尔轻微""查无异常"）确定性降级 urgency，防过度触发。
3. **同源注入**：T6 词表既驱动兜底规则，也注入 LLM 分诊 prompt 作为分诊依据（替代当前 prompt:829 的散写规则文字），还作为 UI"命中依据"展示——三处同源，边界一致可见。
4. **红旗带来源**：`redFlags` 从 `string[]` 改为 `{ message, source: "rule"|"llm", category, quote, matchedTerms? }[]`；红旗排查表加"命中方式/原文依据"列；"程序化红旗指征"措辞废弃（工作区已在改）。
5. **边界文档化**：每类目的触发/不触发边界写入词表注释与医生可见的分诊说明（红旗表"判定依据"列自动生成）。
- **验收**：变异矩阵按 T6 维度组合采样（含"胃痛3+小时不触发 / 突发胃痛触发 / 已缓解的突发胃痛降级"）；regress 两个测评输入对齐期望。

## 4. 类 E：方剂"数据源割裂"——重新定性与检索架构重建（问题 20、21）

### 4.1 根因重新定性（实测结论）

> 以下为 2026-07-22 整改前基线，用于保留根因证据；整改后规模与状态以 §9 为准。

测评现象（无方名出处 + 选药偏弱）的真正上游**不是"两个数据源没关联好"，而是治理目录基线错误**：

- 检索锁定层只查 `tcm-formula-indications.json`：governed 203 = **200 首《古代经典名方目录》**（监管目录，一贯煎/三甲复脉汤类）+ **3 首人工核验补充**（归脾汤/酸枣仁汤/逍遥散），其中仅 90 首匹配到主治文本。
- 实测：**龙胆泻肝汤、丹栀逍遥散、天麻钩藤饮、六味地黄丸、桂枝汤、银翘散、补中益气汤全部不在 203 内**。演示病例的归脾汤能用，只是因为它恰好是那 3 首补充之一。
- 所以肝火扰心病例检索必然空手 → `enforceRetrievedM03FormulaSelection` 降级自拟 → 方名出处消失（自拟的 model_inference 证据被 UI 隐藏）+ 选药失去经典方组成锚定（确定性校验只拦"方向不成立"，拦不住"力度不足"）。**20 和 21 同源。**
- 另一个实测警示：84295 底表同名多方严重（"逍遥散"首条命中是《赤水玄珠》变体方，"龙胆泻肝汤"首条出处《羊毛温证论》），**不能简单把 84295 直接当权威源灌进来**，需要治理。

### 4.2 整改：方-证-药一体化数据与检索架构

**第一步：建 T8 临床高频方治理目录**（这是"大量数据表单"的核心一张表）

- 基线：《方剂学》教材正方 + 临床高频方，目标 300–500 首（覆盖内妇儿外常见病机），不是 203。
- 每首方走**现有 verified supplement 治理通道**（tcm-verified-formula-supplements.json 的机制放大）：标准方名、**别名表**（丹栀逍遥散=加味逍遥散）、标准出处（以权威典籍为准，84295 非标准出处仅作 variant 记录）、标准组成（药名+剂量基线）、主治原文、**结构化标签**：证型标签（引用 T1 id）、病机要素（T3 病位 × T2 病性）、症状标签、中医病名、核验来源（书证/URL）。
- 底本：84295 表 + KB 交叉比对生成候选，治理后入库；构建脚本改造 `build-tcm-formula-indications.py` → `build-tcm-formula-catalog.py`。
- 与饮片 KB 关联：组成药名经既有饮片归一表（`中药饮片标准名别名炮制品映射表`，T9）映射到 `tcm-knowledge.json` herbs（剂量上限/十八反/特殊人群/煎服法）——**方→药→审方数据链贯通**，这也是后续"选药充分性"校验的数据基础。

**第二步：检索逻辑重建**（替换当前"26 概念桥打分≥2"）

- **构建期**（不是运行时猜）：从 T8 的结构化标签直接建倒排索引——证型→方、病机要素→方、症状→方、病名→方、别名→正名。
- **运行时多路召回 + 融合打分**：
  1. 证型精确路：M03 签名证型经 T1 归一 → 直查倒排（权重 3）；
  2. 病机要素路：pathogenesis chain 的病位×病性组合 → 查倒排（权重 2）；
  3. 症状/病名补充路（权重 1）；
  4. 融合：≥3 分且证型或病机路至少一路命中 → 入短名单（top 5）注入 M03/M04 prompt；否则回落自拟（诚实标注）。
- **锁定后核验**：命名方的组成/出处由服务端从 T8 编译（provenance 链已有），组成核验不过 → 自拟。模型永远不背方剂组成。
- **审计**：每次检索记录召回路径/得分/未锁定原因（哪个环节为空）→ 回归分析"为什么没锁到"，驱动 T8 持续增补。
- **选药充分性**（问题 21 的双保险）：M04 reviewer prompt 加"核心证候覆盖强度"维度；确定性检查"P1 治法方向 ⊆ 君+臣药 KB 功效概念并集"（概念数据来自 T9 饮片功效表，基建已有 stage-contract:1375-1382）。

**为什么这能根治**：证型归一（T1）+ 治理目录（T8）+ 构建期倒排，使"能不能锁到方"变成一个**可测的数据覆盖率问题**（黄金病例集锁定率指标），而不是运行时的概率事件；方名别名归一同时消除"同药不同名不同结果"整类问题。

- **验收**：黄金病例集（含 7-21 两个测评病例 + 演示病例）锁定率 ≥90%；肝火扰心 → 龙胆泻肝汤/丹栀逍遥散入短名单；自拟方 UI 明确标注"自拟·无经典方名出处"+ 组方依据。

### 6.2 整改：输出契约注册表（Output Contract Registry）

### 6.3 易用性审查清单（医生视角，随契约测试一起落地）
