## 一、逐条回复

### 1. 西医诊断下仍复述主诉、现病史 —— ✅ 已解决

**根因**：`isNondiscriminatingWesternSupportingFact` 是"什么可以充当西医诊断依据"的唯一判据。
它此前排除了中医四诊、人口学、正常生命体征三类，**独缺"就诊经过"这一类**。
于是"发病后因患者自觉症状不重，未正规诊治……故来就诊"原样通过，医生在"支持依据"里读到一段现病史。

**处置**：补上该类判据。生产实测（贵方原始病例）：西医诊断段落无病史复述。

---

### 2. 中医鉴别仍是"证候鉴别"而非"病名鉴别" —— ✅ 已解决

**根因**（这条值得展开）：`tcm-disease-lexicon.json` 收录 1267 条中医病名，**每条都带 GB/T 15657-2021 层级编码**：

```
A07.01        颅脑类病
A07.01.02     头风病
A07.01.02.01  外感头痛   .02 内伤头痛   .03 偏头风   .04 厥头痛   .05 雷头风
```

**这套编码本身就是"相邻病名"关系。** 而运行时只用了 `canonical`/`aliases` 建归一表，
**`code` 字段一次都没有被读取过**。

后果是一条因果链：服务端不知道相邻病名是谁 → 既无法要求模型给出病名鉴别、也无法判断它给的是病名还是证型
→ `tcmDiseaseDifferentials` 字段在 schema、提示词、Markdown 摘要里**早就都有**，却从来没有被填过。
贵方连续两轮写同一句话，原因在此。

**处置**：把层级编码接入判断。生产实测：头痛例给出**眩晕、郁病**两项病名鉴别；
另一次运行给出**真头痛**并附急诊排查指征（"若出现突发剧烈头痛、喷射性呕吐、意识改变，需急诊排查"）。

### 3. 产后气血亏虚头痛病位仍写"脾、心、清窍" —— ✅ 已解决

**根因**：`tcm-symptom-axis-map.source.json` 是症状→病位的受治理映射，
原有 61 条**全部是伴随症状**（便溏/纳呆/心悸/神疲/盗汗…），
**各科最高频的部位性主症一条都没有**——头痛、胃痛、腰痛、牙痛、皮肤瘙痒、月经异常全缺。
同一张表里"头晕"有映射而"头痛"没有，正是漏掉最关键一项的形态。

**处置**：补齐部位性主症映射。生产实测病位为 `["心","脾","脑窍"]`，并携带依据与边界：

```json
{"location":"脑窍","basis":"产后2月余，头痛反复发作1月"}
resolution: "bounded"
resolutionReason: "病位判断基于症状与舌脉；但缺乏饮食、二便等脾运化信息，边界待补充"
```

### 4. 治法仍包含"养心安神" —— ✅ 已解决

**根因**：治则词表 1276 条中，**956 条治法类术语的 `relationPolicy` 字面写着 `method_requires_case_binding`**
——词表自己声明"这条治法必须绑定到本例才成立"。而运行时唯一读取口的过滤条件是：

```ts
entry.relationPolicy !== "method_requires_case_binding"   // ← 把这 956 条全部排除
```

于是 `therapy.overallMethod` 这一栏**在服务端从来没有被任何受治理词表约束过**，
那句 `requires_case_binding` 也从未被核对过一次。治法可以凭空多出一个方向。

**处置**：接通该约束。生产实测治法为"补益心脾，益气养血，**和络止痛**"，无"养心安神"。

---

### 5. 处方仍是"归脾汤加减"，方证针对性不足 —— ⚠️ 部分解决，需与贵方确认口径

这一条我们要如实说明，不遮掩。

**已做的**：把患者主症接入方剂召回。此前候选池只由证候/病性/病位标签生成，
**主诉与主症一个字都进不去**——检索索引里 `headache` 维度挂着 114 首方，
概念 id 与症状 id 空间 27/27 完全重合，数据齐备、通路也在，缺的只是喂进去的文本里没有"头痛"二字。
修复后头痛类方确实进入候选池（清空膏 #126、川芎茶调散 #204、散偏汤 #208）。

**但首选方仍是归脾汤加减，且十味药与修复前完全相同。** 实测得分：归脾汤 30 分，头痛类方 0.5–2 分。

**我们的判断**：这个排序**在临床上是对的**。产后气血亏虚头痛，证属心脾两虚，
归脾汤精确对证；川芎茶调散是治外感风邪头痛的，给气血亏虚产妇用反而是错的。
把头痛类方强行提到前面，等于用症状压过辨证。

**因此我们理解贵方的意见指向的是加减层**：主方对，但"归脾汤加减"四个字里的
"加减"是空的——十味药全是归脾汤原方组成，**没有一味针对本例主症头痛的引经止痛药**
（如川芎、白芷、蔓荆子）。

**待确认**：贵方所指是否为此？若是，我们将在 M04 加减层处理——
当主方不覆盖主症时，从受治理目录中选取针对该症的药味作为加减并绑定病机节点。
这是新增的一层，判据需要先定清楚（"主方不覆盖主症"如何判定、加什么药由哪份数据决定），
我们不打算仓促上线。

### 6. 方义解析冗长，并混入 L0/L1/L3 等工程标签 —— ✅ 已解决

**根因**（与此前推断不同，是新增的渲染层测试在真实归档产出上跑出来的）：
`ClinicalWarningLevel = "L0"|"L1"|"L2"|"L3"|"L4"` 是内部分级枚举，
它**有现成的中文标签表**（L0=常规信息…L3=高风险复核），却有 5 处渲染点直接印枚举值本身
——药味表每一味药后面跟一个 `L0`。

**处置**：在渲染边界建立单一净化点，并按 `^L\d+$` 整类拦截（不是黑名单这三个字符串）。
生产实测 M03/M04 正文均无泄漏。

### 7. 无汗、脉浮紧的风寒表实病例仍推荐"桂枝合剂" —— ✅ 已解决

**根因有两层，都是"数据在仓库里但从不参与判断"**：

1. `tcm-formula-discrimination-graph.json` 有 **167 条鉴别边**，其中就包括
   "桂枝汤 vs 麻黄汤：有汗/无汗、脉缓/脉紧"——但它**只喂提示词，从不做确定性守卫**；
2. 桂枝合剂说明书**法定禁忌栏原文**写着"表实无汗……者禁服"——而召回层**从不读取 `contraindication` 字段**。

**顺带发现的更深一层**：`affirmedClinicalText("无汗")` 返回 `undefined`。
中医大量**阳性**体征用否定词表达（无汗、不渴、小便不利、不得眠），
语言学否定规则把它们整条剥离，于是表实证的关键指征凭空消失。
此前仅有一个模块手写了 10 个词自保，**且不含"无汗"**，还被复制到第二个模块。

**处置**：新增 `formula-discrimination-guard`，覆盖 169 方、**双向对称**
（桂枝汤×表实拦，麻黄汤×表虚也拦），无关方零误报，6/6 用例钉死。
阴性形式阳性体征改由受治理生成器从鉴别图派生（68 词）。

**一处刻意的克制**：我们**没有**在极性层做全局改判。同一字串在症状回顾式否认
（"无发热、咳嗽、消瘦或心悸"）里是真否定，把患者的否认读成阳性体征比原缺陷更危险。
因此只在**有排除权**的守卫路径并入——守卫唯一的权力是移除候选，方向上是安全的。

### 9. M04 共 13 次：仅 2 次首轮成功、10 次修复后成功、1 次合同拒绝 —— ✅ 已解决

**根因**：合同与提示词错位。
合同 `m03NodeCoverageIssue` 要求 **M03 每一个带治法方向的病机节点**都必须有药味 `targetRef` 承接，
漏一个即驳回；而提示词只把节点列成"可选引用项"，**从不说明哪些是必须覆盖的**。
模型得自己推断强制范围，推错就走修复轮。10/13 能被修复轮救回，正说明模型做得到
——只是首轮没被告知硬要求。这是纯粹的提示词/合同错位，不是模型能力问题。

**处置**：由已签名的 M03 结论确定性生成"必覆盖节点清单"（判据与合同同源：`therapyDirection` 非空），
提示词中标注【必覆盖】并给出节点号与总数。

### 10. 无法证明"测试过的源码"就是"线上运行的镜像" —— ✅ 已解决（这条是元缺陷）

**贵方这条判断完全成立，且我们实测确认了它。**

这不是一条并列缺陷，而是元缺陷：无法证明镜像一致时，前面每一条"已修复"都是无法验证的断言。
于是出现"改了还是老样子"，而真正的分歧可能在部署链路而非源码——**我们没有任何手段区分这两种情况**。

**处置**：
- `scripts/build-source-digest.mjs`：对 **190 个决定临床行为的源码与受治理数据文件**算稳定摘要
- 构建期打进镜像（`CDSS_BUILD_COMMIT` / `CDSS_BUILD_SOURCE_DIGEST` / `CDSS_BUILD_TIMESTAMP`）
- `/api/diagnosis/health` 回显 `build` 字段
- `npm run verify:deployed-image`：部署后强制比对，**对不上就判部署失败**

首次对旧镜像运行时返回 `"reason": "image_has_no_build_provenance"`, `"remote": {}`
——**确认此前确实无法证明**。当前镜像验证结果：

## 二、我们自己发现并修复的问题（贵方未提，但会影响使用）

### 服务故障被伪装成临床结论

上游模型服务 503 期间，10 例中 9 例显示"证候依据不足"。
医生看到这句会去补录病历——**而病历没有任何问题，是服务不可用**。
已新增 `upstream_model_unavailable` 专用码与文案："这不是病历信息不足——已录入内容无需修改，请稍后重试"。

### 一个会导致空白处方页的缺陷（新增测试抓到）

上一轮引入的净化器按键名白名单豁免机器字段，把 `status:"accepted"`、`doseSource:"governed_boundary"`
等枚举清成空串，`normalizeReasoningV2` 随即整份拒收——**医生会看到一张空白处方页**。
69 套既有测试全都发现不了它，因为每个函数单独看返回值都正常。

这也是我们这轮补上**渲染层测试**的原因：此前所有测试都在断言函数返回值，
而贵方看的是浏览器里渲染出来的字，中间隔着提示词、模型、修复轮、呈现层——**这段没有覆盖**。
"函数绿 + 页面错"因此可以同时成立。

## 三、诚实边界

以下事项请贵方知悉，我们不做超出实测的承诺：

1. **第 5 条（方证针对性）只做了一半**，加减层未动，待与贵方确认口径后处理。
2. **目录内经典方 recall@8 约 35%**。曾接入 17270 条真实医案把它提到 53%，
   但该改动**破坏了寒热方向对称性**（风寒表证首选方变成银翘散，因 41 例医案支持压过方向轴），
   已门控为默认关闭。宁可召回停在 35%——召回少一个方医生会补，给错方向的方是临床错误。
3. **专科覆盖不均**：内科较好，妇科/儿科证型特征串偏薄。
4. **中医本身存在流派差异**，部分"分歧"不是错误。我们已就 14 例分歧做循证裁决：
   9 例系统确实错、3 例纯命名差异、1 例系统对、1 例两可。
5. **上游模型服务可用性不在我们控制内**，但故障现在会**如实告知**而非伪装成临床判断。
