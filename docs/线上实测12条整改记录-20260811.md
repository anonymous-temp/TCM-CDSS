# 线上实测 12 条整改记录（2026-08-11）

甲方在线上实操后一次性提了 12 条。本文按条给出**判定、根因、改法、验证状态**，
以及三条**没有完全闭环**的项和它们卡在哪。

线上版本：`tcm-cdss-20260811-online-findings-r4`（commit `bcdcbbec`）。
每次部署都过 `verify:deployed-image`（本地重算源码摘要与线上回显比对），
`strictReady: true`。确定性门禁 117 套全绿。

---

## 先说一件贯穿本轮的事：12 条里有 6 条是同一个形状

**同一个判据/口径，在两个出口各写各的**——服务端 Markdown 算对了、页面没跟上，
或者反过来。这类缺陷的共同特征是**两侧看起来都对**，只是其中一侧少了一段，
所以既不会报错，也不会被任何单元测试照到（两侧各有各的测试，各自都过）。

本轮属于这一类的：第 1、3、4、8、10 条，加上上一轮已修的西医依据分组。
每一条的修法都不是"在缺的那一侧补一段"，而是**收敛成一个导出谓词/投影，两个出口共用**——
补一段的话，下一次改动仍然只会落到一侧。

## 逐条

### 1. 「支持依据」没生效；待查依据里出现近义重复 ✅ 已闭环

**属实。** 0810 要求把笼统的「支持依据 / 待查依据」改成「有啥列啥」（症状/体征/检查/排除/指南），
当时只落到服务端 Markdown，**医生页面继续渲染旧的三组**——而甲方读的正是页面。

近义重复是第二个独立原因：`limitations`（还缺什么）与 `suggestedChecks`（下一步查什么）
取并集时只用 `new Set` 去重，而 `Set` 只认逐字节相等，于是同屏出现
「未提供血常规、CRP 等炎症指标」与「血常规、CRP 等炎症指标」。

**改法**：分组、标题与「只有一类时写『依据』」的规则收敛到 `clinical-fact-source.ts` 一处，
两个出口共用。去重改用仓库里本来就有的 `uniqueClinicalFacts`（剥标点 + 包含即折叠，
保留信息更全的一条），把它从 visible-summary 的私有函数提为共享导出——不新造第三个判官。
实测甲方那 5 条待查依据折叠为 4 条，且「未提供血常规」与「血常规、CRP、病原学、胸部影像」
这类不同条目不会被误合。

commit `40cc4d83`

### 2. 流式过程里就把还没定型的结论打出来了 ✅ 已闭环

**属实。** 模块级进度条的标题直接回显了模型中途产出的证型/方名，
而那些内容还没过结构校验与独立复核，最终结论可能与之不同。

**改法**：`MODULE_HEADLINES` 中西医诊断/病机/治法三处改为「已生成，待结构校验与独立复核」；
方剂一栏只报「已生成候选，共 N 味，待组成核验与审方」，**不报方名**。

commit `c746300a`

### 3. 「辨证未成立」却同时给出了剂量处方 ✅ 已闭环

**属实，但根因是措辞不是门禁。** 内部有三态
（`resolved` 已成立 / `bounded` 已成立但有边界 / `unresolved` 未成立），
页面把 `bounded` 一律说成「未成立」。真实状态是"已成立、但有明确边界"，
出方是允许的；写成"未成立"就变成了自相矛盾。

**改法**：`syndromeDifferentiationState` 三态显式化，`bounded` 呈现为
「已成立（有边界）」并列出边界，不再与 `unresolved` 混用同一句话。

commit `c746300a`

### 4. 指南引用要能点开看原文 ✅ 已闭环（本轮）

**属实，且是第 0 节那个形状。** 这条依据本来就带 `url`——
由 `resolveGovernedGuidelineReferences` 从本轮真检索到的条目字段回填，模型只能写一句 `appliesTo`。
服务端 Markdown 一直在印它；**医生页面拼展示串时写的是 `${citation}（${appliesTo}）`，没有第三段**。

**改法**：收敛成一个投影 `guidelineReferenceDisplay`，返回 `{ text, href? }`。
Markdown 侧仍拼成一行纯文本（输出与此前逐字相同），页面侧据 `href` 渲染
`<a target="_blank" rel="noreferrer noopener">`。两条安全边界：只有 `https` 绝对地址才做成可点链接
（相对路径、`http` 明文、`javascript:` 一律不做）；没有 url 时不出 `href` 字段、更不编一个。

测试判据刻意不看各出口拼出来的字符串，而看**源码里还有没有人自拼**
`${entry.citation}（…）`——那正是分叉的起点。

commit `bcdcbbec`，套件 `test:guideline-reference-outlets`

### 5. 石决明被解释成「祛风止痒」、牛膝被解释成「消肿止痛、排脓止痛」 ✅ 已闭环

**属实，根因在编译产物不在展示层。** 石决明的功效串与**千里光**首段逐字相同——
身份目录里两者互为别名（石决明的本草别名正是千里光），上游按别名图把菊科草药千里光的功效
整段贴到了鲍鱼壳石决明上，连 `primaryCategory` 都一并变成「清热药」。

这类污染此前完全隐形：功效串是自由文本，没有任何断言看它属不属于这味药。

**改法**：三味按药典原文受控覆盖；新套件把污染变成可枚举的——
凡「A 的整段功效串 = B 的某一段，且 A/B 在身份目录里因别名互指」的组合一律列出，
要么给药典原文覆盖、要么逐条登记为何可以共享，两者都没有就红。

线上实测：
- 石决明 → `平肝潜阳，清肝明目；平抑肝阳药；平肝息风药`
- 牛膝 → `逐瘀通经，补肝肾，强筋骨，利尿通淋，引血下行`
- 川牛膝 → `逐瘀通经，通利关节，利尿通淋`
- 千里光 → 保留自己的 `解毒消肿，清热解毒…`（没有被连坐改掉）

commit `c746300a`，套件 `test:herb-function-contamination`

### 6. 交付里出现占位句 ✅ 已闭环

**属实。** 两处：模块进度标题（见第 2 条）；以及 M04 编译器在药味 `function` 字段拿不到值时
写死「由服务端知识库生成」。后者改为 schema 允许模型提交 `function`、取不到就留空，
不再用一句占位文本冒充内容。

commit `c746300a`

### 7. 中成药审方噪声：「不形成疗程医嘱」却被逐条报「无单次剂量」 ✅ 已闭环

**属实，而且是我方设计与我方呈现打架。** 我方对中成药**有意**不下单次剂量
（编译器置空 `singleDose`/`frequency`/`route`，提交清单里干脆没有 `single_dose` 字段），
这是 fail-closed 设计；但这条判据**只写在提交侧**，回包侧没有任何副本，
于是灵犀按协议回的 `INPUT_QUALITY` 告警与真实配伍禁忌同格进风险表，
还顺着处方安全总评、随访触发条件、HIS 写回一路放大。

**改法**：收敛为导出谓词 `declaredNonDoseItemNos` + `isDeclaredNonDoseScopeIssue`，
行号直接读已构造的提交清单、不重新推导。**打标不删条目**：provider 的每条 issue 与 issueId
原样保留在数组里，`audit_result` 与 `highest_risk_level` 一字不动（本地只能上调不能下调），
仅呈现层把它移到「剂量审核范围说明」。判据两条同时成立才算：
整条 `relatedItemNos` 全落在有意不下剂量的行上 **且** 属剂量缺失类——
同一行上的相互作用、禁忌、重复用药一条不动（已实测验证）。

commit `380b05f5`

### 9. 针刺选穴质量 + 气功「常用穴位」栏里印功法名 ⚠️ 部分闭环

**气功那半已闭环。** 「八段锦、太极拳」被印在常用穴位下，字段语义错了，
而且是**被构建门禁逼出来的**：`siteFreeModalities` 硬编码只登记了食疗/意疗，
气功本无穴位却不在集合内，`sitesOrPoints` 为空就 throw，模板只能塞一句功法名过闸。
而运行时的同一判据 `tcmTreatmentProjectIsPointFree` 是从数据反推的（模板取穴全空即判无穴位），
两处方向相反。改法：功法名归到它真正该在的位置（操作边界），气功登记进 `siteFreeModalities`，
测试端删掉手抄的字面量集合、改读运行时谓词——两处不可能再分叉。

**选穴那半只改善了排序，没有完全解决。** 原状：风寒咳嗽给出承灵、孔最、肩中俞。
根因是评估分支里关键词召回是唯一穴位来源且无条件盖过模板穴位池，
召回只按「症状词命中个数」排序，于是承灵（命中 3 词）压过列缺，
孔最靠「热病无汗」这条**热病**主治在风寒例里入选。

已改：先召回更宽的候选池，再按「该适应证下的受治理模板是否也收了这个穴」稳定重排，最后取 5。
不新增任何穴位——入选仍必须是教材主治命中本例已记录症状的穴。孔最已消失、风门升到首位。

**仍未解决**：风寒咳嗽仍拿不到列缺、风池。继续排查后确认根因有两层，都不是排序能解决的：

1. **适应证标签解析走岔**：「流清涕」先命中 `upper_airway`，`respiratory` 在其后，
   于是拿不到呼吸系统模板的穴位池。调整标签优先级会影响所有病例，不宜顺手改。
2. **目录里根本没有"普通风寒咳嗽/感冒"的受治理取穴模板**：现有两条呼吸系统模板分别是
   湖南 2025 **流感**专用方案（列缺、合谷、风池、太阳、外关）与**恢复期**肺脾气虚/肺胃阴虚方案。
   把流感专用方案套到普通风寒咳嗽上属于扩大适应证，不能自行决定。

这两层都需要临床裁定，性质与刚刚终审的 13 条配穴规则相同。**建议按同样流程走**：
我出待裁定清单（普通风寒咳嗽/风热咳嗽的主穴与配穴、来源与等级），请中医师签字后落库。

### 11. 「需优先补充」把头颅 CT、经颅多普勒与「问病程」并列 ✅ 已闭环

**属实，而且是死代码。** 分级判据 `buildTieredSuggestedChecks`（先问诊查体、有指征再影像）
早就实现并测过语义，但它的**唯一调用点**在 `851e4d76`（治法词表全量对账）里被连带删掉，
此后线上渲染的一直是模型原样自由文本。

红旗病例继续豁免——在那里延后检查是有害的。

真正要钉住的是**它为什么没人发现**：展示策略这一层只在渲染点生效，调用点消失后
产物立刻回落到模型自由文本，而所有单元测试仍然全绿（函数还在，还能被直接 import 测）。
所以新判据落在「有没有人调它」上：`result-display-policy` 的每个运行时导出都必须在 `src/` 里有引用点。
实测把调用改回删除前的样子，该判据立刻红并指名 `buildTieredSuggestedChecks`。

### 12. health 接口暴露内部实现 ✅ 已闭环（改了三轮）

**属实。** 各阶段模型名与厂商、修复轮用哪个模型、`reasoning_effort`、`maxTokens`、超时毫秒、
上游探针原始报错、运行期阶段遥测，全在返回体里。它在 proxy matcher 内、要带令牌，
所以不是匿名泄露；但那枚令牌是甲方全员共用的**页面**凭证，不是运维凭证。

**改法刻意选「只删不改」**：对外视图出现的每个字段值必须与完整视图逐字相同，
不打星号、不替换占位符。因为这个接口同时是部署链路的证据来源
（`verify:deployed-image` 比 `build.commit` 与 `sourceDigest`，docker healthcheck 读 `strictReady`）——
一旦允许改写，「线上返回的值」与「镜像里的值」就不再是同一件东西，
而这正是 build 溯源整套机制要排除的情形。删除可判定，改写不可。

完整视图需**同时**满足 `?diagnostics=1` 与 `CDSS_HEALTH_DIAGNOSTICS=true`，两者缺一不可。

改了三轮，两次是线上实测抓出来的漏网，值得记下来：
- **r1**：按键名删除，漏了 `providerId`——它是 `...getPublicTextModelStatus()` 展开进来的，
  源码里字面不出现，扫源码的守卫看不见。判据改成拿真实产物构造 fixture。
- **r2**：漏了 `controlledTerminology.mode` =
  `deterministic_exact_then_prefilter_then_deepseek_closed_set_consensus`——
  **键名无害，泄露在值里**，按键名判敏感对这一类天然是瞎的。
- **r3**：线上复查，`deepseek / glm / qwen / bailian / openai / https:// / stageTelemetry /
  maxTokens / reasoningEffort / repairModel` 全部为 0 命中；
  `build.commit`、`strictReady`、`degradedReasons` 照常存活；响应头带 `Cache-Control: no-store, private`。

commits `1a629b87` / `49d8b666` / `633c59f1`，套件 `test:health-public-view`

2. **第 8 条的口径**：中医病名现在只从**医生页面**移除，HIS 方案与签名载荷仍然携带
   （0805 需求 3 要求接口里有）。如果希望接口出参里也一并去掉，那是对 0805 需求 3 的反转，
   需要甲方明确一句，我再改——两个要求目前是互相矛盾的，各由一条测试钉着，
   所以门禁一直是绿的而产品自相矛盾。
