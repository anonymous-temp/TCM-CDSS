## 2. 准备密钥（受保护运行时，勿提交）

`CDSS_API_TOKEN` 是已经交付给甲方的固定接口凭据，**升级、回滚和扩容均复用受保护环境中的既定值**；不得重新生成、打印、写入命令历史、源码或文档。新环境的首次部署也应从既有密钥管理系统注入约定值，而不是在终端回显。

下面两项是服务端内部密钥，仅在首次建立全新环境时生成；已有环境升级时同样保留原值：

```bash
echo "CASE_SNAPSHOT_ENCRYPTION_KEY=$(openssl rand -base64 32)"   # A256GCM，32 字节
echo "REASONING_CONTRACT_SIGNING_KEY=$(openssl rand -hex 32)"
```
把内部密钥写入受保护的 `.env`；不要把固定接口 Token 复制到聊天、工单或发布记录。

```dotenv

OPENAI_API_KEY=<你的 deepseek key>
CDSS_API_TOKEN=<从受保护运行时复用既定交付值>
CDSS_API_CLIENT_ID=his-integrator             # 非秘密，对接方稳定标识
CDSS_API_CUSTOMER_IDS=hospital-A,hospital-B   # 固定 Token 被授权访问的客户白名单

# 全部调用方完成租户改造后删除该变量；值非法时接口会返回 400，不会静默回落。
CDSS_DEFAULT_CUSTOMER_ID=hospital-A

# —— 模型（compose 已有安全默认，可覆盖）——

NEXT_PUBLIC_BASE_PATH=/tcm-cdss               # 子路径挂载；若独立域名根路径可留空
```

### 3.1 灵犀 transport —— 关键决策（三选一）

代码里 `getRxAuditConfig()` 只允许两类传输：**HTTPS**，或**回环 HTTP（仅 127.0.0.1 / localhost）**。对公网 IP 的明文 HTTP 会被判 `rxaudit_insecure_transport` → 审方停用 → 处方 fail-closed 到人工复核（本次已修：这种情况会锁定采纳门）。所以：

| 方案 | 配置 | 说明 |
|---|---|---|
| **A. 容器共享主机网络（推荐冒烟用）** | compose 加 `network_mode: host`；`RXAI_AUDIT_BASE_URL=http://127.0.0.1:<灵犀端口>`；`RXAI_AUDIT_ALLOW_INSECURE_HTTP=true` | 灵犀就在本机，回环最简单。注意 host 网络下端口映射失效，app 直接监听 3000。 |
| **B. 灵犀走 HTTPS** | `RXAI_AUDIT_BASE_URL=https://<灵犀域名>`；`RXAI_AUDIT_ALLOW_INSECURE_HTTP=false` | 最干净，生产首选。 |
| **C. 暂不接审方** | `RXAI_AUDIT_ENABLED=false` | 审方停用即 fail-closed：能出候选方，但**处方一律不可一键采纳、须药师人工复核**。可做开发冒烟，但严格健康检查不会放行正式发布。 |

> ⚠️ 绝不要用 `RXAI_AUDIT_BASE_URL=http://82.156.128.153`（公网明文）——会被安全传输拦掉，等同方案 C，还白白暴露风险。

### 3.2 多客户库存与快照迁移

正式接口应发送 `x-cdss-customer-id`；浏览器登录后使用服务端签名的客户 cookie。请求客户必须在 `CDSS_API_CUSTOMER_IDS` 白名单内，未知或未授权客户统一返回 `403 customer_forbidden`，不提供客户枚举信息。`CDSS_DEFAULT_CUSTOMER_ID` 只用于旧调用方过渡，且必须同时位于白名单内，不能作为长期多租户鉴权方案。严格健康状态只回报授权配置是否有效和客户数量，不回显客户标识。

旧版单文件库存迁到客户目录时执行（目标已存在会直接失败，绝不覆盖）：

```bash
npm run migrate:drug-inventory-customer -- \
  --source /app/runtime-data/drug-inventory.json \
  --root /app/runtime-data/drug-inventory \
  --customer-id hospital-A
```

命令会保留原文件，并额外创建 `/app/runtime-data/drug-inventory.json.pre-tenant-backup`；写入客户目标采用临时文件加原子重命名。部署前先记录命令输出的 `target` 和 `backup`。如需回滚，停止应用，把输出的客户 `target` 移出客户目录，确认原 `source` 仍在；若原文件被外部操作改动，再从 `backup` 复制恢复原路径，然后回滚镜像并启动。不要删除备份，直到客户库存和线上回归都验收通过。

病例快照由新版本统一写成 `tcm-cdss-encrypted-snapshot-v2` 并绑定客户。发布后的首次恢复仍兼容旧 v1：只对 v1 尝试旧认证范围，成功响应会带 `legacyEnvelope=true`，后续保存会改写为 v2；v2 跨客户校验失败时不会进入旧版回退。

## 4. 构建并启动

```bash
docker compose --env-file .env build
docker compose --env-file .env up -d
docker compose logs -f tcm-cdss        # 看启动日志，Ctrl-C 退出
docker compose ps                      # healthcheck 变 healthy 即就绪（约 30-60s）
```
> healthcheck 打的是 `/api/diagnosis/health?strict=1`（带 token），`strictReady=true` 才算健康。

## 5. TLS 反向代理（对外必须）

容器只绑 `127.0.0.1:3000`，**必须**在前面挂 HTTPS 反代（Nginx/Caddy），否则 `CDSS_SECURE_COOKIE=true` 的登录 cookie 不会下发、外部也访问不到。Caddy 最省事：

```
your-domain.com {
    handle_path /tcm-cdss/* {
        reverse_proxy 127.0.0.1:3000
    }
}
```
（`NEXT_PUBLIC_BASE_PATH=/tcm-cdss` 要和反代路径一致；用独立域名根路径则把 basePath 留空、反代到 `/`。）

## 6. 冒烟测试（部署后自查）

```bash
BP=/tcm-cdss                                   # 与 NEXT_PUBLIC_BASE_PATH 一致
TOK=<你的 CDSS_API_TOKEN>
# 1) 健康
curl -s -H "x-cdss-api-token: $TOK" "http://127.0.0.1:3000${BP}/api/diagnosis/health?strict=1"
# 2) 模型连通（会真调一次模型）
curl -s -H "x-cdss-api-token: $TOK" "http://127.0.0.1:3000${BP}/api/model-health?check=1"
# 3) 无 token 应 401（验证鉴权确实开着）
curl -s -o /dev/null -w "%{http_code}\n" "http://127.0.0.1:3000${BP}/api/diagnosis/health"
# 4) 两个授权客户应可用；未授权客户必须统一返回 403
for CUSTOMER in hospital-A hospital-B; do
  curl -s -o /dev/null -w "${CUSTOMER}: %{http_code}\n" \
    -H "x-cdss-api-token: $TOK" -H "x-cdss-customer-id: $CUSTOMER" \
    "http://127.0.0.1:3000${BP}/api/drug-inventory"
done
curl -s -o /dev/null -w "unauthorized: %{http_code}\n" \
  -H "x-cdss-api-token: $TOK" -H "x-cdss-customer-id: hospital-not-authorized" \
  "http://127.0.0.1:3000${BP}/api/drug-inventory"
```
浏览器再走一遍：登录 → 录一个基层病历 → M01→M05 跑通 → 看处方与审方提示。
> 想跑金标准回归：`BASE_URL=http://127.0.0.1:3000${BP} CDSS_API_TOKEN=$TOK npm run regress:tcm-cdss`（需服务器上有 Node 与源码）。
