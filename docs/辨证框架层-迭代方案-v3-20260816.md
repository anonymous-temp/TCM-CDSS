## 二、v2 没看到的一处机制缺陷：四条证据绑定判据从未触发

报告观察到「190 例声明 443 个病位，只有 205 条病位证据明细；129/190 声明多于证据；54 例完全没有明细」，并判断「目前更多是结论后面放了一段证据，不是每个轴分别由哪些患者事实支持」。

**观察正确，机制现已查明**：`diagnosis-stage-contract.ts` 里的证据绑定判据全部被 `resolution === "resolved"` 门控——

```ts
if (locationResolution === "resolved") {
  if (details.length === 0) return "location_resolved_without_basis";
  if (!patientFactSourceQuote(detail.basis, ...)) return "location_resolved_basis_ungrounded";
}
```

而报告实测：**190/190 例全部是 `bounded`，没有一例达到 `resolved`**。

⇒ **这四条判据（病位 ×2、病性 ×2）在生产里一次都没触发过。** 判据写得对、位置也对，但门控条件结构性地达不到，等于不存在。

全文件共五处 `resolution === "resolved"` 门控（1227 证候 / 1249 病位 / 1272 病性 / 1328 组合 / 1884 兼收 bounded）。只有 1884 那处兼收 `bounded`，是唯一会触发的。

这是本仓库反复出现的那类缺陷的又一变体：**不是判据写错，是判据被放在一个永远走不到的分支里**。

## 三、核心归因与对应任务

### A. 分数低的三层原因要分开看

**① 约 4.51 个百分点是格式惩罚，不是临床错误。** 严格召回 66.87% vs 包含召回 89.44%，161/194 例包含召回超 80%，损失来自长短句、拆句、前缀差异。若任务1改用包含口径，总分 19.71% → 24.22%。

**② 病机/证候低分的首要原因是「映射为空」，不是判错。** 病机 150/194 例未映射到任何选项（映射后全错仅 15 例）；证候 171/194 未映射（映射后全错仅 2 例）。**98 例已完整覆盖临床事实，但病机与证候同时为 0。**

这不能靠扩字符串规则刷分——病例126 生成「卫外不固、营卫不和」，金标准「腠理不固、卫阳不固、风邪乘虚入侵」，既有同义/粒度差异，也**确实遗漏了病因层**。

**③ 安全门不是低分主因。** `needs_information` 162 例均分 19.29%，`red_flag` 31 例均分 **21.85%**（更高），完整度 B 176 例 19.42% / C 18 例 22.51%。历史医案普遍缺过敏史、用药史、现代生命体征，大量进 B 级是**预期的 fail-closed**。

### B. 临床推理的真问题：候选有了，收敛错了

这是最重要的一条——**不是想不出正确证候，是选错了主证**：

| 遗漏项 | 其中已出现在鉴别诊断里 |
|---|---|
| 热证 25 例 | **21 例** |
| 阴虚 21 例 | **13 例** |
| 寒证 16 例 | **10 例** |

典型病例106：系统已列出「肝经郁热、阴虚火旺」，最终却选了证据更弱的「心脾两虚、气不摄血」。

**这正是 v2 里 T1′（分层鉴别评分）要解决的问题，现在有了硬证据。** v2 当时的依据是「11 个候选全 score=1」，现在有了临床端的印证：正确答案在列表里，但没有竞争性裁决机制把它选出来。

其余四条推理问题：

- **根本与标证失衡**：偏抓痰/瘀/风等标实，遗漏阴虚、阳虚、命门不足等根本（病例105/85/93）；并有把特异性的阴虚阳虚退化成通用「气虚血虚」的倾向。
- **寒热虚实证据权重不稳**：由一个显眼症状直接套常见证型，不综合舌苔脉病程兼症（病例228/106/196）。
- **病因、病程阶段、当前证候混在一起**（病例101：当前风痰阻窍正确，但丢掉盛夏高热的暑邪病因与演变）。
- **多系统症状整合不足**：擅长逐条解释，弱于建立统一有主次的病机（病例228 只围绕胃脘痛，闭经/白带/舌暗只放进「不确定项」）。

### C. 结构性问题：主证兼证层级根本没建立

- **157/190（82.6%）** 把多个证候/机制全部塞进 `primarySyndrome`
- **180/190（94.7%）** `secondarySyndromes` 为空

契约里 `secondarySyndromes?: string[]` **字段本来就有**（`diagnosis-types.ts:346`），但是可选、且**没有任何判据要求填**。所以模型把「心肾阳虚，水饮凌心，瘀血内停」整串塞进主证——这会继续污染治法主次、方剂匹配和医生理解。

### D. 优先级最高的其实是运维项：独立复核不可用

- `clinicalReview=accepted` 176 例，均分 20.34%
- `clinicalReview=unavailable` **18 例，均分 13.48%**
- 其中 4 例完全 `unresolved`（病例 4、35、148、250）
- 病例 4、148 **超过 180 秒，最长 209.5 秒**

报告的优先级判断我完全同意：**补失败原因码与监控 → 有限重试/跨提供方复核 → 保持超时后 fail-closed，而不是先调术语刷分。**

补充一条报告没提的：跨厂商复核路径（`PRIMARY_CLINICAL_REVIEW_PROVIDER=bailian-qwen`）**代码已实现但从未在生产启用过**，且 prod 的 `BAILIAN_QWEN_API_KEY` 是空字符串。这 18 例正是它存在的理由。

### E. 数据集本身有噪声，不能全算系统错

- 病例150 金标准解释以「根据」截断
- 病例153 原始病历 OCR 残缺，原文写「寒邪外客」，系统判「寒邪束表」医学上合理，即使选项答案是「风邪袭肺」

结果必须分四类：**明确推理错误**（106/228）、**主次或根本遗漏**（105/85/93）、**病程范围不完整**（101）、**同义或金标准噪声**（150/153）。刷分时只应针对前三类。

## 三·补　执行中查明的两处根因（比报告的观察更深一层）

### ① 复核不可用无原因码：算出来即丢弃，同一个函数第二次

`ClinicalReviewExecutionMeta.reason` **一直算着**五种失败（`not_configured` / `deadline` /
`invalid_contract` / `http_error` / `transport_error`），但 `clinicalReviewAttestation()`
只取 `status` 就返回，原因码在这一步被丢掉。

从 194 例导出数据逐条查证：18 例 `unavailable` 的 attestation 字段只有
`["status", "reviewedPayloadHash"]`——**确实没有任何原因码**。

同一个函数旁边的注释正记着 `independentFromGenerator` 曾经的同款毛病
（「一直算着这一位，却算出来即丢弃」）。**同一处、同一种丢法，第二次。**

已修：原因码 + `attemptCount` + `durationMs` 随 attestation 进契约，
映射提成单一导出谓词 `clinicalReviewUnavailableReason` 并配套件（`test:clinical-review-reason`）。

### ② `resolution` 字段已退化成常量——证据绑定判据死掉只是它的后果

实测三个 resolution 字段的分布：

| 字段 | 分布 |
|---|---|
| `primarySyndromeResolution` | bounded 190 / unresolved 4 |
| `locationDifferentiation.resolution` | bounded 190 / unresolved 4 |
| `natureDifferentiation.resolution` | bounded 190 / unresolved 4 |

**三个字段逐例完全一致，同一批 4 例 unresolved。** 这不是三个独立临床判断碰巧相同，
是一个开关带着三个字段一起动。

提示词的 JSON 示例模板（`diagnosis-prompts.ts:528/550/551`）**三个 resolution 槽位全部硬写 `"bounded"`**，
加上 820 行「基层稀疏病例通常应在诚实降置信后给出 bounded 工作判断」，模型在照抄模板。

**但要说准一点**：`resolutionReason` **不是**模板回声——它逐例不同、内容具体
（「病位『肾、肝、筋脉』仅有 1 条互相独立且可逐字回溯」「阴虚、气虚证据充分；但虚热程度…」，
最高频措辞也只重复 9/194 次）。所以模型**在认真判断边界，只是从不选 `resolved`**。

⇒ 因此 §二说的「四条证据绑定判据从未触发」是**后果**，根因是 `resolution` 取值退化。
先修后者，前者自然活过来。

**放开前先量了爆炸半径**：若把绑定判据放开到 `bounded` 并**直接驳回**，
190 例里完全无证据明细 54 例（28%）、明细少于条目 75 例（39%）——**会打掉 68%**。
这坐实了 v2「先影子记录、不立即驳回」的判断，T10′ 按影子先行执行。

**尚未回答的一问**：`resolved` 达不到，是模板锚定，还是对稀疏历史医案的正确保守？
194 例全是缺舌脉/生命体征的历史医案，从这批数据分不出来。
决定性检验是**四诊齐全的病例能否达到 `resolved`**，已用本地压测夹具跑活体验证。
（顺带修掉一个探针 bug：`regress-robustness-live.mjs` 读的是 `syndromeResolution`，
实际字段名是 `primarySyndromeResolution`，于是这一列一直是 undefined——探针把自己要观测的东西丢了。）

### ③ 本地验证环境的两个坑（记下来省下次的时间）

- **`npm run dev` 在 `</dev/null` 下会自己退出。** Next 16 的 dev 监听 stdin，
  stdin 一关就当收到 EOF **干净退出（exit 0）**。我一开始把连续 21 次重启归因为 OOM，
  **归错了**——真正被 OOM 杀掉的是 `npm run typecheck`（退出码 **137** = SIGKILL，
  它自带 `--max-old-space-size=8192`，与 dev 同跑必撞）。
  正确起法：`sleep infinity | npm run dev`，保持 stdin 打开。
- **这台 6G 机器不能并发跑 dev + 闸门 + typecheck**，必须串行。
  判别方法很简单：退出码 137 是被杀，退出码 0 是自己走的——两者归因完全不同。

## 三·补②　T2′ 落地实测（2026-08-16，线上 `tcm-cdss-20260816-review-reason-r2`）

### 结果

| 指标 | 值 |
|---|---|
| 单轴翻转最小对 | 5 组（寒热/虚实/阴虚阳虚/表里/气滞血瘀）×3 次 = 30 次线上 M03 |
| 传输失败 | 0 |
| 基础准确率 | **0.80**（12/15） |
| **BTR** | **0.167**（2/12） |
| 弃权 | 5 次 |

### 偏离方案原文一处

v2 §六写「基线病例从 L2 抽取并封存」。执行时判断这条依赖可以绕开且绕开更对：
**反事实病例的正确答案不可能来自标注**——标注集只标了原始病例的证型，翻转之后
那条病例的金标准在任何数据集里都不存在，只能推导。既然两条路都要推导，就直接用
**鉴别点定义**构造最小对，正确答案由定义给出。副作用是完全不碰 L2、零污染，
且不再被 T7′ 的数据集可获取性阻塞。基线表 `src/data/tcm-counterfactual-baseline.source.json`
仍受「不得据此改规则」约束。

### 首跑的两次仪器错误（都是仪器把自己的失败算到产品头上）

1. **判分器用完整词穷举**。系统答「肾阴亏虚，虚火内扰」——临床完全正确，
   但期望词写的是「肾阴虚」，而「肾阴亏虚」里『阴』后跟的是『亏』不是『虚』，
   子串对不上，3 次被判答错，基础准确率被从 0.80 压到 0.60。
   **这与本仓红旗词表反复犯的是同一种毛病，只是这次犯在测量仪器上**，
   而且方向是让产品显得更差，比反过来更难引起怀疑。已改概念正则。
2. **传输失败被记成产品失败**。一次 `fetch failed`（status 0，11 秒）被判成
   「模型没给出证候」。已单列 `transport_failed` 并排除出分母；
   重评路径第一版没跟着改（同一判据两处各写各的，又一次）。

### BTR 现在测到的**不是辨证**——这是本次最重要的结论

5 次弃权全部 `clinicalReview=unavailable`，但 `completeness.level=C`（四维全 1.0）：
不是完整度闸门降级，也不是复核服务挂了，而是**结构化合同修复耗尽后 finalize，
复核压根没启动**。

于是一个状态位盖住了两件性质完全相反的事：

| 实际情形 | 正确处置 |
|---|---|
| 复核服务不可用（超时/上游报错/未配置） | 有限重试、跨提供方兜底 |
| **没有东西可供复核**（生成方合同始终不合法） | 重试一百次也没用，要修的是合同校验 |

### 因此 T8′② 的结论改写

线上实测原因码分布（修复后 3 例）：**全部是 `not_attempted_no_valid_draft`**。
也就是说，对这一population，**有限重试与跨提供方复核都不起作用**——
它们解决的是「复核失败」，而这里根本没有复核可失败。

⇒ T8′② 拆成两条独立任务：
- **T8′②a**：面向 `deadline` / `http_error` / `transport_error` 的有限重试与跨提供方兜底
  （代码已就绪，仍缺 DashScope key）。适用人群需按原因码重新统计。
- **T8′②b（新，优先级更高）**：面向 `not_attempted_no_valid_draft` 的
  **合同校验失败归因**。194 例里 4 例、本次 30 例里 3 例走这条路，
  且都是完全 unresolved 的最坏情形。要查的是修复轮为什么始终produce不出合法合同。

### 另一处此前只做了一半的区分

diagnose 路由 2026-08-04 的注释记着：上游 503 期间「甲方 10 例有 9 例显示
『当前证候依据不足』，医生会误以为病历不充分而去补录」。那次把「服务故障」与
「证据不足」在**医生可见文案**上拆开了，但 `clinicalReview` attestation 层没拆——
