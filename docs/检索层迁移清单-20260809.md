# 检索层迁移清单（2026-08-09）

可复用检索层落在 `src/lib/retrieval/`：`cjk-analyzer.ts`（受控词表最长匹配 + 字符 bigram）
+ `bm25.ts`（BM25F 字段加权倒排）。本文件记录**还有哪些检索面待迁移、哪些绝对不能迁**。

## 迁移的硬边界（对抗核验实证，违反即 fail-open）

> **只改「已经过准入闸的候选池内部排序」，不改准入线、不改身份锁路径、不填任何 0 候选状态。**

把绝对阈值换成「取分数前 N」会让 fail-closed 的「查不到」状态**永不可达**——这是本项目
明令禁止的形状。零候选在多处是**设计边界**而非缺陷，其空态文案是显式禁令。

## 已迁移

| # | 位置 | 原实现 | 现状 | 实测 |
|---|---|---|---|---|
| 1 | `tcm-knowledge.ts` `searchTcmKnowledge` / `scoreHerb` | 无 IDF、无长度归一的子串计数（命中一个 token +1） | BM25F（内存惰性索引，不新增 src/data 产物） | 695/695 药材自名可检出零缺失；功效归类召回 94%；200 次查询 190ms → **6ms（32×）**；零结果查询仍为 0 |

选它作首个迁移场的理由：全仓只被 `/api/tcm-knowledge/search` 使用（医生用的只读知识库检索），
不进提示词、不进安全门、不参与方剂身份锁与剂量编译；628→695 味药的索引在内存里建，
零镜像体积代价。**精确药名命中仍原样置顶（score 100），BM25 只决定其余候选的先后；
准入判据仍是 score>0，与旧实现同语义。**

## 迁移 #2：主治词路循环反转（性能等价改造）

| 位置 | 原实现 | 现状 | 实测 |
|---|---|---|---|
| `tcm-formula-indications.ts` `indicationTermMatches` | 遍历 **112,883** 条索引词逐个 `merged.includes(term)` —— 每次检索十万次子串搜索 | 切病历的 2–4 字滑窗、查索引 | 命中集合 **0/300 不一致**；4.27ms → **0.03ms per case（128×）** |

**打分一律没动。** 这一路的权重尺度上标定着一批治理常数（准入线 2、curatedBoost 2、
`SYNDROME_PATH_WEIGHT` 3、`LOCK_ELIGIBLE_RANK_MULTIPLIER` 1.35、`coordinationFactor` ≤1.75），
换尺子会让它们全部作废。这里只换遍历方式。

等价性此前只是同文件 `:410` 的一句注释。本仓库已经因为「相信未经实测的等价性声称」踩过坑，
所以现在它有断言撑着：`scripts/test-formula-symptom-retrieval.mjs` 用 200 例真实归档
M03 产物逐例对拍两种写法的命中集合。成立的前提是索引词就是连续中文串上的 2–4 字滑窗
（`indicationTerms` 与建索引同一个函数），不可能跨标点。

## 改判为「不迁」（原清单列为待迁，实测后推翻）

| 位置 | 原判断 | 实测后的结论 |
|---|---|---|
| `tcm-knowledge.ts:751` `tokenIncluded` → `searchLabThresholds` / `searchHisTcmMappings` / `searchHisSpecConversions` | 待迁移（中高风险） | **不迁**。① 没有性能问题：三张表分别只有 **31 / 252 / 192** 行，全表扫描是免费的；② 语义不对：它们是**过滤器**（命中就进提示词、不命中就不出现），BM25 给的是「分数最高的那条」，对过滤器而言正是 fail-open 形状；③ 用 bigram 分析器替换会**扩大**匹配面，检验阈值规则或药品规格映射误配进提示词是安全相邻错误 |
| `tcm-modern-case-*` 现代医案检索（`tcm-formula-indications.ts` `modernCaseFormulaMatches`） | 待评估 | **无需迁移**。它已经在用「切病历、查索引」这个正确形态（迁移 #2 正是照它改的）；且 `CDSS_MODERN_CASE_RECALL` **默认关闭**，关闭原因是数据轴质量问题（同文件 `:398`「给错方向的方是临床错误，修复轴数据后再开」），不是检索实现问题 |

同理，`patentRisks`（7 行）与 `westernInteractions`（16 行）也没有迁移价值。

**一句话**：这批过滤器的问题不是「检索方式落后」，而是它们本来就不是检索。
把过滤器改成打分召回，是把「查不到」换成「总能给出一个」——本项目明令禁止的方向。

## 参数与方法：实测依据（别凭直觉改）

在 2915 张受治理方剂卡 + **2320 条真实医案查询**上跑（金标准方名已从查询中剔除防泄漏）：

- 子串包含基线 nDCG@10 **0.0619** → BM25F(bigram) **0.1304**（2.1×），R@10 10.8% → 22.3%
- **k1=0.9 / b=0.4 优于 1.2/0.75**（后者 nDCG 掉 9.2%）。与 Kamphuis 等 ECIR 2020
  「八个 BM25 变体之间无显著差异」一致——该调的是 k1/b 与字段权重，不是挑变体
- 字段加权（BM25F）相对扁平 BM25 +7.5%，成本只是几个常数
- **瓶颈在重排不在召回**：BM25F R@10 只有 22.3%，但同一份 top-100 已装着 **49.6%** 的正确答案
- **子问题拆分 + RRF 是净损失**（qB nDCG 0.1304 → 0.0852，−35%）：中医四诊文本是「一个意图的
  多个约束」，需要 AND 式联合打分，不是多意图 OR 式投票
- **RRF 不是「多加一路总没坏处」**：强路 + 弱路 RRF(k=60) 掉 30%。它是取共识，弱路会拉歪
- RM3 伪相关反馈是唯一稳定为正的查询扩展（+2.6~3.7%）
- 中文分词是第一决定因素：Node 自带 `Intl.Segmenter` 对中医术语几乎全失效
  （证候词覆盖 1.0%、方名 0.3%）；SQLite FTS5 unicode61/trigram 对「脾虚」0 命中

## 为什么不上向量库

除「检索量不大、BM25 够用」之外，还有一条本项目独有的治理理由：
`scripts/build-source-digest.mjs` 只摘要 `src/lib` + `src/app/api` + `src/data`。
**外部向量库里的索引内容不在 digest 覆盖范围内**，`npm run verify:deployed-image` 就再也
证明不了「线上跑的知识是哪一版」——而这条链是区分「修错了」与「没上线」的唯一手段。
构建期/内存态倒排索引则完整保留该链。
