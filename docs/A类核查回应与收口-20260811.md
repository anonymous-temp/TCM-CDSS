## 一、A1：V1 契约兼容闭环

### 问题
第三态 `governed_class_template_not_syndrome_tailored` 是在 `schemaVersion` 保持
`tcm-cdss-his-ai-scheme-v1` 的前提下加进出参的。对使用 Java enum / Kotlin sealed class /
TypeScript union / Jackson `FAIL_ON_UNKNOWN_PROPERTIES` 反序列化的集成方，这不是
"多一个可忽略的取值"，而是**解析直接抛异常**。

### 已改成
| 契约版本 | 怎么请求 | `protocolStatus` | `tailoringStatus` |
|---|---|---|---|
| **V1（默认）** | 无需任何改动 | 只回旧两态；第三态折叠为 `assessment_only_no_patient_specific_protocol` | 三态真实值 |
| **V2** | `?schemaVersion=v2`／`x-cdss-his-scheme-version: v2`／`body.hisSchemeVersion` | 真三态 | 三态真实值 |

- 折叠**单向且保守**：第三态 → "尚未形成患者级方案"。旧集成方按它处理只会更保守，
  绝不会把未按证型加减的病种模板当成个体化方案采纳；反向提升在任何版本下都不存在。
- `tailoringStatus`（`syndrome_tailored` / `class_template_only` / `assessment_only`）
  是**非破坏性新增字段**，两版都下发。想区分"病种模板未加减"与"纯现场评估"的，读它，不必升 V2。
- 版本号认不出**一律回落 V1**，不返回 `400`。
- **M04 原始载荷不折叠**，恒为规范三态：该字段在 HMAC 签名域内，按调用方折叠会让 M04→M05 验签失败。
  文档已写明，并建议直接解析 M04 的集成方按"可扩展枚举"处理或改读 `tailoringStatus`。
- 随文档发布 `docs/schema/his-ai-scheme-tcm-projects.schema.json`，两版枚举取值逐条列出。

### 线上实测（`tcm-cdss-20260811-contract-compat-r2-amd64`）
不寐·心脾两虚一例，同一份 caseState 分别请求两个版本：

```
HIS V1（默认） schemaVersion=tcm-cdss-his-ai-scheme-v1
  针刺疗法: protocolStatus=governed_patient_specific_plan  tailoringStatus=syndrome_tailored
  耳穴:     protocolStatus=assessment_only_no_patient_specific_protocol  tailoringStatus=class_template_only
HIS V2（显式） schemaVersion=tcm-cdss-his-ai-scheme-v2
  针刺疗法: protocolStatus=governed_patient_specific_plan  tailoringStatus=syndrome_tailored
  耳穴:     protocolStatus=governed_class_template_not_syndrome_tailored  tailoringStatus=class_template_only
```

第一态在 V1 下**没有被过度折叠**，只有第三态折叠——这正是单向映射要保证的。

## 二、A2：证型配穴改为逐条、逐穴分级

### 核查的判断成立，且我方的原表述确实偏乐观

> 不能对外概括为"不寐和痛经属于权威来源"。

数据核对完全一致：8 组模板、**45 条**证型加减；不寐前 4 条与痛经前 4 条同时挂学会来源与教材表，
不寐「痰热内扰/脾胃不和」、痛经「湿热蕴结」及其余 6 组只有 `SRC-TCM-ACUPUNCTURE-SYNDROME-POINT-TABLE`。
**35/45 条只有项目治理教材来源。**

### 1）来源层级已透传到穴位粒度

新增 `pointProvenance[]`，每个穴带自己的 `sourceRefs` / `authorityTier` /
`adjudicationStatus` / `conflictNote`，`role` 区分主穴、证型加穴、证型剔除穴。
等级由**受治理来源注册表确定性 join**——注册表本来就有 `authorityTier`，
只是从来没 join 到规则上；另加 `sourceAuthorityTier`（本条最高等级）。

线上实测：不寐·心脾两虚的针刺方案 `pointProvenance=6`（4 主穴 + 2 加减穴），
加减穴 脾俞/足三里 = `professional_society_standard`（T/CAAM 011-2014），主穴 = 病种模板来源。

### 2）未终审条目已降级，不再标为患者级个体化方案

新建逐条终审台账 `src/data/tcm-acupoint-syndrome-refinement-adjudications.source.json`：
**45 条中 32 条已核验、13 条待中医师终审**。

未终审时的处置是**非对称**的，方向都取保守侧：

| | 处置 | 理由 |
|---|---|---|
| 加穴 | **不应用** | 加一个没核过的穴是往外多给东西 |
| 剔除穴 | **照常应用** | 剔除是往回收（如湿热证剔关元）；跟着撤销反而更危险 |
| `protocolStatus` | 降为 `governed_class_template_not_syndrome_tailored` | |
| `protocolGap` | `syndrome_refinement_pending_adjudication` | 与"压根没有对应加减"（`syndrome_refinement_not_matched`）严格区分 |
| `adjudicationStatus` | `pending_clinician_review` | 只在**命中了**加减时才下发这一栏 |
| `deferredSyndromeRefinement` | 如实下发未采用的证型与穴位 + 分歧说明 | 隐藏它会让医生以为系统没识别出本例证型 |
| `adoptable` | 恒 `false`（原本如此） | |

台账**未登记的条目一律按未终审处理**——新录进目录、还没进复核的条目不能因为"台账没提到它"

### 3）复核顺带查出并修掉一个新缺陷

`pointProvenance` 对"既是主穴、又被写进加穴"的穴位**不去重**（咳嗽风寒证的太渊、
中风痰热腑实的曲池）：HIS 会拿到两条同名记录，一条 `base_point`、一条 `syndrome_refinement`——
一个所有证型都在扎的主穴被标成本证型特有配穴。候选穴位列表早就按这条去重了，
逐穴溯源这一路漏了，又是同判据只铺一处。已修并加断言。

另修一条语义缺陷（线上实测发现）：一条加减都没命中时也照写
`adjudicationStatus: pending_clinician_review`，会让集成方以为"有条目卡在终审里"，
而实际是本例证候在该病种下根本没有对应规则。现在只在命中时才下发这一栏。
