# B 类遗留项收口：实测、根因与结果（2026-08-11）

对象是 0810 交付后剩下的三条「实测确认未关闭」项（经方可追溯率、中医外治项目为空、未出方 9 例），
外加两条上一轮判定为「不该改」的项（大黄煎法、K04 极性）与三项工程质量欠账。

跑法：本地 standalone 生产构建（与线上同一份源码摘要），**不占用生产限流配额**。
50 例基层病例 + 4 组极性对照 + 8 条审方正控。

## 一、经方可追溯率：三条确定性根因，不是模型质量问题

甲方 0807 起把这一项列为最大遗留项。此前三轮修复（炮制变体丢方名、剥名兜底、剥离器第一档）
端到端都没有实质提升——因为真正的根因一条都没被碰到。

### ① 「这张处方是不是 X 方」有两个互不相识的判官

| | 身份判官 | 出处判官 |
|---|---|---|
| 函数 | `verifyFormulaCompilationComponent` | `resolveFormulaSources` |
| 读的目录 | 受治理编译目录（T8） | 另外三张名录目录 |
| 认不认党参代人参 | 认（有裁定文件） | 不认 |
| 认不认品种等价 | 认 | 不认 |
| 认不认炮制受控解析 | 认 | 不认 |

实测：15 个带方名的候选里 **10 个被出处判官判 ∅，而身份判官对这 10 个全部 verified**——

参苓白术散 10/10《太平惠民和剂局方》、四君子汤加减（党参）4/4、异功散加减（党参）5/5、
五子衍宗丸加减 5/5、缩泉丸加味 3/3、五磨饮子加减 4/5、六神散加减 6/6、
杏仁煎 8/8、四神散加味 4/4、调经方加味 3/3。

后果不是「少一行出处」：`enrichReasoning` 把 ∅ 当成「这不是经方」，直接把方名改写成
「本例辨证组方」、`constructionType` 降为 `self_devised`。

### ② 恢复身份的那次核验手里攥着出处，却把它丢掉

两条身份恢复路径（M03 锁定方名、按组成反查）只写 `name`/`formulaNames`/`constructionType`，
不写 `formulaSource`。于是候选顶着「四君子汤加减」，出处栏仍是 model_inference 的
「本例证候…结构化匹配」——而可见层只在证据可追溯时才打印「方剂出处」。

### ③ 恢复发生在可见正文重建**之后**

恢复只改 sentinel JSON、不碰正文。同一份响应两个答案：

- 医生页面：`## 本例辨证组方` / `**方案类型**：自拟方`
- 签名载荷与 HIS：`四君子汤加减` / `single_base`

甲方读页面。这解释了为什么内部按载荷量出来的数（41.7%）与甲方的体感长期对不上——
按页面量，改前只有 **12.8%**。

### 修法与边界

出处兜底**只在名录查不到时进场**，且完全采信身份判官的 `verified` 结论；
受控解析表只授予身份、**不授予「组成逐字一致」**（清胃散基准记「当归身」、处方写整当归
照给方名与出处，但必须挂「加减」、置信度封顶为中）。
炮制身份（炙甘草 vs 甘草）、最低保留数、身份锚点药三族一字未放宽。
新增 `test:formula-traceability` 在 **2909 个受治理基准**上钉住不变量「核验通过 ⇒ 有出处」。

## 二、中医外治项目为空：一个空字符串，全程零信号

根因不在项目选取，而在**我方自己编译出来的项目活不过我方自己的 schema**：
评估态项目的 `techniqueBoundary` 写空串（当时的理由是「评估态没有患者级参数可写」），
撞上 `TcmTreatmentRecommendationSchema` 的 `min(1)`，被逐条隔离机制整条剔除。

剔除只发生在**签名前**的 `attachClinicalReviewAttestation`，而可见正文在**归一之前**就渲染完了。
后果：医生页面印着三个诊疗项目，签名载荷、HIS 方案与结构化卡片一个都收不到，无日志、无原因码。

两处修：
1. 评估态写这一档**真实存在的**操作边界（本轮不下发患者级操作参数，由现场执业人员按规范确定）；
2. 可见正文的**投影输入**改为 schema 归一后的载荷——页面只能显示载荷里真实存在的内容。
   sentinel 本身按既有口径原样保留，签名链路不受影响。

实测：56 条编译产物 56 条过 schema；载荷 30 例 / 页面 30 例，两者一致。

`test:tcm-treatments` 增了一条**全项目全分支**属性断言：编译产物必须过自家 schema。
下一个空字段在这里就红，而不是又上线一轮。

## 三、未出方 9 例：7 例是报表把受控降级当成了协议破损

M04 有**四种**合法出参形态，本套件此前只认两种：

| 形态 | 此前 | 现在 |
|---|---|---|
| 剂量级候选 | 认 | 认 |
| 非剂量安全页 | 认 | 认 |
| 确定性参考页（模型正文不可回收 → 渲染受治理基准组成 + 药典区间） | **判协议破损、整例中止** | 认，单独计数 |
| M03 未稳时的安全有限页 | **判协议破损、整例中止** | 认，单独计数 |

9 例全部落在后两种：7 例确定性参考页、2 例 `chain_structure_invalid`。中止意味着 M05
及之后一项都不再跑，报表上与真正的失败不可区分。

新增判据 `evaluateDeterministicReference` 比原先**更严**：每一处剂量数字必须紧跟「药典区间」，
否则说明这一页混进了本例建议量——那正是这条降级路径最需要防的事。
降级仍记失败，但只记一次，由新的「剂量级候选达成率」单独计量（本轮 7 例）。

改后本轮 R01、D01 等原「未出方」病例已能正常给出剂量级候选。

## 四、上一轮判「不该改」的两条

### 大黄煎法 —— 改了，用 oneOf

上一轮以「用途相关、一刀切会临床出错」为由不补。这个理由对**单值**成立，对 oneOf 不成立。
审方原话「大黄 应先煎、后下或冲服」，本地只有否定式约束「禁止久煎」，出方时一个字都标不出来。
改用受治理 oneOf（后下 / 先煎 / 冲服，由医师按用药目的择一），既清掉「未标注」又不替医师做选择；
「禁止久煎」一字未动。M05「可预防问题」本轮 **3 → 0**。

### K04 寒热极性 —— 是本套件的误报，不是产品缺陷

上一轮报作「确定性极性门禁正确拦截」，这个说法不准确：它根本不是产品门禁，是回归套件的判据。
白疕案证候=血热证、治法=清热凉血，完全正确，仅因病机里写了加重诱因
「冬季寒邪外束，热郁更甚」就命中 `therapy_cold_heat_polarity_conflict`——把**诱因**当成了证候极性。

按惯例修到整类：证候名里的极性优先于病机行文；证候名不表态而两种极性并存时属寒热错杂，
机械判据不裁定。K04 原文与一例寒热错杂各留一条具名反例，真冲突用例（寒凝血瘀证 + 清热凉血）不变。

## 五、工程质量三项

- `formula.modifications[].triggerSource` 进 HIS 出参（三项齐全才写回——残缺的溯源比没有溯源更坏）；
- `terminologyMappings` 进 HIS 出参（原文 / 候选 ID / 确认状态，不下发模型名与缓存命中这类内部痕迹）；
- `deferredFormulaSelection`（被剥离的方名）上医生页面，措辞与服务端摘要同源；
- 对外接口文档 7 处 curl 示例内联了生产环境真实令牌，改为 `$TOKEN` 占位并补轮换提示。
  **历史版本副本仍含明文**，是否轮换由甲方按其安全规范决定。

## 七、未关闭项（如实登记）

- **经方可追溯率 38.5% 仍不是终点。** 24 例自拟中，M03 未锁方名且组成反查也认不出的占多数——
  这一段要靠 M03 的方名锁定率与 M04 的组成贴合度，属模型与治理目录覆盖，不是确定性缺陷。
- **二陈汤（法半夏 vs 姜半夏）等炮制品种等价**：身份判官按目录记的炮制名严格判，
  按组成反查却认同一味。要放开必须走中医师裁定（政策文件 `tcm-herb-identity-substitution-policy.source.json`
  的既有形态），本轮不自行裁定。
- **药典基线仍是 2020 版**、复核未跨模型、限流单实例内存态、无 Git remote 与 CI 供应链溯源——
  0727 起登记的历史 P1/P2，本轮未动。
