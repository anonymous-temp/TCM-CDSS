## 二、总根因：三条结构性缺陷

这不是几十个独立 bug，是三个架构倾向的展开。**先改这三条，下面一半条目会自动消失。**

### 根因 A — M03 全部校验都是「防编造」型，没有一条「防复述」

`m03SemanticIssue`(`diagnosis-stage-contract.ts:1098-1223`) 的每一条门禁要么是结构门禁（字段存在/长度/去重/术语表内），要么是接地门禁（内容必须能在病历里找到出处）。**没有任何一条要求"从事实到结论存在推演步骤"。**

后果是致命的：**"逐句复述现病史 + 每句都能锚定病历原文" 恰恰是所有接地校验的全局最优解——越复述越容易通过。** 甲方「诊断依据仅罗列病史」「病机罗列现病史」「鉴别只列病史」全部由此而来。

配套证据：
- `hasPathogenesisAnchor`/`hasTherapyAnchor`(`:275`/`:285`) 是**死门禁**——唯一调用者 `m03ChainNodeDiagnostics` 只在已被拒绝时用于拼日志；且判据本身把「任意 4 字症状」当成病机。
- `narrativeMostlyCopies`(`:1061`) **从不比对病历原文**，只比对模型自己填的 supportingFacts/basis。模型把 supportingFacts 写成摘要词、rationale 写成病历长句，复制比就落在 0.85 阈值之下。
- 「有临床推理」的判据是单个连接词，`CLINICAL_REASONING_CONNECTOR`(`:79`) 里 `但`/`而`/`故` 这类裸并列词即可满足。
- `syndromeEvidence` 完全豁免字面接地（`:469` 的 `if (factIndex === 1) continue;`），可任意编造。
- 字段内只要有一个已知症状词，同字段其余编造内容不再检查（`:470`），`patientFactSourceQuote` 还会为其发放病历"出处"。

**修法**：新增一条与接地正交的「推演存在性」门禁——
1. 把 `hasPathogenesisAnchor(item.pathogenesis) && hasTherapyAnchor(item.therapyDirection)` 加进 `hasCompleteChainItem`(`:1100-1105`)，删掉 `:278-281`/`:288-291` 的 `length>=4` 兜底；
2. `narrativeMostlyCopies` 的比较源追加 `clinicalContext` 本身；
3. 连接词表删掉 `但`/`而`/`故`，并额外要求 rationale 出现至少一个不在 patientFact 集合中的诊断学概念（病程阈值/鉴别要点/机制词）；
4. 取消 `:469`/`:470` 的无条件 continue，改为逐子句接地。

> **这条直接决定：往 prompt 里再写多少规则都没用。** `diagnosis-prompts.ts:358/361` 已经把「不得复制主诉」「治则 vs 治法」写得非常清楚了，但没有任何确定性校验在执法。

### 根因 B — 质量问题交给「事后过滤」而不是「生成时保证」

模型写了套话就擦、字段不合格就隐藏、解析失败就套模板。医生看到的结果：**该有的没了、不该有的擦不干净、擦不掉的用模板顶。**

- 免责话术有 4 层擦除（`diagnosis-client-guards.ts:2`、`result-display-policy.ts:144`、`diagnosis-api.ts:1002`、`clinical-output-authority.ts`），**但 `diagnosis-visible-summary.ts:231` 自己在生成**「当前证候为有限资料下的工作判断」。一边擦一边写。
- 「把握度」擦除是**整行删除**(`diagnosis-visible-summary.ts:1590`)，模型把把握度写在句尾时，整行临床事实一起消失。
- 工程术语词典按**裸子串**替换(`clinical-output-authority.ts:50`)，词表含「权重」「schema」「API」「JSON」，会把临床文本改坏并产出半中半码的乱码。
- 展示层把病机链的 `patientFact` 与 `syndromeEvidence` **一并覆写成同一条病历原句**并写回 sentinel JSON(`diagnosis-visible-summary.ts:831/861`)——所以医生看到的病机链两列必然都是病史原文。
- 病历字段缺任一项就把模型全部建议检查替换成写死的神经科三句话(`result-display-policy.ts:156`)。

**修法**：擦除层只做兜底、不做主力；每一处"擦"都要回溯到生成源删掉诱因。整行删除一律改为短语级删除并补单测。

### 根因 C — 同一份事实有多个真源，靠启发式拼接

- **随访时间轴有三套**：服务端确定性(`diagnosis-safety.ts:3530`)、模型生成的表格模板(`diagnosis-prompts.ts:856`)、前端硬编码 `fallbackItems`(`DiagnosisClient.tsx:4061`)。前端 `:4092` 按启发式三选一，`parseFollowupTimelineItems` 再按列名盲映射。
- **中成药概念表有两张且不一致**：检索用 `MEDICINE_CONCEPTS`(28条含同义词)，出口校验用 `MEDICINE_PROBLEM_CONCEPTS`(21条无同义词)，再叠加 limit 6 vs 10 的作用域不一致 → fail-closed 校验把自己产出的候选删掉。
- **`clinical-output-contract-registry.json` 的 sectionOrder 是死数据**，没有任何渲染路径消费它，「展示哪些段」写死在两个 builder 与 JSX 里。

## 三、用户实测 6 条

### U1 频次与审方 — `partial`，但根源比描述的更深
守卫**存在**(`rxaudit.ts:549` → `regimen_incomplete` 不送审)，但它守的是「M04 JSON 里有没有 regimen 字段」，而 **regimen 本身是服务端在 `diagnosis-visible-summary.ts:493-506` 无条件合成的常量**，所以正常链路上守卫**不可达**，100% 送审。送出去的是 `rxaudit.ts:533` 硬编码的 `frequency_code:"QD"` + `每日N剂`。

更根本的是**建模缺陷**：中药医嘱是三维的——剂数/疗程、每日剂数(剂/日)、分服次数(服/日，决定单次给药量)。系统只建模了第一维，第二维写死 1，第三维退化成自由文本(`"早晚分服"`)。`diagnosis-types.ts:340-354` 的 `decoction` **没有任何 frequency 字段**。

**修**：`decoction` 增两个受控数值字段 `dosesPerDay` + `administrationTimesPerDay`，贯穿契约/展示/审方三处共用同一份事实；删除 `rxaudit.ts:533-535` 的字面量注入，映射不成立时走 `regimen_incomplete` 不送审。**在字段真正可变之前，宁可让 provider 报 INPUT_QUALITY，也不发编造值。**

### U2 中成药/西药推不出来 — `not_fixed`
链路是「确定性检索定边界 → 模型只选 ID → 服务端二次校验」，结构是对的，但：
- **索引里根本没有证型维度**。`MEDICINE_CONCEPTS`(`local-patent-medicine-candidates.ts:42-71`) 28 条全是症状/病名正则，没有一条能命中「心脾两虚证/肝火扰心」；虽然 `:92-93` 把 `primarySyndrome` 纳入了事实源，但没有概念能匹配它。
- **排序按"命中概念个数"**，正确药被挤出 limit。
- **短路点**：facts 为空直接返回 `[]`(`:105`)；`score>=2` 门槛使单一「乏力」病例必然为空(`:120`)；出口校验用另一张表做子串比对，把自己的候选删掉。
- **西药**：设计上是 `discussion_only`，依赖 EviMed 说明书检索；未接入时**静默为空，无任何说明**。

**修**：构建期为每条说明书抽「功效术语 + 主治证型」入索引（说明书适应证里已有 477 条显式含"证"）；打分改为「证型/治法对齐分(主) + 症状覆盖分(次) + 剂型适配」；检索/绑定校验/出口过滤共用同一张概念表与同一个 match 函数；西药要么纳入 `health?strict=1` 必需项并明写"未接入"，要么把栏目改名「中成药候选」。

### U4 病机 / 治则治法 — 全部 `partial` 或 `not_fixed`
- **总体病机复述主诉**：`overallPathogenesis` 的 zod 定义是 `z.string().max(2000)`，**无 min、无内容约束**(`diagnosis-types.ts:619`)。「非复述」判据拿模型自己填的 basis 做自比对，不拿病历主诉原文比。**修**：比对源改为 clinicalContext 主诉/现病史 + 正向要求命中病机锚点。
- **治则千篇一律**：三层叠加——① `clinical-terminology.ts:141-149` 用跨病例常量「因人制宜」兜底，**等于给治则设了默认值**，这是最直接成因；② T4 治则白名单被 relationPolicy 过滤到只剩 36 条；③ prompt(`:361`) 和复核提示举的例子「标本缓急」**根本不在词表内**。**修**：归一层命中失败时不得写常量，保留模型原文交给修复循环；把 36 条可接受治则枚举回注给模型。
- **「标本兼顾」与主次治法并列矛盾**：治理词表已把「标本兼治」标为 `requires_root_and_manifestation_targets`，**但运行时无任何代码消费该策略**。`subTherapies[].priority` 的 zod 是 `.catch("次要")`，缺省即"次要"，且不要求至少一条"主要"。
- **西医化提示（缺乏影像学/实验室）**：prompt 给 `resolutionReason` 留了"资料边界"自由槽而未加同款禁令；`NON_TCM_EVIDENCE_GAP` 拦截作用在**不展示的字段**上，拦的不是看得见的那一栏。

### U5 病位缺失 — `not_fixed`，两个独立原因
1. **展示层**：`DiagnosisClient.tsx:4429` 用 `items.length > 0` 作为整块渲染开关，把「明确判定为未定」和「系统没做这件事」渲染成同一结果（都不显示），且从不渲染 `resolution`/`resolutionReason`。
2. **编排层**：`diagnosis-api.ts:2052` 的 `applyM03ProjectionOnlyReviewRepair` 从复核器**自由文本**里正则抽 code，`location_unsupported` 的正则是 `/病位[^。；]{0,24}(?:无|缺乏|不足|超出|不能|不得)/` —— 复核意见写「**病位不得留空**」会被这条正则命中，于是**服务端主动清空了正确的病位病性分类**。

**修**：渲染开关改为「有无结论状态」；复核合同改为返回结构化 `projectionRepair` 字段，不从 prose 反推动作（退一步至少加负向前瞻排除"不得留空/需同步/必须写入"）。

### U6 随访卡片 — `partial`/`not_fixed`
- **字段错位**：`FollowupTimeline` 四个槽位无语义契约，靠 `A || B || 常量` 兜底链"能取到什么填什么"。你看到的「无效或加重 → 触发处置：本次主诉及伴随症状变化」就是兜底链取到了不同语义的内容。
- **分号硬拼**：`DiagnosisClient.tsx:4077` `[reviewFocus, efficacy].join("；")`，reviewFocus 自带句号 → 「…不良反应。；主要症状较首诊改善…」。服务端同款在 `diagnosis-safety.ts:3540`。
- **套话率**：正常路径 28 个可见单元中，个性化入口**只有 monitoring 三元组一个**，且没有"变量缺失就不写该行"的机制——缺变量就用通用句兜底，套话必然出现。
- **根因**：M05 是纯搬运，把 M04 的 monitoring 三元组按位置贴进四列表格；而 M04 侧对这三个字段**既无提示词层语义定义，也无契约层语义校验**（只有长度和非空）；展示层再叠一层跨字段兜底。三层都不为"这一格该放什么"负责。

**修**：三层同时收口——① 契约层给 monitoring 加语义断言（metric 不得含条件/祈使词，trigger 必须含条件或处置动作，三字段互不重复，metric 必须锚定本例已记录事实）；② M05 改「有据才写、按来源分列」，删通用兜底句；③ M05 直接产出结构化 `timelineItems: {time, action, indicators[], triggers[]}` 随 NDJSON 下发，前端只渲染不反解，indicators/triggers 全链路保持 `string[]`。
