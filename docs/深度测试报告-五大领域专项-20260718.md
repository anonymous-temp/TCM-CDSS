## 1. 测试方法

1. **静态分析**：通读 `diagnosis-prompts.ts`（638 行）、`diagnosis-safety.ts`（2855 行）、`m04-proposal-compiler.ts`、`text-model.ts`、`reasoning-contract-signature.ts`、`evidence-source-validation.ts`、`DiagnosisClient.tsx` 关键段。
2. **端到端 HTTP 脚手架**（`deeptest/harness.mjs`）：构造 6 个虚构病例（A 不寐/心脾两虚、B 高血压头晕、C COPD 寒饮伏肺、D 肝郁脾虚湿热、E 妊娠恶阻、F 黑便消化道出血），逐一跑 `diagnose→prescribe→assess→post-prescription-risk→question`，解析 NDJSON，落盘 `deeptest/out/<case>/`。
3. **浏览器 UI 驱动**（Playwright）：填表 → 执行推理 → 截图 + accessibility snapshot，核对真实渲染。
4. **舌诊视觉测试**（`deeptest/tongue.mjs`）：下载真实舌照 → base64 → `collect`（GLM vision）。
5. **引用核验**：对模型给出的指南/文献标题联网检索，判断真伪。

## 2. 五大重点领域深度评审

### 2.1 证据依据（用户首要关切）

#### F3 🔴 西医诊断"依据"=病历复述（已实证，比预期更严重）

用户反馈"西医诊断下面的依据就是把病历复述了一遍"。实测确认，且**比纯复述更糟**——是带噪声的事实堆砌。

**根因（prompt 层）**：`diagnosis-prompts.ts`
- 流式草稿 L400：`**患者依据**：[仅列已提供事实]`
- 结构化模板 L166：`"supportingFacts":["病历中已提供的支持事实"]`

两处都要求"列事实"，而非"诊断下达的主要支撑/异常分析"。设计意图是**溯源防伪造**（每个结论可回溯到逐字事实，好事），但副作用是"依据"读起来就是病历复述。**对照**：同一份 prompt 的病机/证候字段（L410 `患者事实→证候依据→病机`、L137 `患者事实→归属理由`）是要求**推理链**的。所以系统能产出分析性文字，唯独西医诊断"依据"字段被设计成事实清单。

**实证（case B 高血压）`supportingFacts`**：
```
"反复头晕、头胀3年，加重伴视物模糊1周",
"持续性，午后加重",
"颞侧明显",
"入睡困难",
"88次/分",                 ← 心率为何是高血压诊断依据？
"偶发",                     ← 孤立片段（心悸偶发被截断）
"舌暗红，苔薄黄",           ← 中医舌象混入西医诊断依据
"高血压病史3年"
```
没有"哪个事实是关键诊断锚点""哪些异常""为什么是这个诊断而非别的"。

**对照（同一系统内不一致）**：case F（消化道出血）的红旗"依据"是**分析性**的——`黑便提示上消化道出血>50ml；静息心率102、血压98/60，休克指数≈1.04（>1.0 提示有效循环血量显著减少）`。说明模型**能**产出分析性依据，但在西医诊断 supportingFacts 字段不稳定地退化成事实堆砌。

**建议**：把 `supportingFacts` 语义从"事实清单"改为"诊断支撑要点"——要求针对**异常发现 + 诊断标准命中项 + 主要鉴别排除理由**做提炼，而非复述；或在呈现层把"已记录事实"与"诊断依据"分成两个区块。

#### F4 🔴 西医诊断分级错误（准确性）
case B：血压 168/102mmHg 判为"高血压病**3 级**（很高危组）控制不良"。按《中国高血压防治指南》，2 级=160-179/100-109，3 级=≥180/110。**168/102 是 2 级，不是 3 级**。"很高危"因合并糖尿病可成立，但分级错误是事实性临床错误。一个"依据→标准映射"的显式推理步骤本可避免。证据：`deeptest/out/B/01-diagnose.md`。

#### F5 🟠 结构化字段含 JSON 对象 dump（系统性）
`patientFact`/`syndromeEvidence`/`primarySyndromeBasis` 多处出现 stringified 的症状对象，而非逐字短句：
- case A `pathogenesis.chain` P2/P3/P4：`patientFact = "{\"失眠\":\"入睡需1-2小时...\",\"乏力\":\"...\",\"食欲不振\":\"...\"}"`
- case C `primarySyndromeBasis[0] = "{\"咳嗽\":\"阵咳\",\"咳痰\":\"白痰量多、清稀\",...}"`

违反 prompt 明文规则（L132/L140/L176：`patientFact 必须逐字摘录一个短句，不得改写或拼接`）。且 P2/P3/P4 共享几乎相同的超长 dump，使"逐节点锚定单一事实"的设计落空。

#### F6 🟠 内部工程短语泄露进临床字段
case A 渲染后的"支持依据"中出现：`饭量减少，用法与疗程待候选方药阶段核验`——一个用药说明短语被拼进了患者事实。这是模型把内部状态/工程语料当成了临床事实。证据：`deeptest/out/A/01-diagnose.md`。

#### F10 🟠 文本与结构化不一致
case B：流式文本 `高血压病3级（很高危组）控制不良`，结构化 `primary.name` 仅 `高血压`；且该诊断**同时**出现在 `differentials` 里（主诊断=鉴别诊断，自相矛盾）。

#### F13 🟡 引用来源透明度（非伪造，已核验）
对模型给出的两处指南引用联网核验：
- `[EVID-GUIDE-003] VA/DoD clinical practice guideline for the management of chronic insomnia disorder and OSA. 2019` → **真实**（VA/DoD 2019 失眠/OSA 指南）。
- `Evaluation and management of insomnia in the clinical practice in Italy: a 2023 update from the Insomnia Expert Consensus Group` → **真实**（Palagini et al., *Journal of Neurology* 2024, PMID 38063870）。

即反伪造层（`evidence-source-validation.ts` fail-closed，把无来源降级为 `insufficient`）**有效**，未见编造 DOI/指南。**残留问题**：医生只见标题，无链接/DOI/相关性说明；将意大利共识用于中国患者存在外推相关性疑问。建议呈现层附可点击来源 + 标注人群/适用范围。

### 2.2 西医诊断与中医证候推理

**中医证候推理（正向）**：case A 核心**病机推理链**为真正的临床推理，非复述：
> 脾虚气血生化乏源 → 血不养心 → 心神失养 → 失眠多梦；脾气不足 → 乏力/纳差/脘胀；血虚不荣 → 面色萎黄/健忘。总属因虚致神不安。

病名（不寐）、证型（心脾气血两虚证）、resolution（bounded，诚实降置信）、鉴别（肝郁化火/痰热内扰，并正确以"无急躁易怒/口苦/苔黄腻"排除）均准确。case C（肺胀/外寒内饮，肺脾阳虚）、case E（恶阻/脾胃虚弱）、case F（血证/气血两虚）病名证型均规范。**这是系统的强项。**

**西医诊断**：除 F4 分级错误外，诊断倾向本身合理（慢性失眠障碍、COPD 急性加重、妊娠期 NVP、急性上消化道出血）。但 prompt L134-136 的"必须逐项核对诊断标准、不得因可能性像而跳过标准"在 case B 未被遵守（跳过了分级标准核对）。

### 2.3 处方推理

**组方临床合理性（正向）**：case C（外寒内饮）候选方为 干姜+法半夏（温化寒饮，君）+ 紫菀/款冬花/苦杏仁（止咳平喘，臣）+ 陈皮/厚朴/五味子/紫苏叶（理气化痰/解表敛肺，佐）+ 桔梗（引经，使）。契合病机；**主动避开附子**（不触十八反）；法半夏为规范炮制品；苦杏仁 `isToxic:true` 正确标记；SpO₂<90%→急诊 触发得当。

**缺陷**：
- **F7 方义分析乱码**：`deeptest/out/C/02-prescribe.md` 方义段：`君药以干姜、法半夏为组，针对外感寒邪，或阳气亏虚，阴寒内盛，本方案，痼疾新发...` —— "本方案"token 错位插入多处（`围绕"本方案，降气平喘"展开`），段落近不可读。是确定性方义编译器（`m04-proposal-compiler.ts` / visible-summary 方义生成）的缺陷。
- **F9 加减方空转**（见 2.4）。
- **F14 独立处方复核 unavailable**：`clinicalReview.status:"unavailable"`，候选仅过结构校验，缺第二意见。

### 2.4 处方加减方

**F9 🟠 系统性空转**：`formula.modifications` 在 case C（COPD 寒饮伏肺+脾肾阳虚，**明显**应随症加减：喘甚加葶苈子/苏子、痰多加白芥子/莱菔子、寒重加细辛）与 case D（肝郁+脾虚+湿热多兼夹）**均为 `[]`**。

**结构原因**：`m04-proposal-compiler.ts` 的 `modifications` 被设计为"**复诊时**的条件性 IF-THEN（0-4 条）"，`trigger` 必须是"复诊时出现的明确症状或证候变化"，且仅可加 KB 已收载药、不得填剂量。即**当前处方本身没有随症加减**，加减被推迟到复诊且约束极严，模型倾向于直接输出空数组。对一个标榜"候选方药"的系统，**初始方即缺随症加减**是明显的实用性短板。

### 2.5 四诊推理

**F11 🟠 闻诊无专门模块**：UI"问诊补充"占位符明示 `闻诊模块本轮暂不启用`；`CaseState` 仅有 `tongue/pulse/faceNote/symptoms`，无闻诊（听声/嗅气）字段。望（舌/面）、问（症状/M02）、切（脉）有结构化入口，**闻诊缺位**，只能散落进 symptoms/faceNote，无法进入结构化推理。

**F12 🟠 舌诊视觉即时失败**：`deeptest/tongue.mjs` 用真实舌照（Wikimedia 鹅口疮白苔舌，269KB）调 `collect`（GLM vision），**158ms 即返回 `模型服务暂时不可用`**，重试一致失败。`GLM_VISION_ENABLED=true`、`GLM_API_KEY` 已配置、`GLM_VISION_MODEL=glm-5v-turbo`，但后端即时报错。**舌照上传功能在本环境对医生不可用**。需排查 GLM 模型名可用性/配额/Key 有效性（158ms 的快速失败更像是鉴权或模型名被拒，而非超时）。

## 3. 算法架构与流程

### F1 🔴 结构化输出可靠性间歇性失败（最严重）
- **case A（最简单的心脾两虚）M04 产出空处方**：`deeptest/out/A/02-prescribe.md` = `CDSS_NON_DOSE_PRESCRIPTION` + `[TRUNCATED]`，正文"模型处方输出被截断或结构化结果未闭合，服务端已阻断半截处方文本"。
- **case D 的 M03 结构化结果为 NULL**（sentinel 未闭合/解析失败），导致 M04 因无有效签名直接 409。

即模型有时不在结构化时限内闭合 `<!-- DIAGNOSIS_JSON_START/END -->` sentinel，且结构化重试也未能修复。**M03/M04 的结构化契约生成不稳定**——对一个临床决策支持系统，"有时给不出处方/给不出结构化辨证"是不可接受的可靠性级别。建议：统计线上 sentinel 闭合失败率；加强结构化修复策略；对常见简单证型预置稳定模板兜底。

### F2 🔴 M02 追问契约校验 flaky，静默降级
- **harness case A**：模型产出优质问句（"怕冷/怕热"区分阳虚阴虚；"月经是否停止"判断围绝经期→补肾 vs 调肝），被 server 以 `模型结构化追问计划不可用` 替换为通用 fallback"症状加重/缓解/波动"（`<<<CDSS_STREAM_FINAL>>>` 之后）。
- **真实 UI 复现**：高血压（168/102）病例，UI 显示的也是 fallback 通用问句，而非安全分诊问句（高血压急症症状/当日降压药服用）。
- **不一致性**：harness 中 case B 的同等质量问句却被保留。说明 M02 结构化计划校验**时好时坏**，且降级时**不提示医生**"本轮追问已降级"。核心追问功能实质退化。

### F8 🟠 UI 正则提取 Markdown 渲染（脆弱架构）
`DiagnosisClient.tsx` L470-496 大量 `.replace()`、L2245-2296 `extractSectionLoose/extractField` 从模型自由文本里**正则抽取**"西医诊断/证据依据/辨证依据"。项目已有完整的 V2 结构化契约（`schemaVersion: tcm-cdss-reasoning-v2`），呈现层却重新解析文本。后果：F6（工程短语泄露）、F10（文本/结构不一致）、以及整体呈现随模型措辞波动。这是 memory 已标记的 `STREAM_REPLACE_MARKER` 根因。建议：呈现层直接消费结构化契约，文本仅作辅助展示。

### F14 🟡 交叉复核与审方降级
`strictReady:false`（`tcm_treatment_capabilities_not_configured`）；M04 `clinicalReview.status:"unavailable"`；`灵犀`审方 Key 未配置（`.env.local` 无 `RXAUDIT/LINGXI`），`post-prescription-risk` 返回 `lingxi_unavailable`。系统按 fail-closed 退化为"医生/药师人工复核"（安全），但 M05 风险随访实质失去审方输入。属**部署配置缺口**，非代码缺陷，但需在上线前补齐。

### F16 🟡 自动化测试覆盖缺口
`regress:tcm-cdss.mjs`（金标）对 M04 的断言全是 `routeSource.includes(...)` 形式的**源码静态检查**（L242/284/391），**不发起真实 HTTP M04 请求、不验证签名链、不验证处方实际产出**。因此 F1（M04 间歇失败）这类问题不会被金标捕获。建议增加 live M04 E2E 用例（含稳定 caseId 的 M03→M04 签名链）。

## 4. 产品交互 / 页面设计

**正向**：表单分区清晰（基本信息 / 一诉五史 / 生命体征 / 四诊），流派偏好 13 选项，右侧报告 5 阶段 tab（病历采集/重点追问/辨病辨证/候选方药/审方随访），主诉为唯一必填，"执行辅助推理"按钮在主诉空时禁用并提示。整体专业度高于一般原型。

**问题**：
- **响应慢**：M03 单阶段 70-95s（含独立复核/结构化重试），M04 再 80-90s。门诊场景下医生等待"辨病辨证+候选方药"全流程可能 >3 分钟，体感偏慢。
- **beforeunload 反复弹窗**：测试中页面多次触发 beforeunload（疑 dev 热重载），干扰连续操作；生产构建需确认是否复现。
- **降级无提示**：M02 追问被替换为 fallback、M04 复核 unavailable、舌诊失败，均以普通文案呈现，医生难以感知"本轮结果已降级、可信度降低"。
- **console 持续 1 error**：未细查，建议排查。

## 5. 安全门控专项（正向结论）
