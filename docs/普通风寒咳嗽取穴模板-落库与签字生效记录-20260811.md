# 普通咳嗽·风寒袭肺证 取穴模板 —— 落库内容与签字生效记录（2026-08-11）

**当前状态：`approved` —— 中医师 2026-08-11 已签字终审，模板已启用。**

命中本模板的病例现在返回**患者级方案**（`protocolStatus = governed_patient_specific_plan`、
`tailoringStatus = syndrome_tailored`），不再是评估态，也不再下发 `deferredGovernedTemplate`。
理由见 §4：闸门的准入条件本身就是「病种事实 + 已签名证型 + 已终审」三者同时成立，
而这正是本仓库对「个体化方案」的定义。

---

## 一、为什么要新建这条模板

甲方线上实测：风寒咳嗽给出**承灵、孔最、肩中俞**，缺列缺、风池。

第一轮只调整了评估分支的排序（孔最消失、风门升首位），列缺、风池仍拿不到。继续排查后确认
根因有两层，都不是排序能解决的：

1. **适应证标签解析走岔**：「流清涕」先命中 `upper_airway`，`respiratory` 排在其后，
   于是够不到呼吸类模板的穴位池。
2. **目录里根本没有「普通风寒咳嗽」模板**：针刺呼吸类只有两条——
   湖南省 2025 **流感**专项方案（列缺、合谷、风池、太阳、外关）与**感染恢复期**方案。
   把流感专项套到普通风寒咳嗽上属于**扩大适应证**，不能由我方自行决定。

因此按 13 条证型配穴的同一流程出裁定稿送中医师。

## 二、中医师裁定（含对我方设想的一处修正）

> 「列缺应固定进入普通咳嗽主穴，风池不应对所有风寒咳嗽强制加入，
>   而应作为鼻窍、头项症状明显时的**条件加穴**。」

理由：支持风池的北京市卫健委内容属**政府健康科普**，撑得起「可选用」，
撑不起「所有普通风寒咳嗽的固定主穴」。

| 项目 | 裁定内容 | 落库状态 |

## 三、技术落库（按裁定的五条要求）

1. **不动全局 `upper_airway`/`respiratory` 优先级**——那会影响所有病例。
   改为新增前置闸门 `preciseSyndromeGate`，只对声明了它的模板生效。
2. **两把钥匙同时对上**：`requireCurrentFactAny`（**当前**咳嗽事实）
   + `requireSignedSyndromeAny`（**已签名**风寒袭肺/风寒束肺）。
   「当前事实」取 `treatmentCurrentFacts`（主诉/现病史/四诊，已阳性化，**不含既往史**），
   因此「否认咳嗽」与「仅有既往咳嗽」都不命中。
3. **排除范围逐条落库**：流感、流行性感冒、恢复期、风热、肺脾气虚、肺胃阴虚、气阴两伤。
   任一命中即出局，方向取保守侧。
4. **「流清涕」只决定加不加风池**，不改变整例走哪条模板。
5. **频次不照搬流感专项方案**的「每日1次、每次30分钟」：
   改为「门诊项目频次参考按本机构针刺排程执行；单次留针时长与疗程由面诊医师按本例耐受和复评结果确定」。

「仅限针刺项目内部」这条边界**钉在构建期**而不是写在代码里（写在代码里会漂）：
别的项目哪天声明了闸门或条件加穴，`npm run build:tcm-governance-tables` 直接失败。

### 实现中被自己的用例抓到的一个真缺陷

闸门最初裸用 `includes`，于是「**无**咳嗽」里的「咳嗽」照样命中——正是本仓库显式测过的
「把否认当阳性」那一类。已加极性判据：只看紧邻词前、被标点截断的一小段，
「恶寒无汗，咳嗽」里的「无」属上一短句，不能算到「咳嗽」头上（反向误判更难发现）。
排除侧刻意保持裸 `includes`——排除是保守方向。

## 四、签字生效后的行为，以及一个只有签字后才暴露的问题

生效后：

- `protocolStatus` = `governed_patient_specific_plan`，`tailoringStatus` = `syndrome_tailored`；
- 不再下发 `deferredGovernedTemplate`；
- 候选穴位 = 肺俞、中府、列缺、太渊、风门、合谷（+ 鼻窍/头项症状时的风池）。

**一个只有批准后才暴露的问题，已一并修掉。** 本模板没有 `syndromeRefinements`
（它整条就是风寒证方案，无需再分证型加减），而原有判据是「有没有匹配到证型加减」——
于是它会被判成 `governed_class_template_not_syndrome_tailored`，`protocolGap` 还会写
「本例已签名证候未匹配到受治理的证型加减方案，请按本例寒热虚实增减」。
**而它恰恰是目录里最贴本例证型的一条**，这句话会让医生以为系统没认出证型。

改法：「个体化方案」的判据本来就是三件事同时成立——病种事实 + 本例已签名证型 + 该条已终审，
而精确闸门把这三件事写成了模板的**准入条件**（`requireCurrentFactAny` /
`requireSignedSyndromeAny` / `adjudicationId` 已 `approved`）。因此走闸门进来的模板天然满足定义。
`protocolStatus` / `tailoringStatus` / `protocolGap` 三者现在**由同一个判据** `syndromeTailored`
决定，不可能再各说各的。

**签字当天端到端实测又抓到一个更严重的缺陷（已修）**：本模板同时也是一条普通的
`respiratory` 模板、`matchAny` 是「咳嗽/咳痰/干咳」，于是**按病名匹配的常规通路可以绕过闸门
把它选出来**——实测「风热咳嗽」与「仅有既往咳嗽」两例都因此拿到了风寒证取穴。
闸门写了「必须同时命中已签名风寒袭肺」，却还留着一扇不看证型的后门，
正是中医师裁定明令禁止的扩大适应证。

修法：带 `preciseSyndromeGate` 的模板**只能**从闸门进，常规通路直接跳过它。
判据放在选择函数里而不是给 `matchAny` 加限定词——`matchAny` 是**病种**判据，
它本来就该匹配所有咳嗽；决定"这条模板能不能用"的是闸门，两者不是一回事。

这个缺陷纯函数套件看不见（闸门判据本身完全正确），只有端到端跑真实编排路径才暴露。
因此另建 `test:cough-template-e2e`，专打**接线**而不是判据。

**未签字路径仍然钉着**：台账里没有登记的闸门模板一律按未终审处理——不启用、但不静默
（`deferredGovernedTemplate` 如实告知）。回归用一条合成的未登记模板验证这条边界，
以免下一条待签字模板进来时这条路径悄悄失效。

## 五、签字是怎么落的

1. `src/data/tcm-acupoint-syndrome-refinement-adjudications.source.json` 里
   `common-cough-wind-cold-template` 的 `adjudicationStatus` 改为 `"approved"`，
   `conflictNote` 置空，`basis` 记入签字结论。**只改数据，未改判据代码**
   （§4 那处修正是签字后暴露的呈现口径问题，与签字本身无关）。
2. `npm run verify:release`（typecheck + lint + 确定性回归 + build）。
3. `IMAGE_TAG=<新tag> ./scripts/deploy-prod.sh` + `npm run verify:deployed-image`。

## 六、回归覆盖

`npm run test:common-cough-template` —— 裁定点名的 7 条逐条钉住：

| # | 情形 | 期望 |
|---|---|---|
| 1 | 风寒咳嗽 + 鼻塞流清涕 | 含列缺、风门、合谷、**风池** |
| 2 | 风寒咳嗽，无鼻窍/头项症状 | 含列缺、风门、合谷，**不加**风池 |
| 3 | 单纯鼻炎无咳嗽 | 不得命中 |
| 4 | 流感 | 只命中流感专项模板 |
| 5 | 感染恢复期 | 只命中恢复期模板 |
| 6 | 风热咳嗽 | 不得命中风寒模板 |
| 7 | 否认咳嗽 / 仅有既往咳嗽 | 不得命中 |

另加：闸门仅限针刺项目、频次不得照搬流感方案、未登记进台账的闸门模板不启用但不静默、
**带闸门的模板不得从常规按病名通路被选出**、
逐穴溯源里风池单列 `conditional_point` 且不与主穴同源同级、重排不新增穴。

> 红旗病例由更上游的门禁拦截（`compileTcmTreatmentRecommendations` 在
> `safetyGate.status === "red_flag"` 时整条不返回治疗建议），不依赖本模板的排除项。
