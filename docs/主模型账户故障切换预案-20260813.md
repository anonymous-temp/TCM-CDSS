## 1. 故障确认（两分钟内分清三种情况）

```bash
# ① 是不是上游账户问题（在服务器上执行，token 不出容器）：
ssh ubuntu@82.156.128.153
KEY=$(docker exec tcm-cdss-prod-tcm-cdss-1 printenv OPENAI_API_KEY)
curl -s -m 30 https://api.deepseek.com/chat/completions -H "Content-Type: application/json" \
  -H "Authorization: Bearer $KEY" \
  -d '{"model":"deepseek-v4-flash","messages":[{"role":"user","content":"hi"}],"max_tokens":1}' | head -c 200
#   402 "Insufficient Balance" → 余额耗尽（走 §2）
#   401/403                    → key 失效/被禁（换 key，同样走 §2 的验证步骤）
#   超时/5xx                   → DeepSeek 平台故障（走 §3）
#   200                        → 上游没问题，去查应用（docker logs / strict health 的其他降级原因）

# ② 看降级史：
tail -20 /home/ubuntu/tcm-cdss/strict-health-alerts.log
```

## 2. 首选处置：充值（本次事故的实测路径）

1. DeepSeek 控制台充值（只有账户所有者能做）。
2. **无需重启任何东西**：探针缓存 5 分钟，充值后下一轮探针自动转绿；容器 healthcheck 一次成功即从 unhealthy 翻回 healthy。
3. 验证：
   ```bash
   TOKEN=$(docker exec tcm-cdss-prod-tcm-cdss-1 printenv CDSS_API_TOKEN)
   curl -s -H "x-cdss-api-token: $TOKEN" "http://127.0.0.1:3016/tcm-cdss/api/model-health?check=1" | head -c 200   # liveCheck.ok=true
   curl -s -H "x-cdss-api-token: $TOKEN" "http://127.0.0.1:3016/tcm-cdss/api/diagnosis/health?strict=1" | python3 -c "import json,sys; j=json.load(sys.stdin); print(j['strictReady'], j['degradedReasons'])"
   ```
4. **预防复发**：在 DeepSeek 控制台设余额告警（系统侧已有 strictReady 监控 cron，见 §5，但它只能事后报警，不能预警余额）。

## 5. 相关监控与验证设施（2026-08-13 已就位）

- **strictReady 告警日志**：`/home/ubuntu/tcm-cdss/strict-health-monitor.sh`，cron 每 5 分钟，
  翻转即写 `/home/ubuntu/tcm-cdss/strict-health-alerts.log`（降级期间每 30 分钟心跳一条，恢复写 RECOVERED）。
- **部署验证含模型活检**：`npm run verify:deployed-image` 在镜像身份一致后强制打一次
  `model-health?check=1`——「代码对」与「上游活」分开证明，任一不成立都算部署失败
  （维护窗口可 `SKIP_MODEL_LIVE_CHECK=1` 显式跳过）。
- 容器 healthcheck 本身每 60s 打 strict 健康（探针缓存 5 分钟），unhealthy 状态可由
  `docker ps` 直接看到——但没人看它，所以才有上面的告警日志。
