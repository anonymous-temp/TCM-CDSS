## 0. 文档效力与冲突裁决

### 0.1 本文是什么

本文是后续研发必须遵守的产品与工程基线，不是当前实现完成情况说明，也不是历史问题清单。

- 本文中的“必须”是发布验收条件。
- 本文中的“不得”是明确禁止的设计或实现。
- 本文中的“建议”是可按成本分期实现的增强项。
- 本文中的“延期”表示已明确不进入当前范围，不得借机扩大需求。
- 某项在代码中已经存在，不代表已经达到本文验收标准。
- 某项在历史文档中出现，不代表仍是有效需求；如与本文冲突，以本文为准。

### 0.2 规则优先级

发生冲突时，按以下顺序裁决：

1. 甲方和产品负责人最新明确锁定的产品决策。
2. 医疗安全、隐私、药事合规和执业责任底线。
3. 本文定义的流程、交互、输出和验收约束。
4. 当前正式数据契约和单一真源约束。
5. 历史设计文档、整改方案和测试报告。
6. 当前代码实现和开发便利。

不得以“当前代码就是这样”“历史回归这样断言”“旧文档要求 C 级才继续”等理由，恢复已经被明确否定的过度阻断。

### 0.3 需求与缺陷分离

- 本文描述应达到的产品行为。
- 测试报告描述某个版本是否达到该行为。
- 历史缺陷不能被包装为产品规则。
- 历史补丁不能被提升为长期算法架构。
- 新发现的问题应更新测试和问题清单，只有形成稳定产品决策后才更新本文。

### 0.4 变更治理

任何修改本文核心约束的变更，必须同时说明：

1. 修改原因和甲方决策来源。
2. 影响的 M01-M05 阶段。
3. 是否增加必填项、阻断项或医生操作成本。
4. 是否改变剂量级候选、审方或采纳权限。
5. 新增或调整的类别级回归。
6. 对现有病例快照、HIS 契约和报告的兼容策略。

## 1. 产品定位

### 1.1 产品角色

灵犀中医 CDSS 是面向门诊医生和基层诊所的中医临床决策支持副驾驶，不是患者自主诊断工具，也不替代执业医师开具医嘱。

系统应完成：

1. 接收医生录入的有限、口语化、可能不完整的病例。
2. 识别真正需要关注的急危重风险和高价值信息缺口。
3. 必要时进行一轮高信息增益追问。
4. 给出西医诊断方向、中医病名证候、病位病性、病机链和治则治法。
5. 给出中药饮片、中成药、西药和非药物中医治疗的结构化候选建议。
6. 调用真实证据检索和合理用药审方，提供可核验依据与风险提示。
7. 支持医生修改、复核、采纳、拒绝和写回 HIS。
8. 保存并恢复病例与推理进度，避免刷新或关闭后丢失。

### 1.2 两项甲方核心能力

以下两项是甲方明确提出的核心能力，必须作为独立验收主线：

1. **中医主要流派的问诊与辅助处方**
   - 流派不能只是一个提示词标签。
   - 必须影响 M02 追问策略、M03 辨证视角、M04 方源选择和加减说明。
   - 必须服从病例事实、红旗、安全、现行药典、说明书、指南和药事规则。

2. **中药味数加减**
   - 处方必须是可编辑的结构化药味表。
   - 支持增、删、改药味和剂量。
   - 显示原方味数与调整后味数。
   - 每次调整都应重新审方并形成新版本。
   - 审方结果用于提示和复核，不得让整个诊疗流程死锁。

### 1.3 北极星体验

医生应感受到的是：

> 填写已有信息，系统判断是否需要追问；需要则问少量真正有价值的问题，回答或跳过后继续；诊断、辨证、病机、治法、方药、审方和随访从上到下逐块出现，每一块都有明确作用，没有重复、占位、假运行或莫名阻断。

## 2. 不可违反的核心产品约束

### 2.1 只有主诉是初始必填项

- 主诉是启动辅助推理的唯一初始必填字段。
- 年龄、性别、生命体征、舌象、脉象、过敏史、用药史、妊娠状态、辅助检查等均不是初始页面的统一必填项。
- 其他字段是否需要补充，必须由当前病例、当前候选方向和临床影响动态决定。
- 特殊人群信息可以成为剂量采纳或正式医嘱前的条件，但不得被误做成整个辨证流程的前置必填。

### 2.2 给什么信息就用什么信息

- 系统应在用户已经提供的信息范围内做有边界的推理。
- 不得为了追求“大而全”而要求医生先完成一份完整教材式病历。
- 信息越少，结论置信度和具体程度应越受限，但流程仍应继续。
- 不得因为缺舌脉、缺生命体征或缺若干辨证维度，就把已经形成的有效分析全部替换成重复的“信息不足”模板。

### 2.3 追问是算法工具，不是门槛仪式

- 追问必须基于信息增益、鉴别价值、红旗排查价值或处方安全影响生成。
- 追问不是固定模板，不是完整度分数低就机械触发。
- 信息已经足够时应直接进入 M03。
- 信息不足但仍可形成有限判断时，可追问，也必须允许跳过后继续。
- 追问不能形成无限循环或 M03 死锁。

### 2.4 流畅度优先，风险提示不等于全局阻断

- 风险应尽量转化为醒目、可操作的提示。
- 红旗、危急生命体征或特殊人群风险可以限制剂量级处方或一键采纳，但不得让整个会话停止。
- M03 风险分析、鉴别和就医建议应继续输出。
- 灵犀审方只作提示和复核依据，不作为全局硬拦截。
- 审方不可用、返回人工复核或命中问题时，不得伪装成通过，也不得让页面永久转圈。

### 2.5 AI 原生，不做规则补丁产品

- 语义理解、信息缺口判断、追问生成、辨证推理和处方论证应充分使用模型能力。
- 确定性规则用于阈值、安全底线、身份归一、剂量边界、合同校验和单调性保护。
- 不得以不断增加关键词、正则和单病例特判替代语义推理。
- 规则和模型的边界必须清楚：模型负责泛化和临床语义，规则负责可验证的硬约束。

### 2.6 发现一个问题，解决一类问题

每个缺陷修复必须回答：

1. 这是单个样例，还是某类输入的共同根因？
2. 同义表达、口语变体、否定、既往、条件句、主体变化是否也会失败？
3. 是提示词、结构合同、状态机、单一真源还是渲染的问题？
4. 是否能通过一个类级不变量消除，而不是新增一个词表补丁？
5. 是否已加入正例、反例和变体回归？

### 2.7 单一真源

- 同一临床事实、诊断、处方、审方结果和阶段状态只能有一个权威结构化来源。
- 页面不得同时从结构化 JSON、Markdown 正则和本地猜测派生三套互相矛盾的结果。
- Markdown 是流式预览和报告格式，不应成为安全权限或药味解析的权威源。
- 医生修改后的药味必须成为后续审方、报告和 HIS 写回共同使用的当前版本。

### 2.8 不向客户展示内部实现

不得在医生界面出现：

- 服务端、知识契约、sentinel、结构化解析、模型修复、V2 JSON、fallback、degraded 等工程术语。
- 模型供应商、内部阶段所有权、内部错误码或证据供应商失败详情。
- 无意义的“证据不足/待检索”“未配置”“检索失败”占位。
- 对医生没有动作价值的安全机制说明。

### 2.9 真实能力，不允许占位假运行

- 模型、证据和审方必须实际调用并可观测。
- 不得用固定模板伪装成模型推理。
- 不得在已经失败或已经返回受限状态后继续显示“正在生成候选方药”。
- 不得先显示“未生成处方”，后台又继续生成并最终失败。
- 没有实际结果的板块不得以完成态展示。

## 3. 目标用户、使用场景与边界

### 3.1 主要用户

1. 门诊中医师和中西医结合医师。
2. 基层诊所医生。
3. 处方复核药师。
4. HIS 集成和医疗机构运营人员。

### 3.2 主要场景

- 常见病、慢病、亚健康和症状性门诊。
- 信息不完整、表述口语化的基层问诊。
- 医生已有部分判断，希望获得补充辨证和候选方药。
- 需要按特定学术流派或院内方案组织问诊和处方。
- 需要在候选方上进行药味加减并重新审方。
- 需要推荐机构能够开展的中医非药物治疗项目。

### 3.3 当前不改变的入口形态

- 保持医生侧 HIS 工作台形态。
- 不改成患者侧极简自诊入口。
- 不新增“为本人咨询”等患者身份切换。
- 追问保持一轮并列呈现若干高价值问题，不改成低效率的一次一问聊天模式。

## 4. 标准端到端流程

### 4.1 正常流程

```text
录入主诉及已有病例信息
  -> M01 结构化采集与事实校验
  -> 红旗与信息价值评估
  -> 如有必要，M02 一轮高价值追问
  -> 医生点选、自由补充或跳过
  -> M03 西医诊断 + 中医辨证 + 病机 + 治则治法
  -> M04 候选方药 + 中成药/西药 + 非药物治疗 + 调护
  -> 灵犀合理用药审方
  -> M05 风险提示 + 随访
  -> 医生修改、复核、采纳、拒绝或写回 HIS
```

### 4.2 流程状态约束

| 状态 | 页面行为 | 允许操作 | 禁止行为 |
|---|---|---|---|
| 等待录入 | 只展示输入与清晰启动按钮 | 编辑、提交 | 提前显示红色“辨证不足” |
| 正在采集 | 显示 M01 运行状态和已完成内容 | 取消 | 空白转圈、重复提交 |
| 需要追问 | 显示一轮结构化问题 | 点选、自由输入、跳过 | 让医生回左侧猜字段、无继续按钮 |
| 正在辨证 | 流式展示 M03 当前板块 | 取消、等待 | 未完成先显示最终失败 |
| 正在方药 | 保留 M03，流式展示 M04 | 取消、等待 | 洗掉 M03、同时显示失败和生成中 |
| 正在审方 | 展示候选方并标明审方中 | 继续查看、修改 | 把审方中当硬锁 |
| 完成 | 展示完整报告与审方结果 | 修改、重审、下载、写回 | 重复下载入口、重复风险卡 |
| 部分完成 | 保留有效上游结果，说明失败板块 | 就地重试该板块 | 清空整份结果、漂浮“重试当前阶段” |
| 红旗 | 展示风险、依据和处置建议 | 查看 M03 风险分析、转诊摘要 | 继续生成不受限剂量处方 |

### 4.3 无死锁不变量

1. 每个运行态必须有终态、取消或超时出口。
2. 每个追问态必须有提交和跳过出口。
3. 任何阶段失败不得让后续状态仍显示运行中。
4. 重试只重试失败阶段，不得静默删除仍与当前病例一致的上游结果。
5. 病历变更后，旧结果必须标记过期，不能继续假装有效。
6. 所有按钮点击必须在 300ms 内出现可见状态变化。

## 5. M01 病例采集需求

### 5.1 输入字段

支持但不强制一次填满：

- 姓名、性别、年龄。
- 主诉。
- 现病史、既往史、过敏史、用药史、家族史和个人史。
- T/P/R/BP/SpO2/意识状态。
- 面象、舌象、脉象、问诊补充。
- 检验、检查和影像摘要。
- 流派或诊疗思路偏好。

### 5.2 事实处理

- 保留医生原文和结构化事实之间的映射。
- 区分阳性、可能、否定、既往、未知和条件性事实。
- “未提及”“不清楚”不得被当作“否认”。
- 区分患者本人、家属、旁人、引用病例和宣教文本。
- 既往正常检查不得自动排除当前新发急症。
- 已缓解或稳定的既往病不得被当作当前证候和开方目标。
- 模型抽取不得覆盖医生明确事实。

### 5.3 面象

- 面象采用直接点击预设和自由文本录入。
- 不做面部图像识别。
- 不单独打开面部画像弹窗。

### 5.4 舌象

舌象采集应参考标准化采集向导，至少支持：

1. 舌面图像。
2. 舌下络脉。
3. 拍摄姿势、距离、光线和避免滤镜提示。
4. 图像质量检测、重新拍摄和人工确认。
5. 图片上传明确征得医生操作确认。
6. 舌照原图不进入浏览器长期快照。
7. GLM-5V 只接收舌照和完成任务所需的最小提示，不发送完整病例和患者准标识信息。
8. 视觉结论只能作为辅助证据，医生可修改。

### 5.5 闻诊

- 闻诊音频和气味采集当前延期。
- 页面可保留普通文字问诊信息，不建设音频识别流程。

## 6. M02 信息度判定与追问

### 6.1 触发逻辑

M02 应回答三个问题：

1. 当前是否存在影响急危重判断的关键不确定性？
2. 当前最主要的两个或多个候选诊断、证候或方证，靠哪个问题最能区分？
3. 哪个缺口会实质改变治法、方药、剂量或特殊人群安全？

只有能明显改变下一步判断的问题才应进入追问。

### 6.2 数量与轮次

- 原则上一轮完成。
- 同屏 1-4 个问题，以 2-4 个为常见范围。
- 每个问题应有明确的信息价值和影响范围。
- 不得为了达到分数而凑问题。
- 回答后自动回填病例并继续，不要求医生重复提交同一内容。
- 医生可跳过后继续有限信息推理。

### 6.3 交互方式

每个问题应包含：

1. 医生可理解的临床问题。
2. 简短、专业的追问理由。
3. 互斥或可明确组合的选项。
4. “其他/医生补充”自由输入。
5. 对应结构化字段或事实补丁。
6. 已选择状态和可修改能力。

点选答案后：

- 直接更新结构化病例和左侧对应字段。
- 只有包含患者实际事实的选项才算已回答；“填写诱因病程”“填写相关诱因”“手动补充”一类导航标签不能被当作临床答案或已核实事实。
- 不把“问题 S1：……”整段复制进底部全局自由文本框。
- 不需要医生再去左侧寻找位置填写。
- 自由输入支持自然语言、多问题合并回答、否定和不确定表达。

### 6.4 流派化追问

每个流派必须有：

- 专属问诊重点。
- 证候或方证锚点。
- 关键鉴别问题。
- 禁忌和不适用边界。
- 对应的高信息增益问题模板。

流派问题只能在当前病例相关时入选，不得机械展示流派知识。

### 6.5 禁止的追问

不得生成：

- “请补充或复核：证候归纳。”
- “请补充或复核：病机关联。”
- “请补充或复核：安全边界。”
- 只有抽象概念、没有医生可回答事实的问题。
- 已经在病例中明确回答的问题。
- 纯粹因为完整度分数低而生成的通用问题。
- “咱不清楚”“未注意”“需询问患者或家属”等不符合医生工作台语境的选项。

## 7. 红旗识别与安全语义

### 7.1 双层架构

红旗识别必须由两层共同完成：

1. **模型语义层**：理解口语、长句、否定、时间、主体、因果、病程变化和规则未覆盖的新表达。
2. **确定性安全层**：处理危急生命体征、明确硬阈值、已治理的急危重模式和模型不可取消的底线。

不得只靠关键词或正则覆盖红旗；也不得让模型单独决定所有安全权限。

### 7.2 单调性

- 模型语义层可以追加风险和建议。
- 模型不得取消确定性阳性红旗或危急生命体征。
- 阴性、既往、条件性和非患者主体必须被正确处理。
- 陈旧正常心电图、肌钙蛋白或既往评估不得清除当前新发胸痛等风险。

### 7.3 医生界面展示

- 有真实风险时才显示红旗板块。
- 没有红旗指征时，不展示固定的 ACS、心律失常、高血压危象、甲状腺、贫血、感染等整套模板。
- “未提及某症状”不能作为低风险的充分依据。
- 风险内容必须包括患者依据、风险等级和具体动作。
- 红旗时继续输出风险分析和鉴别，但不输出不受限的剂量级处方。

---

## 8. M03 西医诊断与中医辨证

### 8.1 输出顺序

M03 应按以下逻辑展示：

1. 有风险时的红旗提示。
2. 西医初步诊断和鉴别。
3. 中医病名、主证和兼证。
4. 病位、病性、寒热、虚实和本标。
5. 总病机和病机演变链。
6. 子病机、权重和对应患者事实。
7. 治则、治法和病机关联。
8. 仍需医生确认的关键不确定性。

### 8.2 西医诊断

必须包含：

- 初步诊断或诊断倾向。
- 诊断状态：考虑、需排除或暂不能确定。
- 与病例事实直接相关的支持依据。
- 反证或不支持点。
- 鉴别诊断及其区分要点。
- 必要的检查或下一步管理。

不得：

- 把舌象、脉象等无关中医信息塞进西医诊断依据。
- 把病历重新抄一遍当作诊断依据。
- 把临床推断伪装成文献参考。
- 仅列病名，不说明为什么。

### 8.3 中医辨证

必须区分：

- 中医病名。
- 主证候。
- 兼证。
- 病位。
- 病性。
- 寒热虚实。
- 本虚与标实。
- 总病机。
- 子病机。
- 证候之间的主次关系。
- 治则与治法。

不得把症状直接当证候，不得把“本虚”当作完整病性词，不得只罗列现病史。

### 8.4 病机链

采用以下证据链：

```text
患者事实 -> 临床解释 -> 病位/病性 -> 主证/兼证 -> 总病机 -> 子病机 -> 治则治法
```

要求：

- 每个关键病机节点必须能回指患者事实。
- 病机必须有因果和演变，不是术语堆砌。
- 子病机应说明主次、权重、对应症状和治疗方向。
- 子病机没有真实外部证据时，不保留空的“证据依据”栏。
- 病位和病性应说明形成判断的四诊依据。
- 证据不足时降低置信度或列为待确认，不凭空补齐。

### 8.5 治则治法

- 先有总体治则，再有针对各病机节点的治法。
- 治法应与病机一一对应。
- 不得把单个方名、药名当治法。
- 不得只给“滋阴降火、宁心安神”等孤立短语而没有病机关联。

### 8.6 参考依据

“参考依据”只允许表示外部可核验来源，例如：

- 指南。
- 共识。
- 药品说明书。
- 药典。
- 正式文献。
- 经典方剂或古籍原文。
- 经治理的本地知识库条目。

“基于本例病史与症状推断；置信度：中”属于临床推理依据，不得命名为参考依据。

### 8.7 去除无意义板块

- 若“辅助诊疗摘要”只是重复主诉，则删除。
- 不重复展示同一诊断、证候、病机和安全说明。
- 报告中不再出现第二个“中医临床辅助诊断报告 V2”卡片。

### 8.8 术语、编码与稳定性

- 失眠等病例的中医病名应使用“不寐”等规范病名，不能把证候名误当病名。
- 西医诊断、中医病名、证候、病位、病性、治则和治法应经过治理词表归一。
- HIS 需要时应输出可追溯的西医和中医编码，编码不得反向篡改临床原文。
- 同一病例、同一知识版本和同一配置重复运行时，允许措辞有变化，但主诊断方向、主证候、核心病机、治则治法和方证方向不得无事实依据地大幅漂移。
- 若因新证据、追问回答或知识版本变化导致结论改变，应说明改变依据。

## 9. M04 候选方药与综合治疗

### 9.1 输出组成

M04 应包含：

1. 方剂定位。
2. 候选方名或自拟方说明。
3. 经典方或基础方出处。
4. 方证对应。
5. 结构化药味表。
6. 方义与君臣佐使。
7. 子病机到药组的对应。
8. 主动随症加减建议。
9. 剂数、疗程和煎服法。
10. 中成药和西药候选。
11. 非药物中医治疗项目。
12. 调护、食疗、情志、运动和监测建议。

### 9.2 处方卡片

处方应以紧凑的结构化方式展示，不写成一大段。

药味表建议字段：

| 药名 | 炮制/规格 | 每剂剂量 | 特殊煎法 | 君臣佐使 | 处方角色 | 对应病机/症状 | 配伍意义 |
|---|---|---:|---|---|---|---|---|

约束：

- 剂数和疗程采用紧凑字段，不单独占据大面积空卡。
- 每味药的意义应有区分，不能所有药都重复同一个总病机。
- 方义应说明配伍协同、制约和主次关系。
- 特殊煎法必须落到具体药味。
- 煎服法应明确浸泡、火候、煎次、合并药液、服用时机和必要忌宜，但不得用冗长免责套话淹没核心信息。

### 9.3 方剂出处

必须区分：

1. **经典方或成方加减**：展示核验后的方名、出处和基础组成。
2. **合方**：分别核验各基础方，不能因为其中一个方命中就把整个合方标成已核验。
3. **自拟方**：展示组方依据，不虚构古籍出处。
4. **单味或小药组**：展示本例配伍意义，不强行套方名和出处。

规则：

- 方剂出处优先从本地方剂库和经典证据层核验，可由模型协助归纳。
- EviMed、文献、指南和其他资料可补充现代证据。
- 未核验时省略出处，不向客户展示“证据不足/待检索”。
- 不得编造古籍、方名、条文、DOI 或指南。

### 9.4 随症加减

系统应主动给出结构化加减建议，不只是给一个空工作台。

每条建议包含：

- 触发症状或体征。
- 加减药味。
- 建议剂量边界。
- 调整理由。
- 对原方结构的影响。
- 需要复核的风险。
- 有可靠经典条文时展示来源。

### 9.5 药味加减工作台

工作台必须支持：

- 新增药味。
- 删除药味。
- 修改剂量。
- 修改炮制或特殊煎法。
- 显示原方味数。
- 显示当前味数。
- 显示增减差异。
- 记录版本和编辑者动作。
- 使用当前编辑后的药味重新调用审方。
- 保证页面、审方、报告和 HIS 使用同一处方版本。

审方命中问题时：

- 清晰展示问题和关联药味。
- 允许医生继续修改或发起药师复核。
- 不得让整个 M01-M05 流程卡死。
- 是否最终采纳由医生及机构药事规则决定。

### 9.6 处方前风险预控

- M04 生成候选处方时，应预先使用与后置审方一致或相容的药味身份、剂量边界、配伍禁忌、特殊人群和重复用药知识。
- 应在生成阶段规避可以确定识别的剂量、十八反十九畏、特殊人群、重复药味和明显配伍问题，降低“系统自己推方、系统自己审不过”的比例。
- 处方前风险预控不能替代灵犀后置审方，也不能为了追求通过率而隐去真实风险。
- 预控结果不单独形成一张噪声卡；只有需要医生动作的内容才进入候选处方说明或审方板块。

### 9.7 中成药和西药

不能只输出以下空泛套话：

- “可在医生确认适应证后使用。”
- “需按说明书和院内规则复核。”
- “可作为饮片方案外的替代方向。”

真正展示具体候选时必须包含：

- 类型和名称。
- 适应问题或诊断。
- 用药定位：联合、替代、短期对症等。
- 规格、用法用量边界和疗程。
- 联用或替代关系。
- 禁忌和关键风险。
- 对应说明书、指南或本地治理证据。

没有足够证据时不生成具体药名和剂量，也不展示空模板卡。

### 9.8 非药物中医治疗

系统应支持甲方提出的项目范围：

1. 针刺疗法。
2. 灸法。
3. 推拿疗法。
4. 拔罐疗法。
5. 刮痧疗法。
6. 针刀。
7. 敷贴。
8. 膏药。
9. 熏洗。
10. 药浴。
11. 耳穴。
12. 埋线。
13. 药熨。
14. 放血。
15. 火烙。
16. 钩割。
17. 挂线。
18. 结扎。
19. 食疗法。
20. 意疗法。
21. 气功导引疗法。
22. 杂疗法。

要求：

- 正式上线时优先推荐当前诊所可开展的项目。
- 机构可配置项目范围、设备、人员资质和禁忌。
- 不在机构能力目录中的项目可隐藏或降为转诊/外院建议。
- 高风险项目必须有适应证、禁忌和医生确认。
- 不得把未经治理的具体穴位、操作参数或频次当成可直接执行医嘱。

### 9.9 调护和健康处方

按病例需要输出：

- 饮食和食疗。
- 起居和睡眠。
- 情志。
- 运动和功法。
- 穴位保健。
- 节气或调候建议。
- 监测指标和复诊触发条件。

不得因处方板块失败而把调护能力一起丢失。

### 9.10 候选方药卡禁止文案

以下内容不得占据候选方药主卡：

- “候选方药状态：未生成。”
- “有限候选，需复核。”
- “审方提示：需调整后复核。”
- 大段“医生已跳过舌脉等软追问……”说明。
- “候选方药方案（非医嘱）”等重复免责标题。
- “流派适配说明”中的泛泛套话。
- “方名与出处由服务端知识契约复核。”

风险和审方统一放到合理用药审方板块。

## 10. 流派能力

### 10.1 默认和示例流派

至少支持以下入口：

1. 不限定：循证安全优先。
2. 经方思路。
3. 时方/验方思路。
4. 温病思路。
5. 脾胃学派。
6. 滋阴/丹溪思路。
7. 温补学派思路。
8. 扶阳学派思路（含火神派传承，但不得与温补学派合并为一个枚举）。
9. 孟河医派。
10. 岭南医派。
11. 海派中医。
12. 院内方案优先。
13. 攻邪思路。
14. 寒凉思路。

后续可增加流派，但必须有明确医家、著作、核心理论、适用范围、问诊重点、代表方、禁忌和治理版本。

### 10.2 流派如何生效

流派必须实质影响：

- M02：追问优先级和鉴别点。
- M03：辨证框架和病机组织。
- M04：候选方来源、组方风格和加减原则。
- 报告：简洁说明采用了哪些流派特征，只有病例相关时展示。

流派不得：

- 覆盖患者事实。
- 为了贴合流派强套证型和代表方。
- 覆盖急危重处置、药典剂量、禁忌、相互作用和审方提示。
- 使用未经治理的流派经验剂量直接生成正式剂量级候选。

## 11. 证据、知识库与出处

### 11.1 证据来源

模型接入不得只接指南检索。应综合：

- 本地中药和方剂知识库。
- 古籍和经典方证证据。
- 现行药典。
- 药品说明书。
- 临床指南。
- 专家共识。
- 文献。
- EviMed 多源检索。
- 院内药事规则和院内方案。
- 灵犀审方结果。

### 11.2 四类依据必须分开

1. **患者事实**：本例明确提供的内容。
2. **临床推理**：模型基于患者事实形成的判断。
3. **外部证据**：文献、指南、说明书、药典、古籍或知识库。
4. **审方结果**：灵犀返回的具体问题和建议。

不得互相冒充。

### 11.3 证据绑定

- 每条外部证据必须说明支持哪个诊断、方剂、药味、剂量或风险。
- 证据列表不得只是页面底部一堆无关联参考文献。
- 外部引用必须可核验，不得编造。
- 若没有可靠外部证据，可保留临床推理，但不要显示虚假的“参考依据”。
- 证据状态和供应商错误保留在内部日志，不向医生展示不专业占位。

### 11.4 方剂与单味药的区别

- 基于经典方加减时，优先核验并展示经典方出处。
- 自拟方强调证候、病机、治法和配伍依据。
- 单味药和小药组通常无法用方剂出处解释，应展示药典、本草、现代证据或本例配伍意义。
- 不得为了填满“出处”栏而生成无意义来源。

### 11.5 知识治理

知识资产至少应覆盖：

- 中西医诊断和编码。
- 中医病名、证候、病位、病性、治则和治法词表。
- 方剂标准名、异名、出处、基础组成、适应证和方证鉴别。
- 中药饮片标准名、别名、炮制品、剂量、煎法和风险。
- 中成药和西药说明书索引。
- 四诊合参和方证鉴别规则。
- 非药物治疗项目、机构能力和禁忌。
- 经典证据、现代证据和审方规则版本。

要求：

- 生成型知识文件不得手工修改，应由可重复构建脚本生成。
- 每条治理数据保留来源、版本、适用范围和审核状态。
- 经验性流派材料、现行药典规则和危险内容必须分层管理。
- 危险、反现代医学或未经核验的经验内容不得进入可执行剂量链。

## 12. 模型与算法接入边界

### 12.1 文本模型

- M01-M04 的文本生成、结构修复、事实抽取和临床复核统一使用 DeepSeek 文本模型；当前生产基线为 `deepseek-v4-pro`，更换模型必须重新完成质量回归。
- 当前不使用 GLM 做文本复核或文本兜底。
- 每个阶段必须能证明真实模型调用已经发生，不能只检查环境变量存在。

### 12.2 舌象视觉

- 舌象视觉使用 GLM-5V。
- GLM-5V 不承担文本诊断主链。
- 视觉失败时明确提示医生手工录入，不静默伪造识别结果。

### 12.3 EviMed

- EviMed 是证据检索服务，不是生成模型后端。
- 检索应覆盖指南、说明书、文献和综合搜索。
- 检索失败不应把整份 prompt 填满“证据不足”占位。
- 检索结果必须经过来源校验、相关性判断和引用净化后再进入医生可见输出。

### 12.4 模型与规则分工

适合模型：

- 口语化病例理解。
- 临床事实语义抽取。
- 信息增益判断。
- 追问生成。
- 西医鉴别。
- 中医辨证和病机链。
- 方证、组方和加减论证。
- 证据相关性归纳。

适合确定性层：

- 生命体征危急阈值。
- 药味身份和剂量单位归一。
- 药典剂量边界。
- 十八反、十九畏及已治理禁忌。
- 特殊人群权限。
- 输出 schema、签名、版本和状态机。
- 审方对象与展示对象一致性。
- 鉴权、限流、快照和隐私。

### 12.5 禁止的算法模式

- 发现一个失败句式就增加一个关键词。
- 用标题正则决定是否有稳定病机或处方。
- 从 Markdown 表格反向解析药味再送审。
- 用固定红旗病种列表填满结果。
- 用模型自评完整度直接控制安全权限。
- 结构化解析失败就把已生成的专业正文全部清空。
- 模型失败后用貌似完整的模板冒充真实结论。

## 13. M05 合理用药审方与随访

### 13.1 审方接入

- 使用灵犀真实合理用药审方接口。
- 请求必须发送当前实际处方的结构化药味、剂量和必要病例摘要。
- 医生编辑后必须用编辑后的处方重审。
- 审方响应中的所有有效 issue ID 必须保留。
- 每个 issue 应分条展示风险、关联药物、依据和建议。

### 13.2 审方呈现

- 审方统一放在“合理用药审方”板块。
- 候选方药卡不重复展示审方状态和审方警告。
- 没有问题时显示绿色、默认折叠的“未发现需特别提示的问题”。
- 有问题时按严重度展示。
- 审方不可用时显示“审方服务暂不可用，请医生或药师人工复核”，不得显示绿色通过。
- 审方只作提示，不全局硬拦截。

### 13.3 风险提示来源

风险提示必须来自：

- 灵犀实际 issue。
- 确定性处方安全规则。
- 明确的患者特殊人群事实。

不得由前端根据几段文字或“风险”“证据”等词语自行升级。

### 13.4 随访

随访按时间轴展示：

- 当日开方前。
- 服药 1-3 日。
- 疗程结束。
- 症状加重或出现红旗时。
- 复诊复评。

每项包含：

- 医生或患者动作。
- 观察指标。
- 触发处置。

不得：

- 保留空的“证据或依据”列。
- 多行重复同一句处置。
- 未生成剂量处方时仍显示固定服药天数。
- 将内部安全说明重复成多张卡片。

## 14. 页面结构与交互

### 14.1 页面布局

- 左侧为病例录入。
- 右侧为中医辅助诊疗报告。
- M01-M05 状态横条放在“中医辅助诊疗报告”标题下，不做全局页面置顶。
- 状态条可以保留 M01-M05 编号；临床内容卡片标题使用“辨证分析、候选方药、合理用药审方”等医生语言，不重复阶段码。
- 结果按流程从上到下逐块出现。

### 14.2 板块职责

| 板块 | 唯一职责 |
|---|---|
| 信息度与追问 | 告诉医生还值得补什么，并接收回答 |
| 西医诊断 | 诊断倾向、鉴别和检查建议 |
| 中医辨证 | 病名、证候、病位病性和病机 |
| 治则治法 | 病机到治疗方向 |
| 候选方药 | 方剂和药味方案 |
| 中成药/西药 | 有证据的其他药物候选 |
| 非药物治疗与调护 | 机构可执行项目和健康管理 |
| 合理用药审方 | 灵犀 issue 和药事提示 |
| 随访 | 时间轴和触发处置 |

同一内容不得跨板块重复。

- 处方生成状态、剂量状态和候选方状态只能放在候选方药板块内，不得作为脱离处方的全局侧栏卡片。
- 审方状态只能放在合理用药审方板块内，不得与候选方药状态混成一段。
- 运行中的中间状态不得被渲染成最终临床结论。

### 14.3 控件行为

- 面象、舌象、脉象等选择面板必须锚定触发按钮。
- 下拉面板不得跑到页面右上角。
- 所有按钮必须有 loading、disabled、success 或 error 状态。
- 重复点击不得重复创建运行或重复送审。
- 失败后允许就地重试，并保留可编辑输入。
- “重试当前阶段”必须放在失败板块内部，并说明重试对象。

### 14.4 报告入口

- 页面只保留一个全局报告下载入口。
- 不在报告正文再放第二个“完整报告”按钮。
- 报告由结构化结果生成。

### 14.5 已明确删除的交互

- 删除底部全局“补充一诉五史、四诊或医生备注……”输入条。
- 删除追问区“安全边界”卡。
- 删除重复的报告摘要卡。
- 删除对医生无意义的技术机制说明。

### 14.6 文案语气

页面面向医生，应使用：

- “暂未获得该信息”。
- “如已掌握，可补充……”。
- “该信息有助于区分……与……”。
- “可跳过并基于现有信息继续分析”。

不得使用：

- “咱不清楚”。
- “未注意”。
- “请询问患者或家属”作为选项文本。
- “下方填写”而没有具体问题。
- 对医生带有责备、教学或系统自辩意味的文案。

## 15. 流式输出、性能与异常体验

### 15.1 流式要求

- M03 和 M04 必须边生成边显示。
- 长推理阶段即使暂时只有 reasoning 内容，也必须通过心跳和阶段状态保持前端判活。
- 最终可用权威净化版替换预览，但不能造成页面闪空或已读内容无解释消失。
- 每个板块应在完成后立即固定，不等待全部阶段结束才一起出现。

### 15.2 体感要求

- 点击后 300ms 内显示已受理状态。
- 不得出现 20-30 秒“正在判断红旗与下一步”但无任何进度反馈。
- 心跳不能只按可见正文字符增长判断。
- 超时、取消和上游断开必须传递到前端。
- 失败终态必须停止 spinner。

### 15.3 质量优先级

- 当前阶段先保证临床效果和输出质量。
- 在不降低质量、证据和安全的前提下持续优化延迟。
- 不得为追求速度关闭必要证据、缩短到输出残缺或用模板替代模型。
- 每次性能优化必须同时比较临床质量回归。

## 16. 病例保存、历史恢复与版本

### 16.1 自动保存

应自动保存：

- 已录入病例字段。
- M01-M05 当前阶段。
- 已完成的结构化结果。
- M02 选择和自由输入。
- 当前候选处方。
- 已采纳的药味编辑版本。
- 审方结果和随访。

### 16.2 恢复

- 关闭页面或刷新后应恢复最近病例。
- 恢复后不得丢失辅助诊疗结果。
- 中断中的阶段恢复为可重试，不得假装完成。
- 新建病例必须有明确确认，并清理旧病例关联状态。
- 快照版本必须与病例版本、处方版本和审方版本绑定。

### 16.3 隐私

- 病例快照应加密并绑定访问身份。
- 姓名、证件号、手机号、住址等直接标识符不得送模型、外部检索或通用 trace。
- 舌照原图不得进入 localStorage 或长期快照。
- 快照应有自动过期和主动清除能力。

## 17. 鉴权、登录与部署

### 17.1 登录

- 访问口令必须稳定可用。
- 错误口令应给出友好、明确的错误，不暴露安全细节。
- 限流后应告诉用户何时或如何重试，不能表现为“正确口令也不正确”。
- 发布新版本不得无意改变现有访问口令。
- API token、模型密钥、审方密钥和服务器凭据不得写进文档、源码或日志。

### 17.2 部署

- 使用不可变镜像标签。
- 线上读取真实服务器环境变量。
- 对外必须通过 HTTPS 或可信反向代理。
- 审方的内网隧道或回环入口必须有健康检查和重连策略。
- 发布后运行与本地相同的线上回归。
- 线上回归不得读取或输出真实密钥。
- 必须有可验证回滚方案。

## 18. 医生决策与 HIS

### 18.1 医生动作

系统应支持：

- 采纳。
- 修改后采纳。
- 拒绝。
- 发起药师复核。
- 下载或复制报告。
- 写回 HIS。

### 18.2 写回要求

- 写回对象必须带病例版本、结果版本和处方哈希。
- 修改后采纳必须写回修改后的结构化内容。
- 页面和 HIS 不得各自维护一套不同的处方真源。
- 审方结论、医生修改和最终采纳均需留痕。
- 系统只输出建议，正式医嘱仍由医生签署。

## 19. 测试与验收要求

### 19.1 测试纪律

大规模深度测试时必须：

1. 先冻结代码并完成全部预定测试。
2. 汇总真实问题和证据。
3. 剔除伪问题、测试夹具错误和过期结论。
4. 按根因和问题类别设计整改。
5. 一类一类修复并扩展回归。
6. 修复完成后重跑同一套测试。

不得在尚未建立完整基线时边测边改，导致后续结果无法比较。

### 19.2 病例多样性

至少覆盖 50 个不同方向的基层门诊病例，并保持：

- 信息不完整。
- 口语化表达。
- 不同年龄和性别。
- 常见病、慢病、疼痛、睡眠、消化、呼吸、妇科、儿科、皮肤、情志等多领域。
- 红旗阳性、阴性、既往、否定、陈旧正常检查和主体混淆。
- 不同流派。
- 有方可锁、无方可锁、自拟方和不宜给剂量等场景。

不得长期只用失眠、归脾汤或少数固定病例证明系统有效。

### 19.3 分阶段质量评审

每个病例逐阶段检查：

| 阶段 | 必查内容 |
|---|---|
| M01 | 事实抽取、极性、时态、主体、回填 |
| M02 | 是否应追问、问题信息增益、选项质量、自由输入、跳过、回填 |
| M03 | 红旗、西医诊断、中医病名证候、病位病性、病机链、治则治法 |
| M04 | 方证、方名、出处、药味、剂量、君臣佐使、加减、中西成药、非药物治疗 |
| 审方 | 是否真实调用、处方对象一致、issue ID 完整、无问题时不噪声 |
| M05 | 风险来源、时间轴、监测和触发处置 |

### 19.4 真实点击旅程

必须用浏览器完成并截图留证：

1. 登录。
2. 新建病例。
3. 只填主诉提交。
4. 触发并回答 M02。
5. 使用自由文本回答。
6. 跳过追问。
7. 查看 M03 流式输出。
8. 查看 M04 流式输出。
9. 编辑药味并重新审方。
10. 展开和折叠审方问题。
11. 下载报告。
12. 刷新和关闭后恢复。
13. 修改病历后重新分析。
14. 失败阶段重试。
15. 移动端和窄屏使用。
16. 舌象上传、质量失败、重拍和手工确认。

每次点击应核对：

- 是否有响应。
- 是否触发正确状态。
- 是否重复请求。
- 是否出现错位弹层。
- 是否出现相互矛盾的状态。
- 是否真的调用模型、证据和审方。

### 19.5 极端输入和操作

覆盖：

- 空白、超长、乱码、emoji、复制表格、HTML、提示词注入。
- 重复点击、连续取消、快速修改、断网、超时、刷新、后退。
- 一条文本同时包含多个患者或家属信息。
- 否定、双重否定、既往、已缓解、条件句和不确定表述。
- 数值单位错误、极端生命体征和药物别名。

### 19.6 发布总闸

发布前至少满足：

- typecheck 通过。
- lint 通过。
- 确定性回归通过。
- 生产 build 通过。
- M02、M03、M04、审方和证据专项通过。
- 真实模型健康检查通过。
- 本地 Live HTTP 回归通过。
- 核心浏览器旅程通过。
- 部署后线上同套回归通过。
- 已知残余风险形成清单，不得口头宣称“100% 完美”替代证据。

## 20. 明确禁止的回退和反模式

后续评审发现以下任一项，应直接要求整改：

- 除主诉外新增统一初始必填项。
- 缺舌脉、缺完整度或辨证充分度不足就卡死 M03。
- 回答追问后仍停在 M03 前。
- 追问没有跳过或继续按钮。
- 追问只给抽象概念，不问患者事实。
- 红旗只靠关键词匹配。
- 无风险也输出整套固定红旗病种。
- 审方失败导致整个流程不可用。
- 审方没有真实调用却显示通过。
- M04 失败后 M05 仍假装基于处方完成。
- 模型已失败但 spinner 继续。
- 候选处方和审方使用不同药味版本。
- 方剂出处写“证据不足/待检索”。
- “参考依据”只是病例复述。
- 西药/中成药只显示空泛套话。
- 子病机证据列大面积为空。
- 一个结论在多个卡片重复。
- 页面出现服务端、V2 JSON、fallback 等内部术语。
- 下拉菜单脱离按钮跑到右上角。
- 重复报告下载按钮。
- 全局底部补充输入条重新出现。
- 用局部正则、关键词和单病例分支替代类级算法修复。

## 21. 延期或不在当前范围

以下事项已明确，不应在当前迭代中反复摇摆：

- 闻诊音频和气味采集延期。
- 面部图像识别不做，面象仅文字或预设录入。
- 不建设患者侧自助诊断入口。
- 不改成一次只问一个问题的聊天式流程。
- GLM 不作为文本模型或文本复核模型。
- 灵犀审方不作为全局硬阻断器。
- LangGraph/ReAct 是目标架构方向，当前仍可使用 M01-M05 线性兼容链路；不得把目标态文档冒充已实现。
- 性能专项在临床质量稳定后单独推进，但当前应持续消除无反馈等待和无效模型调用。
