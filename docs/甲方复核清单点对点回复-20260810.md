## 1. ⑫⑤ 急症排查确认是个「字数验证器」——已改为逐条处置留痕契约

**现象（贵方实测）**：`assessmentSummary = "今天天气不错今天天气不错今天天气不错"` 即可签发
HMAC 凭证，`status` 由 `red_flag` 变 `ready`，`allowDosePrescription` 由 `false` 变 `true`，
`redFlags` 由「胸痛/胸闷伴大汗、放射痛或气促…」变成空数组。

**根因**：`emergency-clearance.server.ts` 与 `diagnosis-safety.ts` 两处的唯一内容判据都是
`assessmentSummary.trim().length < 12`。这是全系统**唯一**一个能把确定性阳性红旗整条抹掉的入口，
而它的判据是字数。

**改法**：新增 `src/lib/emergency-clearance-contract.ts` 作为该判据的**唯一**导出谓词，
签发端、安全门重验、医生端表单三处共用同一份判据（此前签发端与前端各写一遍 `length >= 12`）。
三条判据必须同时成立，缺一即不解除：

1. 当前每一条活动红旗都有且只有一条对应的处置记录（多一条、少一条都不受理）；
2. `disposition` 取自受控集合（已客观排除 / 已转急诊并交接 / 复测后不成立 / 病历记录有误）；
3. `basis` 必须含**客观证据词**——指向一件做过的事（心电图、复测血压、已转急诊完成交接…）。

**方向说明**：这一处的 fail-closed 方向与系统别处**相反**。别处是「证明不了 ⇒ 按有风险处理」；
这里凭证 = 解除约束，因此「证明不了 ⇒ 不解除」。

**现在的实测结果**

| 输入 | 结果 |
|---|---|
| 字数达标、无逐条留痕 | `400 emergency_clearance_attestations_missing` |
| 逐条留痕但 `basis` 是废话 | `400 emergency_clearance_attestation_basis_not_objective` |
| 漏处置任一条红旗 | `400 emergency_clearance_attestation_count_mismatch` |
| 处置记录对不上当前红旗 | `400 emergency_clearance_attestation_finding_unmatched` |
| 写明「心电图无 ST 段抬高，肌钙蛋白阴性」 | `200` 正常签发 |

**接口影响（需贵方配合）**：入参新增必填 `findings[]`；凭证签名版本 v1→v2，
升级前签发的历史凭证一律验签不过（回到「不解除」）。详见接口文档 §4.8。

**回归**：`test:customer-review-20260810`（4 条）、`test:reasoning-signature`、`test:clinical-grounding`。

## 2. ⑫③ `symptoms` 传字符串被静默丢弃 —— 已支持三种形态

**现象**：`symptoms` 为字符串时归一后变成 `{}`，现病史整段消失，请求仍返回 `200`、无任何告警；
红旗由「胸痛/胸闷伴大汗、放射痛或气促」降级为「…即使暂未记录伴随症状…」的弱档。

**根因**：`mergeHisSymptoms` 用 `recordValue()`，对字符串返回 `{}`。接口文档 §3.3.1 写的是
`string`，示例与另外两处写的是 `object`，代码只认 `object`——三方不一致。

**改法**：字符串与字符串数组统一归一到 `symptoms.presentHistory`；与 `hisRecord.fields.xianbingshi`
同时存在时以后者为准，自由文本并入 `symptoms.extraText`，**不丢字**。

**现在的实测结果**：同一段「胸痛伴大汗，向左肩背放射，伴气促，持续20分钟不缓解」，
`string` / `string[]` / `object` 三种形态的安全门状态与红旗数组**逐条一致**。

**回归**：`test:customer-review-20260810`（2 条，含 HIS 字段并存时不丢字）。

## 3. ⑤ 黄芪那条的真身：修复轮指导语是永远打不到的死代码

**现象**：模型没写方义时，药味「配伍作用」栏显示
「臣药，本方中的具体配伍作用需医生结合方义复核」这句零内容套话。

**根因**（比「占位语难看」更深一层）：服务端在**契约校验之前**就用 KB 兜底把这句话写进了
`herb.function`，而契约侧又显式放行该句 ⇒ `candidate_*_herb_*_function(_ungrounded)`
永远不会触发 ⇒ 那一轮「把本方配伍作用写清楚」的修复指导语从未被唤起。

**改法**：兜底分两段。契约前只写 **KB 对齐串**，对不上就留空/留原文，让修复轮真正跑起来；
角色兜底句移到**修复机会用尽之后**的 finalize，只负责「不给医生一个空栏」。
同时把那段修复指导语的措辞改对——旧文案写「服务端最终会用受控功用文本覆写这一列」，
等于告诉模型「随便写，反正会被盖掉」。

**安全面**：编造的高影响方向（如给茯苓写「清热活血，破血逐瘀」）与营销词
**绝不会活过 finalize**，已单独钉住。

**回归**：`test:customer-review-20260810`（3 条）、`test:llm-adjudication-boundaries`（改写为两段语义）。

## 4. ⑪ 穴位：四组八例逐字相同 —— 已补证型加减层，标签改为三态

**现象（贵方实测 + 我方复现）**

| 组 | 两侧穴位 | 两侧 protocolStatus |
|---|---|---|
| 甲流 风寒束表 / 风热犯表 | 逐字相同 | 均 `governed_patient_specific_plan` |
| 不寐 心脾两虚 / 肝火扰心 | 逐字相同 | 同上 |
| 胃痞 湿热中阻 / 脾胃虚寒 | 逐字相同（含「关元（须结合寒热虚实复核）」） | 同上 |
| 右膝痹 寒湿 / 湿热 | 逐字相同 | 同上 |

**根因**：25 条治理模板的 `matchAny` **无一含寒热虚实**，命中判据是病名字符串；
400 穴目录的 `indications` 里也没有性质词，匹配面为零。合同层「个体化」的全部门槛
只是「穴位列表非空 + 频次串非空」——两条都与「有没有按本例证型加减过」无关。

**改法（两步一起上）**

*第一步（零模型、零新数据）*
- 治理分支改用已有的 `indicationEvidenceTerms`（只引用病历原文落点）。该判据当初为
  「产后 → 经带与下腹症状」写好，只铺到了评估分支，治理分支漏了。**「头胀」现在只会被写成「头胀」**。
  举不出落点时**一个症状域也不说**——不给只感冒、无咳嗽的病人写「围绕咳喘与呼吸功能」。
- 逐穴绑定入选依据：`合谷（LI4·手阳明大肠经·主治含发热、恶寒）`、`曲池（LI11·手阳明大肠经·风热犯表加减）`。
- 按贵方意见**保留**「头胀」正则（肝火头胀确实该进头部证候候选）。
- 内部状态码 `protocolGap` 此前被原样印给医生看（`catalog_indication_mismatch`），已改为受控中文映射。

*第二步（联网检索权威来源后录入证型配穴）*
- 新增证型加减层：先命中病种模板，再命中**本例已签名证候**，两把钥匙都对上才算按证型加减过。
  判据只读已签名的证候/病机/治法，**不读病历原文**——「淋雨受寒」不等于辨证结论是风寒束表。
- 覆盖：感冒/流感、咳嗽、不寐、胃痞胃痛、头痛、痛经、痹证、中风面瘫，共 8 个病种 42 条证型加减。
- 来源分层如实标注：
  - 不寐 → **T/CAAM 011-2014《循证针灸临床实践指南：失眠》**（中国针灸学会团体标准，现行）
  - 痛经 → 中国针灸学会官网痛经条目
  - 其余 → 《针灸学》规划教材证型配穴表（多源公开交叉核对录入，
    `authorityTier` 标为 `project_governed_source`，**待贵方权威方案核准后升格**）
- **关元的寒热闸门做在配穴表这一层**，不是我们自造的词表：关元只出现在虚寒类加减里，
  湿热类由 `removePoints` 显式剔除。贵方指出的「确定性层没有寒热属性列」判断正确，
  因此我们没有在 lib 里写词表。

**现在的实测结果**

| 组 | 证型 | 穴位 |
|---|---|---|
| 甲流 | 风寒束表 | 列缺、合谷、风池、太阳、外关 + **风门、肺俞** |
| 甲流 | 风热犯表 | 列缺、合谷、风池、太阳、外关 + **曲池、尺泽、大椎** |
| 不寐 | 心脾两虚 | 安眠、神门、内关、心俞 + **脾俞、足三里** |
| 不寐 | 肝火扰心 | 安眠、神门、内关（**心俞剔除**）+ **行间、侠溪** |
| 胃痞 | 湿热中阻 | 中脘、天枢、足三里、内关 + **阴陵泉、内庭**（**无关元**） |
| 胃痞 | 脾胃虚寒 | 中脘、天枢、足三里、内关 + **关元、脾俞、胃俞** |
| 右膝痹 | 寒湿 | 阿是穴、循经远端穴 + **肾俞、关元、阴陵泉、足三里** |

**顺带修好的一处**：`感冒/流感` 此前不在适应证词表的 respiratory 维度里，
一例「流行性感冒 风寒束表、流清涕」只命中 `upper_airway`（来自「清涕」）而针刺无该标签模板，
整例落回评估态——流感模板永远够不着。已补齐。

**`protocolStatus` 第三态命名**：按贵方提议采用 `governed_class_template_not_syndrome_tailored`，
UI 文案「已命中该病种标准取穴模板，尚未按本例证型加减」。**这是 HIS 写回契约的新枚举值，
请贵方确认后我们再冻结**；若需更短的名字，改一处枚举 + 三处呈现即可，不影响数据。

**回归**：`test:customer-review-20260810`（6 条，含四组配对不得逐字相同、关元闸门、头胀标签、三态）、

## 5. ⑫④ 库存 413 文案教对方删药 —— 已提供真正安全的分片通路

**现象**：`413` 文案写 `split the import into batches`，而落盘是原子 rename **整批替换**。
实测第 1 批 4 味、第 2 批 3 味 → 落盘只剩第 2 批 3 味。系统在错误提示里教对方把第一批药删光。

**改法**：不改「整批替换」这条正确的设计（增量语义要求贵方维护删除事件，风险更高），
而是让「分批」变成一条真实存在且安全的通路：带 `part={importId,index,total}` 的请求
**只写暂存**，集齐全部分片后才做一次原子替换。

| 情况 | 状态码 | 线上库存 |
|---|---|---|
| 分片已收下、仍缺其他分片 | `202`（返回 `missingParts`） | **未被改动** |
| 最后一片到齐 | `200` | 一次性原子替换 |
| 累计超 20000 条 | `413` | 不落盘 |

**实测**：4 味 + 3 味两片 → 落盘 7 味，一味不丢；缺片期间线上库存保持上一版本。

**回归**：`test:customer-review-20260810`（1 条，含「413 文案不得再出现 split into batches」）。

## 6. ⑩ EviMed 指南依据：检索是通的，缺的是回写契约

**现象**：归档 1531 个 json、2280 条 evidence 中，`model_inference` 2177 条 = **95.5%**，
`source` 全部是「病例内推理」；grep「指南/文献依据」→ **0 个文件**。该栏自诞生起产出过 0 条。

**根因（贵方定位正确）**：提示词模板把 `evidence` **预填**成 `model_inference / 病例内推理`，
而呈现层第一个排除的就是 `model_inference`、第二个正则第一个词就是「病例内推理」——
模板在教模型填一个呈现层保证会丢掉的值。

**改法**：照搬已跑通的 EVID-INST 形状。模型**只回 `evidenceId` + 一句 `appliesTo`**，
题名/机构/年份/URL 一律由服务端按 id 反查本轮真检索到的条目字段渲染，
模型侧字段随即删除——**模型无法引入任何新字符串**。集外 id 直接丢弃；
一条都取不到就不显示这一栏（= 今天的行为），绝不回落到自撰题名（贵方 D 组结论保持）。

**新增出参**：`westernDiagnosis.primary.guidelineReferences[]`（M03 响应）、
`diagnoses.westernDetail.guidelineReferences[]`（HIS 方案）。

**回归**：`test:customer-review-20260810`（3 条，含「自撰题名与集外 id 一律丢弃」
与「该栏必须真的出现在医生可见正文里」）。
