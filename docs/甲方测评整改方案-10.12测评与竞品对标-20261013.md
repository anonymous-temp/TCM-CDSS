## 一、结论

### 1. 仍然最急：安全缺口还在线上，等你一句话

按甲方的传参方式，追问只要有一条回答或「跳过」，安全闸门和事实模型就不再读病历正文（`symptoms`）。生产验证：现病史写了呕咖啡样物和柏油样黑便、孕 28 周、长期口服华法林，三种情况都开出了带剂量处方。甲方今天 12 个病例全部落进这个分支。详见附录 E。

这件事和下面的方案无关，修复估计 1–2 天。**请回一句「修」或「先不修」。**

### 2. 这版方案做五件事

1. **回归集换成甲方的真实请求。** 生产留存的请求原样回放；甲方 10 例标准病历已按他们的传参方式建好，每次上线前每例跑 3 次。
2. **只删甲方明确不要的**：西医诊断下面的症状依据、待查依据、检查建议三块，诊断名里的括号，以及所有工程用语。其余板块都留。
3. **留下的每个字段都由模型按本例来写**，服务端不再往里拼句子、套模板，只做核对；核对不过，只让模型重写出错的那一项。
4. **定一次、处处引用**，解决前后不一致和两次结果不同：病名、证型、治法、方名在辨证阶段从教材候选里定下来，后面的依据、鉴别、出处、方义都引用它；同一份病历的结果留存复用。
5. **追问只在答案会改变证型或用方时才问**，最多 1 题；医生看题的时候后台已经按「不回答」算好结果，跳过就直接出。

### 3. 关于把底层换成 DSH + DeepSeek

我的看法：**插件化值得做，但甲方的五个接口不建议搬到 DSH 上跑。**

- DSH 是为对话和长任务设计的 Agent 框架。它没有「一次请求返回一份固定 JSON」的接口，也没有 JSON 模式、输出结构约束、随机种子这些参数；默认开思考，开思考时温度不生效。
- 你自己的两个 DSH 产品，遇到「固定 JSON 的模型调用」都是绕开 DSH 直连 DeepSeek 的。HECRS 那个文件头上写着 "This is deliberately not an agent framework"。中医 CDSS 的每个阶段正是这种调用。
- 响应时间不会因为换框架变快。HECRS 实测，带工具的回合 46 秒起。时间取决于模型写多少字、调用几次。
- 建议走「一套插件、两条车道」：确定性能力整理成一组工具；甲方接口继续直连，直接调用这些工具；同一组工具再包成 DSH 插件，承载对话式改方、复诊对比这类新场景。详见第九节。

### 4. 需要你定的、需要问甲方的

第十一节。需要你定 7 项；需要问甲方 5 项，都是只问不改。

## 二、接口冻结下：删什么、留什么、谁来写

### 2.1 冻结的含义

- 字段名、层级、类型、枚举值、调用顺序、请求格式都不变。
- 只允许两种变化：某个字段不再输出内容（空数组或空串，接口文档本来就约定空值按缺失处理）；某个字段的内容写得更短、更准。
- 每次上线前，用甲方真实请求回放，逐字段比较新旧输出的键和类型。结构有任何差异就不上线。

### 2.2 删除清单

| 删什么 | 字段 | 依据 |
|---|---|---|
| 症状依据 | `westernDiagnosis.primary.supportingFacts` 输出空数组 | 测评（一）1 和（二）1.1 的红框，「方框内内容不建议展示」 |
| 待查依据 | `westernDiagnosis.primary.limitations` 输出空数组 | 同上 |
| 检查建议 | `westernDiagnosis.primary.suggestedChecks` 输出空数组 | 同上 |
| 辨证依据末尾那句「辨证采用病历原文中的关键鉴别事实：…」 | 不再追加 | （一）1 |
| 西医诊断名里的括号内容、「，病因待查」 | `name` 只写规范病名 | （二）1.1、1.2 |
| 各字段里的工程用语 | 见 2.3 | （一）1 |

甲方面板没显示、只在内部用的字段（证据等级、来源标注、病机拆解的内部编号等）这一轮先不动。等甲方给出面板实际读取的字段清单后，清单之外的再停止生成，用来提速。

### 2.3 保留的字段：谁来写、写成什么样、服务端核对什么

「候选」指从教材对照表里按本例症状取出的几行「病—证—治法—代表方—加减」，见第五节。

| 面板板块 | 由模型写成什么样 | 服务端只核对 |
|---|---|---|
| 西医诊断名称 | 一个最可能的规范病名。确实只能到症状层面时写「XX待查」 | 单一病名，无括号 |
| 西医鉴别诊断 | 最多 3 条，每条一句鉴别点和一项建议检查 | 不再插入「（需问诊核实后方可用于排除）」「病历未记录…」 |
| 中医病名 | 从候选里选，用教材的规范叫法 | 名称在候选或国标词表里 |
| 辨病依据 | 一两句：核心症状是什么，为什么归这个病，和哪个病区别 | 提到的鉴别病名要出现在「中医鉴别诊断」里 |
| 主证 | 从候选里选规范证名 | 同上 |
| 兼证 | 默认不写。只有病历里另有一组主证解释不了的症状时才写，最多 1 个 | 写了兼证，辨证依据里必须单独讲到它 |
| 辨证依据 | 每个证型一句，从症状讲到病机；必须解释主诉 | 主证名、兼证名都要出现 |
| 中医鉴别诊断 | 1–2 条，每例必出 | 为空时只重写这一项 |
| 治则 | 从国标 33 条治则里选 1–2 条，不带括号和「兼以、佐以」（第七节） | 术语在清单里；和证型的虚实寒热不矛盾 |
| 治法 | 一行，和证型对应。伴随症状不单独立法 | 治法里每一项都能对应到主证或兼证，否则重写 |
| 复诊计划 | 写给患者：服完这次的药后来复诊，出现什么情况提前来。这一句写在开方之前，所以不写具体天数；天数在处方的剂数里 | 不出现与处方矛盾的天数；不出现写给医生的话 |
| 方名 | 辨证阶段从候选里定，开方阶段不得改名。确无成方时写「自拟方」 | 两个阶段方名一致；不再出现「本例辨证组方」 |
| 药味 | 模型写药和剂量；特殊煎法脚注（先煎、后下、包煎、另煎）取自药典数据 | 剂量封顶、十八反十九畏、妊娠禁忌、儿童折算 |
| 方剂出处 | 按方名查目录得到的数据，如「安神定志丸：《医学心悟》」。自拟方只写「自拟方」 | 出处里的方名等于方名 |
| 剂数与煎服 | 剂数、频次是数字。煎煮方法由模型按本方写成一行用法，点名需要先煎、后下、另煎的药（第七节） | 有特殊煎法的药必须被点到，否则只重写这一句 |
| 方义 | 120–150 字。开头点出方名，讲清君臣佐使，结尾呼应治法 | 方名一致；提到的药都在方里 |
| 随证加减 | 「若…，加 X 10g」，带剂量，优先用教材该证的加减 | 剂量在药典范围内；不再出现「请在药味工作台确定剂量」 |
| 推荐西成药 | 候选仍取自说明书库 | 删掉「不默认联用…」「说明书用法字段已与…指纹绑定」这类说明 |
| 中医治疗（针灸、理疗等） | 按本例证型写具体方案：取穴或部位、操作、疗程、注意点。教材和规范里同病证的取穴作候选 | 按妊娠、出血倾向、皮损、发热等禁忌筛掉不适合的项目。不再输出「本例命中该病种标准取穴模板」「本轮不下发…」 |
| 食疗 | 按证型写一个方子，食材限定在药食同源目录内 | 证型对不上就不出这一项，不再把各证型的方子全列出来 |
| 饮食、起居、情志、运动、穴位保健 | 按本例各写一两句 | 不再追加通用句（现在「三餐定时」会出现两遍） |
| 注意事项 | 最多 5 条短句。数字只能来自处方（剂数、疗程） | 病历已写明的过敏史不再提醒「请先告知有无过敏」；出现普通英文单词就重写该句 |

服务端现在往可见字段里写句子的地方至少有 11 处（附录 D 第 3 点列了文件和行号）。这一步把它们全部去掉：有的字段改由模型写，有的直接不要。

## 四、追问：现在的逻辑、数据和改法

### 4.1 现在的逻辑

- 模型看病历后决定问还是不问，问就出 1–2 题。提示词写的是「不存在能明显改变处置、鉴别、证候或治疗边界的未决问题时就不问」。
- 模型出的题如果被服务端删光（已在病历里回答过、选项不互斥等），服务端会换上一道按主诉类别预置的兜底题，而不是改成不问。
- 事实模型认为某类急症「可能」时，第一题换成服务端预置的急症筛查题，第一个选项是「存在上述任一情况，请补充具体表现」。
- 每题附「信息增益」分数，由模型自己打。

### 4.2 数据

| 指标 | 数值 |
|---|---|
| 回归 92 例里决定「问」的 | 92 例（100%），其中 72% 出 2 题。病历完整度最高的 78 例也全部问了 |
| 模型自评信息增益 ≥0.8 的题 | 69%。这个分数起不到筛选作用 |
| 题目类型（158 题） | 西医鉴别 41%，辨证 33%，急症分诊 13%，用药安全 13% |
| 甲方今天 26 轮追问 | 跳过 21 轮（81%），作答 5 轮 |
| 从发起追问到下一步 | 跳过的中位 11 秒，作答的中位 23 秒 |

### 4.3 问题在哪

1. **每例必问。** 「问不问」交给模型自己判断，它几乎总能找到一个可问的点；删光了还有兜底题。
2. **四成的题是西医鉴别方向。** 对辨证选方没有帮助，医生自然跳过。
3. **跳过不是免费的。** 每次白等约 11 秒。更糟的是，甲方把「跳过」作为一条消息传回来，正好触发第一节的安全缺口；事实模型还会把这句话当成「病情不明」的证据。
4. **急症筛查题的阳性选项不是一句事实。** 甲方把它原样传回时，系统没有当作阳性。今天有一例，医生对急腹症筛查选了「存在上述任一情况」，照常开出了带剂量处方。
5. **舌脉缺失时不问舌脉。** 95% 的题落在现病史上，而对辨证影响最大的往往是寒热、汗、二便和舌脉。

### 4.4 改法（接口不变）

1. **问不问，看候选证型分不分得开。** 先按症状从教材对照表取出本病的候选证型。病历已经能把第一候选和第二候选分开，就返回「不需要追问」。分不开，才问那一个能把它们分开的事实。
2. **最多 1 题。** 只有确实需要澄清急症时才出第 2 题。
3. **选项就是事实。** 每个选项是一句能直接写进病历的话，各自对应一个候选证型，例如「恶寒重、发热轻、无汗」对「发热重、微恶风、有汗、咽痛」。急症题的阳性选项也写成具体事实，选了就按阳性处理。
4. **题目和选项由模型按本例来写**，服务端核对三点：问的事实病历里确实没有；选项对应至少两个不同的候选证型；选项互斥。核对不过就不问，不再换兜底题。
5. **跳过零成本。** 发出追问的同时，后台按「不回答」先把辨证和开方算出来。医生点跳过，后面两步直接取现成结果。「跳过」那句话不进入病历，也不作为任何判断的依据。
6. **回答按事实并入病历。** 回答和原病历一起进入闸门和模型，不再互相顶替。

预期：追问比例从 100% 降到三到四成；跳过后的等待从二十多秒降到几秒。

这样改的依据：

- 竞品的追问是现病史输入框下面一个可以关掉的点选浮层，固定八类（诱因、特征、影响、伴随、寒热、汗出、饮食、二便），每类约 5 个选项。它是帮医生填现病史的，不是出结果之前的关卡。
- 研究上，直接让模型「多问几句」反而会降低诊断准确率；先列出候选诊断、再问最能区分它们的那一个问题，效果最好；模型自己报的把握度不可靠，不能用来决定问不问（来源见附录 G2）。

### 4.5 需要向甲方确认的一点

接口文档里 `m02Plan.decision` 本来就有 `ask` 和 `proceed` 两个值，`proceed` 时题目为空。但今天 26 次调用我们返回的全是 `ask`，甲方面板处理 `proceed` 的那条路可能从来没走过。上线前请甲方在测试环境确认：收到 `proceed` 时面板会不会自动进入下一步。如果不会，就退一步：仍然每次出 1 题，但保证跳过零成本。

## 五、前后一致，以及同一病例输出一致

### 5.1 两种不一致

- **同一次输出里前后矛盾**：方名与出处、治则与治法、辨病依据与鉴别诊断、处方剂数与复诊天数。
- **同一病例两次输出不同**：证型叫法、用方、药味。

### 5.2 现在有多不一致

今晚在生产上做了一次测量：甲方 10 例标准病历按甲方的传参方式，每例重新生成 3 次（绕过结果复用，温度为 0）。

| 项目 | 三次完全一致的病例数（共 10 例） |
|---|---|
| 中医病名 | 10 |
| 证型 | 8 |
| 兼证 | 6 |
| 西医诊断 | 6 |
| 治则 | 5 |
| 方名 | 5 |
| 病名鉴别列出的病 | 3 |
| 药味组成 | 2 |
| 药味和剂量 | 1 |
| 治法的写法 | 0 |

- 药味两两重合度中位 0.83，最低 0.19。方名变化的例子：心悸一例三次是「酸枣仁汤」「本例辨证组方」「酸枣仁汤加减」；蛇串疮一例是「龙胆泻肝汤加减」「本例辨证组方」「龙胆泻肝汤加减」；虚劳一例是「补中益气汤」「补中益气汤合玉屏风散加减」「补中益气汤」。心悸这一例正是测评里批评的「心胆气虚用酸枣仁汤」。
- 30 次输出里：治法带「兼以/佐以」的 83%，治法里出现「安神」的 40%，用了安神类药的 30%，写了兼证的 50%，西医诊断带「病因待查」的 40%、带括号的 40%。
- 证名与标准答案字面一致的 6/30 次，方是教材代表方的 8/30 次。
- 甲方今天自己重复测的情况：病历一字不差时结果相同（走了 30 分钟内的结果复用）。病历略有改动时变化明显：一例（恶心、头晕伴流涕）证型从「风邪外袭，胃气上逆证」变成「风痰上扰证」，方从芎菊上清丸变成半夏白术天麻汤；另一例只把主诉里的「XXX天」改成「3天」，西医诊断就从「头晕，病因待查」变成「急性上呼吸道感染」。

温度设成 0 并不能保证每次相同。联网查到的测量也是这个结论：同一提示词在温度 0 下跑 1000 次能得到 80 种不同输出；DeepSeek 接口没有随机种子参数。能保证逐字相同的办法只有按病历内容留存结果；能让「改几个字结果不大变」的办法是让模型从固定的候选里选。

### 5.3 做法

1. **定一次，处处引用。** 病名、证型（含兼证）、治法、方名在辨证阶段定下来，写进辨证结果里现有的字段。开方阶段只能照用，不能改名改法。依据、鉴别、出处、方义都引用这几项。现在辨证阶段已经在定方（回归里 79% 的病例定了），这一步把它做成每例必定。
2. **从教材候选里选，不凭空起名。** 病名和证型用教材的规范叫法；方用教材的代表方或其合方。本机教材原文里有 614 处「代表方」。甲方 10 例标准答案在教材里都查得到代表方，而今天线上这 10 例里，证名与标准答案字面一致的只有 2 例，方是教材代表方的也只有 2 例（附录 F）。候选由确定性检索给出，所以同一病例每次拿到的候选相同。
3. **核对后只重写出错的那一项。** 2.3 表里的核对项都是确定性的。发现不一致时，把那一个字段连同已定的病名、证型、方名交给模型重写，不由服务端改写，也不整份重来。
4. **同一病例复用结果。** 现在相同请求 30 分钟内复用同一结果，只存在内存里，重启就丢。改成按病历内容的指纹留存到磁盘，默认保留 30 天；标点、空格这类无意义差异不影响指纹。医生要求重新生成时才重算。
5. **病历改几个字，结果不该大变。** 靠的是第 2 点：候选相同，定下来的证型和方就相同。

### 5.4 验收

| 指标 | 门槛 |
|---|---|
| 甲方 10 例各重新生成 3 次，病名、证型、方名三次完全一致（现在是 10、8、5 例） | 10 例都一致 |
| 同样条件下药味组成三次一致（现在是 2 例） | ≥ 8 例 |
| 同一份病历不要求重新生成时 | 逐字相同 |
| 同一次输出内部的交叉核对（2.3 表）不通过的 | 0 |
| 证型为教材规范叫法 | ≥ 9 例 |
| 方为教材代表方或其合方 | ≥ 8 例 |

## 六、红旗

测评里 4 例不该出红旗。今天按甲方传参方式在生产上重跑这 4 例，都不报硬红旗；9 月底当时为什么报已无法复原。但今天仍有四个来源会造成过度提示或漏报：

| 来源 | 表现 | 改法 |
|---|---|---|
| 追问后读不到病历正文 | 该报的不报（第一节） | 第 0 步修复 |
| 事实模型把慢性常见病判成「需专科紧急评估」 | 甲方今天的病例「29 岁，反复胸闷心悸半月」被提示「心血管相关表现需优先复核」 | 只有明确的现症急症才提示：危急生命体征，病历明确写出的出血、卒中表现、胸痛伴大汗或放射痛、气道受累等。「可能」「需排除」不再产生提示，也不限制给药 |
| 否定句被当成线索 | 瘾疹一例写了「无胸闷、气紧，无喉头梗阻感」，仍提示气道受累 | 提示必须有阳性原文；否定句不触发 |
| 「跳过」和问句文字被当成病情 | 「本次未能确认」被事实模型引用为证据；问句里的「胸痛、冷汗、气促」被规则当成阳性 | 跳过不进入病历；只读回答，不读问句 |

红旗接口的返回结构不变。甲方那条红色横幅按哪个返回值显示，需要问他们；知道以后，我们保证只有明确急症时那个值才出现。

## 七、治则治法、煎煮：竞品怎么放，我们怎么写

### 7.1 竞品怎么放

- **治法**：竞品不是把治则并进了治法，而是没有治则。它的面板只有一行治法（截图里是「疏风散寒，消食导滞，和胃止痛」），三个词都是治法层面的，和证型里的要素一一对应。它的病历表单和开放接口里也只有「治法」字段，接口文档里「治则」出现 0 次。
- **煎煮**：竞品的 AI 面板里没有煎煮方法这一块。煎服信息在处方表单里，全是结构化字段：剂数、用法（煎服、冲服等）、每日剂量、频次、单次用量、服用要求、单味药的特殊要求（如先煎）、代煎。AI 只在注意事项第一条带一句服法。

### 7.2 规范怎么说

| 规范 | 要点 |
|---|---|
| 《中医临床诊疗术语 第3部分：治法》（2020 修订版） | 治则是个闭集，连子条目共 33 条：急则治标、缓则治本、标本兼治；扶正祛邪、扶正固本、祛邪扶正；攻补兼施；寒者热之、热者寒之、虚则补之、实则泻之；反治四法；调理阴阳；三因制宜；治未病等。**「治病求本」不在里面。** 治法另分 23 类，「疏风散寒」这类属于治法 |
| 《中医病历书写基本规范》 | 门诊病历不要求单列治则或治法，只要求疾病诊断和证候诊断；也没有主证、兼证的说法 |
| 《中药处方格式及书写规范》 | 特殊煎法注明在药名右上方的括号里，如先煎、后下。用法用量紧随剂数之后写一行，例如「每日 1 剂，水煎 400ml，分早晚两次空腹温服」。没有要求单独的煎煮法段落 |

我们现在的治则，回归里 81% 以「治病求本」「标本兼治」这类总纲收尾；「治病求本」本身不是国标条目。

### 7.3 我们怎么写（字段不动）

**治则**（`therapy.overallPrinciple`）
- 只从国标 33 条里选 1 条，最多 2 条。不带括号，不带「兼以、佐以」，不写「治病求本」。
- 由模型按已定证型的虚实寒热和缓急来选。服务端核对两点：术语在清单里；和证型不矛盾（实证不写补，纯虚证不写泻，没有虚象不写扶正祛邪）。
- 甲方表单的「中医法则」是下拉框。拿到他们的选项后，以他们的选项为准，保证「采纳」能对上。

**治法**（`therapy.overallMethod`）
- 一行，和证型要素一一对应，写法同竞品。

**煎服**（`decoction` 和每味药的特殊煎法字段）
- 剂数、每日几剂、分几次这些数字字段照旧。
- 煎煮方法写成规范要求的那一行用法，并点名需要特殊处理的药，例如「每日 1 剂，龙齿先煎 30 分钟，人参另煎兑入，余药水煎两次取汁 400ml，分早晚两次温服」。由模型按本方来写。
- 不再输出固定的长段说明（浸泡多久、武火文火、「特殊药味按药味表执行」）。

## 八、响应时间

甲方今天实测中位：红旗 4.8 秒、辨证 11.7 秒、开方 10.7 秒；加上追问生成约 5 秒和医生看题的时间，一次就诊从点击到出齐处方约 35–45 秒。9/30 是 2 分钟。

不改接口还能做的：

| 手段 | 省多少（估算） | 说明 |
|---|---|---|
| 跳过追问时提前算好 | 跳过的病例省 20 秒左右 | 发出追问的同时后台就开始辨证，辨证完接着开方。今天 81% 的追问被跳过 |
| 减少追问次数 | 不问的病例省掉看题的 11 秒 | 第四节 |
| 删掉症状依据、待查依据、检查建议 | 西医那一半少写约三成 | 时间基本等于模型写出的字数 |
| 红旗接口复用追问阶段已做的事实抽取 | 约 4 秒 | 现在因为多了一句「跳过」，病历指纹变了，事实抽取重做一遍 |
| 同一病例复用结果 | 重复打开同一病历时接近 0 | 第五节第 4 点 |

估算效果：医生跳过追问或不需要追问时，从点击到出齐处方约 10 秒；回答了追问时约 20 秒。

两点说明：

- 这些都不依赖换框架或换模型。第三方测速显示 DeepSeek 非思考模式约 193 token/秒，耗时基本由输出长度决定；我们各阶段已经是关思考、单次调用。
- 联网查到同一个模型在第三方托管商那里输出速度能到 2–5 倍。这要把病历发给另一家厂商，合规和功能是否对等都没有核实，这一版不采用，只记在这里。

## 九、架构：换成 DSH + DeepSeek 的评估

### 9.1 DSH 的实际情况

以下来自两类材料：本机上 HECRS 和 EviMed 的代码与文档、已安装的 DSH 源码（0.1.2 和 0.1.7 两个版本）；DSH 的官方仓库和文档。

| 方面 | 事实 |
|---|---|
| 定位 | DeepSeek 开源的 Agent 运行框架，MIT 许可，「一切皆插件」。一个进程里可以跑多个会话 |
| 对外接口 | 发一条消息，订阅事件流，等回合结束。发消息的接口立即返回「已入队」，没有同步应答 |
| 结构化输出 | 两个版本的源码里都没有 JSON 模式、输出结构约束、`tool_choice`、`seed`。唯一带结构的输出是子代理的一个工具调用，仍然在 Agent 循环里 |
| 采样 | 默认开思考（高强度），最大输出 25.6 万；开思考时温度不生效 |
| 会话 | 历史逐轮重发；到上下文 80% 时旧历史被模型写的摘要替换 |
| 稳定性 | 全部是预发布版，README 写明没有兼容承诺。线协议、会话格式、适配协议都换过。HECRS 锁在五周前的版本，试升新版第一步就失败 |
| 多租户 | 没有用户和租户的概念。HECRS 生产用 1 个 DSH 进程承载全部会话，前面自己写了鉴权代理；生产量级的并发没有测过 |
| 时延实测 | 框架自身开销很小（假模型 5 步一轮 0.48 秒）。真模型零工具回合 1.3–3.6 秒；带工具的回合 46–414 秒，每轮 3–5 次模型调用。每个场景只有 1–2 个样本 |
| 配套成本 | 两个产品各自维护上千行的适配层、契约测试、版本锁定、模型网关 |
| 官方定位 | DeepSeek 文档称它是「面向 Agent 框架开发者的开发者预览」；两个月发了 31 个预发布版；安全说明里写未经安全审计、不应视为可用于生产；不接受外部代码贡献 |
| 固定开销 | 社区实测首个请求的系统提示加工具定义约 6,000–8,000 token |
| 隐私 | 会话日志默认随请求上传到模型端点，包含用户内容和工具结果，需要显式关闭。病历数据要特别注意这一条 |

### 9.2 你的两个 DSH 产品怎么处理「固定 JSON 的模型调用」

- **HECRS**：记忆合并、地名抽取这类调用走 `DeepSeekJSONClient`，直连 chat/completions，JSON 模式、关思考、温度 0。文件头写着 "This is deliberately not an agent framework"。DSH 只承载流式对话。
- **EviMed**：控制面的模型调用和六个专科引擎都直连 DeepSeek，不经内核。9 月的备忘里写过，CDSS 需要一条「不经内核」的路径。

中医 CDSS 现在五个接口的每个阶段，正是这种「固定 JSON 的单次模型调用」。按你两个产品的现行做法，它们本来就该直连。

### 9.3 对照你的几个目标

| 目标 | 把五个接口搬到 DSH 上 | 说明 |
|---|---|---|
| 响应更快 | 不会更快，多半更慢 | 时间取决于模型写多少字、调用几次。让模型自己调工具，每多一次工具就多一次模型调用；不调工具，也多一层 1–3 秒的回合开销 |
| 接口不变 | 要在外面再包一层 | DSH 不产出固定 JSON，得自己把事件流拼成现在的结构，等于把接口层重写一遍 |
| 同一病例输出一致 | 更难 | 思考开时温度不生效，没有 seed，模型自己决定调哪些工具 |
| 内容由 AI 来写、少模板 | 两条路都能做到 | 这取决于提示词和服务端拼不拼句子，和用不用 DSH 无关 |
| 插件化、好扩展 | 有帮助 | 确定性引擎做成工具、知识做成技能，这套结构是现成的 |
| 稳定 | 有风险 | 甲方接口背后挂一个没有兼容承诺的内核 |
| 运维 | 多一个常驻进程和一层适配 | 生产机 15.5G，八个以上产品共用，swap 已满 |

### 9.4 建议：一套插件，两条车道

1. **先把确定性能力整理成一组工具。** 病历归一、急症判定、教材候选检索、方剂与药味目录、处方核对（剂量、十八反、妊娠、儿童）、取穴候选。每个工具单一职责，返回事实、来源和缺项，可以单独开关。这一步本来也是第二到第五节改造的一部分。
2. **车道一：甲方的五个接口继续直连 DeepSeek。** 直接把上面的工具当函数调用。接口不变、时延可控、同病例一致，都靠这条车道。
3. **车道二：同一组工具包成 DSH 插件。** 加一个 preset 和一份中医写作的 skill，承载五个接口做不了的事：
   - 医生和系统对话式地改方（「患者对半夏过敏，换一下」「改成颗粒剂」）；
   - 复诊时对比上一次；
   - 带教和答疑。
   这才是「中医 CDSS 插件」能发挥作用的地方，也可以挂到 EviMed 或别的 DSH 产品里。
4. **车道二同时当质量对照。** 同一病例让原生 DSH + DeepSeek 自由发挥，和车道一的输出比，看我们的管线有没有把模型本来能写好的东西管坏。这和你给另外两个产品定的验收方式一致：基线、插件开、插件关三方对照。
5. **什么时候把车道一也搬过去**：等 DSH 出稳定版并提供同步的结构化输出，而且在甲方 10 例上实测时延和一致性不差于直连。在这之前不搬。

Anthropic、OpenAI、Google、微软四家的公开指南口径一致：流程可预知、一次调用能完成的任务用固定流程；Agent 是用时延、成本和不确定性去换开放问题上的能力（来源见附录 G2）。

和你那份开发约束的关系：约束里「不强制固定流程」针对的是对话；「工程边界留在代码里」「精确计算交给确定性工具」对两条车道都成立。车道一是和外部系统对接的固定契约，属于工程边界。

### 9.5 如果想先用数字说话：2–3 天的对照实验

- 把「辨证 + 开方」做成一个 DSH preset 加 3–4 个工具，在本机真实 DSH + DeepSeek 上跑甲方 10 例，每例 3 次。
- 车道一跑同样的 10 例 × 3 次。
- 比五项：时延的中位和最长、三次一致率、输出结构合规率、证型和方命中教材的比例、可读性盲评。
- 按数字决定车道二先做哪些场景，以及车道一要不要动。

## 十、分步与验收

## 附录 D：为什么问题这么多——六条原因和证据

### 1. 我们测的不是医生看到的东西

- 医生看到的是甲方面板，面板读的是结构化字段。我们历次优化和验收看的主要是自己的页面和正文。
- 甲方的传参方式和我们页面不同（病历在 `symptoms` 的中文键下、问答在 `conversation`）。代码里把这种调用方叫作「兼容调用方」，按次等路径处理。
- 回归脚本和 223 套测试主要用我们页面的传参方式。我没有找到用甲方的方式（病历在 `symptoms`、回答在 `conversation`）验证红旗和硬边界的测试；现有代码把「有对话就丢弃 symptoms」当作有意为之。
- 10/12 之前服务器不留请求内容。9/29 那轮的「过敏史矛盾」就是按猜测的字段复现的，18 次都没复现出来，于是判断为模型问题并加了规则。真正的原因今天才看到。

### 2. 输出面太大

- 每例约 3,800 字、13 个板块。甲方按板块打勾，板块里任何一句不妥就算不合格。
- 板块越长越容易不合格：西医诊断约 950 字，不合格 90%；复诊计划约 60 字，不合格 13%。
- 竞品按截图估算约 1,500 字，其中外治约 900 字、注意事项约 200 字；诊断到处方只有约 400 字。

### 3. 服务端在替医生写话

| 与中药饮片方案不默认联用，由医生结合重复功效…择一或评估联用 | `medicine-candidate-planner.server.ts:124` |

这些话每一句当初都有理由：可追溯、不撤回结果、不把未知当阴性。但它们是写给审计看的，不是写给门诊医生看的。

### 4. 补丁叠补丁

| 上一轮意见 | 当时的做法 | 这一轮意见 |
|---|---|---|
| 治则都是「治病求本」 | 强制先写「虚则补之/实则泻之（…）」 | 治则错误、与治法矛盾、模板固化 |
| 中医治疗项目机械化、食疗展示错误 | 加教材非药物方案模块（按病种取教材原文） | 食疗与辨证不符、机械化；具体内容未展示 |
| 煎服法不对 | 按方剂类型套煎服模板 | 先煎后下没体现 |
| 方名、出处错误 | 服务端另算出处并标注自拟方 | 方名与出处矛盾、方名未显示 |
| 结果被服务端撤回 | 改成保留结果并加边界标注 | 工程术语 |

每一条都是加，没有一条是减。

### 5. 一个判断被拆给很多个作者

- 西医半和中医半并行生成，互相看不到。
- 方名在辨证阶段锁，药味在开方阶段写，出处、煎服、方义检查、食疗、取穴各由不同的确定性模块补。
- 复诊一句写在开方之前。
- 竞品从界面看是一次生成：显示「已深度思考」后整段给出，前后自然一致。

### 6. 保守规则层层叠加

- 回归 112 例：需补充信息 79%，正常给药 12%。
- 甲方今天 12 例：12 例都是需补充信息、限量给药。
- 每一层单独看都合理，叠在一起，系统的默认状态成了「不确定」。

## 附录 E：测评之外查出的问题

### 安全缺口的生产验证

- 甲方把整份病历（现病史、既往史、过敏史…）放在 `symptoms` 里，把追问的回答放在 `conversation` 里。现病史放 `symptoms`、追问记录放 `conversation` 正是我们接口文档示例的写法。
- 我们的代码假定「`conversation` 里有医生的话时，`symptoms` 是模型整理出来的二手内容，不可信」（`diagnosis-safety.ts` 的 `trustedInputText` 和 `authoritativeFieldOrFallback`）。于是只要追问环节有一条回答或「跳过」，安全闸门和事实模型就不再读 `symptoms`。
- 用测试租户在生产上验证：

| 病历里写的内容 | 不带追问回答 | 带一条「跳过」 |
|---|---|---|
| 现病史：今晨呕咖啡样物约 200ml、柏油样黑便 2 次、头晕心慌 | 报红旗，不给剂量 | 不报红旗；开方阶段给出 9 味带剂量处方 |
| 现病史：孕 28 周 | 不给剂量 | 给出 7 味带剂量处方 |
| 既往史：房颤，长期口服华法林 | 不给剂量 | 给出含牛膝、丹参、川芎、鸡血藤的带剂量处方 |

- 生命体征数值触发的红旗不受影响。
- 同一原因还造成：性别、舌象、脉象、过敏史在闸门里一律变成「未提供」，12 例 12 例都是「需补充信息、限量给药」。甲方当天拿到处方的 11 例，注意事项里 11 例都有「请先告知医生有无药物过敏」，其中 8 例病历里写了过敏史。
- 9/29 那轮整改里的「过敏史矛盾」一条，当时是按猜的传参方式（`guomin` 字段）复现和修的，没修到真正的原因。

### 提示过多的后果

- 用药警示被医生忽略的比例在 49%–96%（[van der Sijs 2006](https://pmc.ncbi.nlm.nih.gov/articles/PMC1447540)）。
- 同一次就诊每多一条提醒，被接受的概率下降约 30%（[Ancker 2017](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC5387195/)）。
- 按严重程度分级的机构，最严重一级的警示接受率接近 100%；不分级的只有 34%（[Paterno 2009](https://pmc.ncbi.nlm.nih.gov/articles/PMC2605599)）。
- 基层胸痛患者里急性冠脉综合征只占 1.5%–3.6%（[Haasenritter 2015](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC4655927/)）。10 例里提示 4 例，比真实急症比例高一个数量级。

### 监管口径

- 没有查到要求门诊辅助系统必须弹危急提示的条文。成文要求集中在两处：医师做最终决定；用药安全检查。
- 「严禁使用人工智能等自动生成处方」出自《互联网诊疗监管细则（试行）》第二十一条，只适用于互联网诊疗。线下由注册医师开具处方。「候选 + 医生采纳」的定位不变。
- 《中药处方格式及书写规范》要求处方写明中医诊断（病名加证型）、用量用法、特殊煎法；有配伍禁忌或超剂量的须医师再次签名（[国家中医药管理局](http://www.natcm.gov.cn/yizhengsi/gongzuodongtai/2018-03-24/3056.html)）。所以十八反十九畏和超量检查不能删，特殊煎法要标出来。
- 《中医病历书写基本规范》第十条要求病历诊断包含中医病名、证候和西医诊断。这是病历的要求，不是面板的要求，对应第九节第 2 项：西医诊断留一个名称供写入病历即可。

### 和本方案有关的研究

- 16 个模型对 60 名中医师的真实病例评测里，模型的典型错误之一就是「因病历里一句睡眠差而加酸枣仁」，另有药味偏多、证名像按症状逐条判断后拼接（[arXiv 2609.17544](https://arxiv.org/abs/2609.17544)）。和甲方这轮的意见是同一类。
- 把生成过程固定成「理、法、方、药」的顺序，试点里处方质量更高、前后不一致更少（[arXiv 2609.25755](https://arxiv.org/abs/2609.25755)）。
- 多个模型分工协作的收益常常很小，而「各环节之间不一致」本身是一大类失败（[Cemri 2025](https://arxiv.org/abs/2503.13657)）。
- 同一提示词重新提问，DeepSeek 会给出不同的药方；可重复性和准确率不相关。稳定要靠固定版块和先确定证型、方名，不能只靠把温度调低。
- 没有查到「用教材的证型—代表方对照表做检索锚」的对照研究；这一条是本方案自己的判断，证据是第八节那张 10 例对照表。

### 追问的研究

- 直接提示模型去追问会降低表现；加上「先估计把握再决定问不问」后诊断准确率提高 22.3%（[MediQ](https://arxiv.org/abs/2406.00922)）。
- 先列候选诊断，再选信息增益最大的问题：任务成功率平均提高 38.1%（[UoT](https://proceedings.neurips.cc/paper_files/paper/2024/hash/2b0e14abd8128e6bf98b6b0bec1cfcbf-Abstract.html)）；诊断错误约减少 27 个百分点（[MedClarify](https://arxiv.org/abs/2602.17308)）。
- 信息缺失时模型自报的置信度和准确率对不上，不能直接当追问的触发条件（[arXiv 2608.09080](https://arxiv.org/abs/2608.09080)）。

- 微软：「Use the lowest level of complexity that reliably meets your requirements.」[指南](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)

### 同输入同输出

- 温度 0 不等于确定：同一提示跑 1000 次得到 80 种输出，原因是结果随服务器批大小变化（[Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)）。
- 处方类任务在温度 0 下，文本逐字不同但语义相似度很高（[arXiv 2604.19598](https://arxiv.org/abs/2604.19598)）。逐字相同只能靠留存结果。
